# Security boundary

- Jellyfin access tokens are session-only fields inside `JellyfinGateway`.
- Server URLs follow decision record 0001 (`docs/decisions/0001-private-lan-http.md`). HTTPS is accepted for every host. Plain HTTP depends on the literal host after WHATWG parsing, never a DNS answer: loopback (`localhost`, `127.0.0.0/8`, `::1`) needs no confirmation; private LAN (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `fc00::/7`, `fe80::/10`, `*.local`, `*.home.arpa`) needs a one-time confirmation per server `Id` and origin; every other host, including CGNAT `100.64/10`, is public and refused before any request. IPv4-mapped IPv6 takes the class of the embedded IPv4 address. A name with an internationalized (`xn--`) label is public for plain HTTP, because the WebView URL parser accepts some invalid punycode (for example `xn--a.local`) that the Rust `url` crate refuses; HTTPS IDN names are unaffected. URLs containing user information are rejected.
- `src/domain/host-class.ts` and `src-tauri/src/url_policy.rs` implement the classifier separately and are both tested against `tests/fixtures/host-classes.json`, so they cannot drift.
- `JellyfinGateway` refuses a public `http://` URL in its constructor, before an HTTP client exists. For a private-LAN `http://` server it sends only the unauthenticated `GET /System/Info/Public` probe, then refuses `AuthenticateByName` and every Quick Connect call until the user has confirmed the warning for that server `Id` at that exact origin. A different `Id` at a confirmed origin, or a known `Id` at a new origin (including another port), asks again. The confirmation record (`fluster.lanHttpConfirmations` in WebView storage) holds only the server `Id` and origin; it never holds or derives from a token. Until saved servers exist (P3), clearing WebView storage is the only way to revoke it. The server `Id` is public (`/System/Info/Public` returns it to anyone), so the confirmation is not proof of identity: a device that holds the same LAN address and port on another network and presents a copied `Id` inherits the confirmation (ADR 0001 decision 7, accepted residual risk).
- After the user confirms, the password, access token, and media cross the LAN unencrypted. Anyone on that network can read them. The warning says so.
- No gateway request follows a redirect, authenticated or not. The Axios client uses the fetch adapter with `maxRedirects: 0`, which sets `redirect: "manual"`. Node's fetch then returns the 3xx response, which Axios rejects. A WebView (checked in WebKitGTK 2.54.2) returns an opaque redirect with status 0 instead, and Axios resolves it as a success, because `settle()` in `axios/lib/core/settle.js` resolves any falsy status. The gateway therefore checks both rejected errors and resolved responses: a status of 0 or 3xx becomes an error telling the user to enter the final address, on every call including playstate reports and `POST /Sessions/Logout` (a refused logout is logged as failed, and the local session is still cleared). A server, or anyone on the path, therefore cannot move the token to another origin. The XHR adapter cannot stop a redirect, so it must not be used.
- Media requests authenticate with a header, never a URL. The playback plan carries the signed-in `MediaBrowser` header (`SessionGateway.authorizationHeader()`) next to token-free stream and subtitle URLs, and the native engine sends it as the typed `authorization` field of the `launch_playback` request. Rust validates it like the socket header (`MediaBrowserAuthorization` in `src-tauri/src/auth_header.rs`: `MediaBrowser` scheme, a `Token="`, at most 4 KB, a valid header value, so no CR, LF, or other control characters), redacts it from `Debug`, and never logs it. It then sets it as the single `http-header-fields` item `Authorization: …` on the per-session mpv handle before `loadfile`. mpv builds FFmpeg's `headers` option from that list for every network open (`mp_setup_av_network_options`, `stream/stream_lavf.c` v0.41.0 lines 214-225), and `sub-add` opens subtitles through the same stream layer (`cmd_track_add` → `mp_add_external_file` → `demux_open_url`, `player/command.c` line 6343 and `player/loadfile.c` line 862), so external subtitles get the same header. A loopback Rust test checks the exact request bytes for both. The handle is destroyed when the session ends, so the header does not outlive it.
- `http-header-fields` applies to every network open on the handle, not only the validated stream and subtitle URLs. Two kinds of open could otherwise carry the header elsewhere, and both are blocked:
  - Redirects and proxies: `stream-lavf-o=max_redirects=0,http_proxy=direct://` (below).
  - References inside downloaded content (a playlist, PLS, mpv EDL, or HLS playlist served as the movie or as a subtitle, sniffed or by MIME type): libmpv starts with `access-references=no`. mpv documents it as "Follow any references in the file being opened" (`DOCS/man/options.rst`, v0.41.0). With it off, the playlist, EDL, CUE, and libarchive demuxers refuse to open (`demux/demux_playlist.c` line 657, `demux/demux_edl.c` line 635), Matroska ordered chapters are skipped (`demux/demux_mkv_timeline.c` line 527), and every nested FFmpeg demuxer open (HLS segments, concat, MOV references) goes to `block_io_open`, which returns `EACCES` (`demux/demux_lavf.c` lines 909-916 and 1066-1072). Automatic external-file loading never reads a network directory (`player/external_files.c` line 107).
  - Loopback tests (`references_inside_the_stream_body_are_never_opened`, `references_inside_a_subtitle_body_are_never_opened` in `src-tauri/src/player/media_auth_wire/references.rs`) serve each of those bodies and assert that a second origin receives nothing; with the option removed both fail (the second origin is contacted for m3u, m3u-MIME URL lists, PLS, EDL, and HLS as the stream, and for EDL and HLS-MIME through `sub-add`).
  - No FFmpeg `protocol_whitelist` is set: with nested demuxer opens blocked, the only URLs FFmpeg opens are the validated stream and subtitle URLs, and its http protocol nests only `tcp`, `tls`, or a proxy.
  - The generated H.264, HEVC HDR10, AV1, ASS, multitrack, and sidecar MKV samples and the BluRay `.m2ts` still play to first frame over loopback HTTP with these options. Verified with mpv 0.41.0 and FFmpeg 9.0.2 only. This is not a generic option bridge: Rust sets one fixed option from one typed value. Rust also refuses any stream or subtitle URL with a credential query parameter (`api_key`, `ApiKey`, `access_token`, `token`, `X-Emby-Token`, any case).
- Jellyfin 10.11.7 and 12.4.0 serve `GET /Videos/{id}/stream` and the subtitle `Stream.{format}` route without authentication (no `[Authorize]` on `VideosController.GetVideoStream` or `SubtitleController.GetSubtitle`, v12.4 at 83d0d0e; observed 206/200 with no header or a bogus token on both fixtures). Fluster still sends the header, so a server or proxy that does require it works, and a token never travels in a URL that proxies, logs, or browser history keep.
- The stream URL is passed directly from the typed Tauri load request into in-process libmpv. It never appears in a child-process argument, environment variable, or IPC socket.
- Rust exposes load, surface geometry, pause, seek, volume, mute, audio/subtitle selection, fullscreen, and stop. It does not accept arbitrary mpv commands.
- Rust also exposes `discover_servers` (P3-03; a new command, approved by the user on 2026-11-07). It takes no arguments. It sends one fixed datagram, the 22 bytes `who is JellyfinServer?` and nothing else (no token, device id, or user data), from an ephemeral UDP port on `0.0.0.0` to `255.255.255.255:7359`, and closes the socket after 2 seconds. Jellyfin listens on IPv4 only (`AutoDiscoveryHost.cs` at v10.11.7 and v12.4, `IPAddress.Any`), so there is no IPv6 discovery. Any device on the network can answer, so every reply is untrusted: Rust reads at most 64 datagrams, drops any over 4 KB or that is not JSON with string `Address`, `Id`, and `Name`, accepts only an ASCII id of at most 64 characters, strips control characters from the name and caps it at 128 characters, and keeps a reply only when its `Address` passes `url_policy::parse_allowed_url` (HTTPS for any host; plain HTTP only for loopback and private-LAN hosts; no user info, fragment, or query) and is at most 2 KB. A public `http://` address, including CGNAT `100.64/10`, is dropped and never shown or probed. It returns at most 16 servers, deduplicated by id. Rust never logs addresses, ids, names, or reply bodies (the `trace_canary` test scans `discovery.rs`), and the only error is fixed text. The frontend adapter also replaces every failure with fixed text. A listed server is not trusted either: choosing it only fills the server URL, and the gateway then normalizes and classifies that URL, sends the unauthenticated `/System/Info/Public` probe, and asks for the private-LAN plain-HTTP confirmation exactly as for a typed address. A spoofed reply can therefore at most list a server the user then probes; it cannot skip the confirmation or receive a credential without the user signing in to it.
- On Linux, Rust serves MPRIS on the session bus (`src-tauri/src/media_controls/`). Any process on the user's session bus can read what it exposes and send it requests. It exposes only the item title, length, play state, and position; the track id is `/app/fluster/Fluster/Track/<n>` with n a per-run session counter, never an item id, URL, token, or play-session id (`redaction_canary_*` tests in `media_controls`). Requests are a closed set: play, pause, play-pause, seek, set-position, and stop. The first five call the typed `MpvController` methods; stop is the typed `fluster://media-control` event. `OpenUri` fails, so the desktop cannot make Fluster open a URL.
- Rust also exposes `realtime_connect` (server URL and Authorization header) and `realtime_disconnect` for the Jellyfin server socket. The socket lives in Rust because the WebView's WebSocket API cannot send an `Authorization` header and tokens never go in URLs. The server URL must pass the same host-class, no-credentials policy as playback URLs, and the socket uses `ws://` only where `http://` is allowed (`wss://` everywhere else); the header must be a `MediaBrowser` header with a token and no control characters, and is marked sensitive. Rust forwards only typed `user-data-changed` and `connection` events, never logs the URL, header, or server responses, and reports connection failures only as fixed descriptions. `SessionGateway.authorizationHeader()` is the only TypeScript accessor for the header; it is used for this command and for the playback plan's `authorization` field.
- tungstenite trace-logs the full socket handshake request, including the `Authorization` header. Fluster installs no `log` or `tracing` logger, and the `logger_guard` Rust test fails if a logger crate enters `Cargo.lock`. Anyone adding a logger must first cap the `tungstenite` and `tokio_tungstenite` targets below trace and prove with a canary test that the header never reaches log output.
- libmpv starts with application-controlled configuration loading and default input bindings disabled, preventing user scripts or config from changing playback policy.
- FFmpeg's http protocol appends its custom `headers` option to every request, including requests to a redirect target on another origin (`http_connect` in `libavformat/http.c`, FFmpeg master at 6eb1078: `if (s->headers) av_bprintf(&request, "%s", s->headers);`; the redirect branch of `http_open_cnx_internal` resets only the HTTP-auth state). mpv builds that option from `http-header-fields` (`mp_setup_av_network_options` in `stream/stream_lavf.c`). Checked locally with mpv 0.41.0 and FFmpeg 9.0.2: a header set with `--http-header-fields` reached a second origin after a 302. Fluster therefore starts libmpv with `max_redirects=0` in `stream-lavf-o`, so FFmpeg fails the open on any redirect (`redirects++ >= s->max_redirects` returns `AVERROR(EIO)`); the same check showed the second origin received nothing. Residual risk: the `max_redirects` AVOption exists in FFmpeg 6.1 and 7.1 and later but not 7.0; with FFmpeg 7.0 mpv ignores the unknown option (logged only at verbose level) and redirects are followed. The release AppImage must bundle an FFmpeg that has it, because with FFmpeg 7.0 the `Authorization` header would follow a redirect to another origin. A loopback Rust test (`redirects_are_refused_while_the_header_is_set`) checks that the redirect target receives nothing while the header is set.
- FFmpeg's http protocol tunnels through the `http_proxy` environment variable unless its own `http_proxy` option is set (`http_open_cnx_internal`, `libavformat/http.c` FFmpeg 9.0.2 lines 252-257), which would hand the header to a proxy. Every handle sets `http_proxy=direct://` in `stream-lavf-o`; a value that does not start with `http://` disables the proxy, and the option overrides both the environment and mpv's `http-proxy`. Test: `static_and_hls_handles_never_use_an_http_proxy`.
- libmpv also starts with `ytdl=no`. The `[libmpv]` built-in profile does not disable it, and the built-in `ytdl_hook` script retries a failed load by running yt-dlp with the full stream URL (which includes the play-session ID) as a process argument.
- Rust errors redact URLs and query strings. The frontend does not log request objects, authenticated URLs, passwords, or tokens.
- External subtitle URLs must use the stream's origin (scheme, host, and port) and HTTP(S), must not carry credentials, and are authenticated only by the header. Stream, subtitle, and image URLs are built from the normalized server URL, so they share its host class. Rust re-checks stream and subtitle URLs with the same host-class policy before libmpv sees them; Rust does not see the confirmation and does not need it, because a load request only arrives after the gateway has signed in.
- The browser player is development-only. A `<video>` element cannot send an `Authorization` header, so it requests the token-free stream URL and never receives the header. It plays on 10.11.7 and 12.4.0 because their stream route is anonymous; a server or proxy that requires auth there refuses it. It does not persist the URL and does not provide authoritative decode diagnostics.
- Tauri is pinned to an exact version because the native composition accesses platform WebView handles. The WebView CSP allows HTTPS and plain `http:` in `connect-src`, `img-src`, and `media-src` for user-selected Jellyfin servers, but does not load remote fonts or scripts. CSP host sources cannot express CIDR ranges or `*.local` alone in a way that covers IP literals, so the CSP is not the plain-HTTP enforcement point; the gateway (before any request) and the Rust URL policy are. CSP still blocks every other script, style, and font origin. wry documents that the Linux and macOS custom-protocol origins allow mixed-content `http` fetches (`with_https_scheme`, wry 0.55.1 `src/lib.rs`). macOS uses Tauri's private API support and therefore is not intended for Mac App Store distribution.

## Planned: server conversion over HLS (decision 0002)

Not implemented yet; the code above still plays only `Static=true` URLs. When P10-04 lands, this section replaces the planned wording with the tested boundary.

- A `TranscodingUrl` is never used as given. Playback Negotiation rebuilds it as a same-origin `/videos/{id}/master.m3u8` or `/audio/{id}/master.m3u8` URL, removes every credential parameter, sets `EnableTrickplay=false`, and refuses `SubtitleMethod=Hls`. `DynamicHlsController` is `[Authorize]` and reads the header token before any `ApiKey` query, and the server copies the master request's query string into variant and segment URLs, so no HLS URL carries the token (sources in decision 0002, Q1).
- Rust validates every HLS playlist before mpv reads it (E1-B, approved by the user 2026-11-07; E1, trusting server playlists, was rejected because FFmpeg's HLS demuxer does not check the origin of playlist URIs, `hls.c` lines 867-905). Only a launch with the typed `delivery: "hls"` field takes this path. Rust fetches the master and every variant playlist with the header and no redirects, resolves every URI line and every `URI=` attribute (stream, i-frame, media, map, key, session key, image), and rejects the whole playlist unless each one is HTTP(S) on the server's origin with no user info and no credential parameter. mpv reads only Rust's validated copies, served from a loopback server on `127.0.0.1` with a random per-session path that closes with the session. `access-references` is turned on only for these sessions, because FFmpeg must open the variants and segments; static sessions keep it off. `max_redirects=0` must reach the nested segment opens. Loopback tests must show a cross-origin URI in a playlist is refused and a redirected segment sends nothing to a second origin.
- The master URL must be on the signed-in server's origin. mpv loads the loopback master only with per-file `demuxer=lavf,demuxer-lavf-format=hls`, so a failed `hls` open can never fall back to mpv's playlist demuxer, which would play each server segment as a top-level file with references on. FFmpeg's segment demuxers may not open anything (`nested_io_open`, `hls.c` FFmpeg 9.0.2 lines 1898-1906). The per-file format is cleared after the file loads, before `sub-add`.
- External subtitles on converted sessions are never `sub-add`ed from the server (approved by the user 2026-11-07): Rust fetches each with the header from the server's origin, refuses any body that is not a known subtitle format or that names a playlist, EDL, or reference format, and serves the checked copy from the same loopback server.
- mpv sends the header to the loopback server too, because `http-header-fields` applies to every open on the handle; that server is Fluster's own listener on `127.0.0.1`, never logs requests, and answers only the session's exact paths.
- Defence in depth: Rust also rejects a playlist body that contains a credential parameter name (`ApiKey`, `api_key`, `access_token`, `Token`, `X-Emby-Token`, any case) anywhere, or a playlist or subtitle body that contains the token value itself, and the launch fails closed.
- E2 (accepted by the user with a canary test, 2026-11-07): a server that ignores `EnableTrickplay=false` would put the token in a playlist body. Fluster does not request libmpv log messages and never logs, persists, or displays playlist bodies; the fail-closed check above stops it before mpv; a canary test asserts the token reaches no log, error, diagnostic, event, or UI text.
- `DELETE /Videos/ActiveEncodings` carries `deviceId` and `playSessionId` in its query, like the static stream URL carries `PlaySessionId`. Neither is a credential; both stay out of logs, errors, and diagnostics (I4).
- The streaming limit is a non-secret preference and may be stored in WebView storage.

No player preferences are persisted in this slice. Authentication secrets must not be added to persisted Query caches, analytics, crash payloads, or diagnostic exports.

In-process rendering intentionally trades fault isolation for integrated presentation. A native libmpv or graphics-driver crash can terminate the application; normal playback errors and end-of-file events are recovered in the player lifecycle.
