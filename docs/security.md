# Security boundary

- Jellyfin access tokens are session-only fields inside `JellyfinGateway`.
- Server URLs follow decision record 0001 (`docs/decisions/0001-private-lan-http.md`). HTTPS is accepted for every host. Plain HTTP depends on the literal host after WHATWG parsing, never a DNS answer: loopback (`localhost`, `127.0.0.0/8`, `::1`) needs no confirmation; private LAN (`10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `fc00::/7`, `fe80::/10`, `*.local`, `*.home.arpa`) needs a one-time confirmation per server `Id` and origin; every other host, including CGNAT `100.64/10`, is public and refused before any request. IPv4-mapped IPv6 takes the class of the embedded IPv4 address. A name with an internationalized (`xn--`) label is public for plain HTTP, because the WebView URL parser accepts some invalid punycode (for example `xn--a.local`) that the Rust `url` crate refuses; HTTPS IDN names are unaffected. URLs containing user information are rejected.
- `src/domain/host-class.ts` and `src-tauri/src/url_policy.rs` implement the classifier separately and are both tested against `tests/fixtures/host-classes.json`, so they cannot drift.
- `JellyfinGateway` refuses a public `http://` URL in its constructor, before an HTTP client exists. For a private-LAN `http://` server it sends only the unauthenticated `GET /System/Info/Public` probe, then refuses `AuthenticateByName` and every Quick Connect call until the user has confirmed the warning for that server `Id` at that exact origin. A different `Id` at a confirmed origin, or a known `Id` at a new origin (including another port), asks again. The confirmation record (`fluster.lanHttpConfirmations` in WebView storage) holds only the server `Id` and origin; it never holds or derives from a token. Until saved servers exist (P3), clearing WebView storage is the only way to revoke it. The server `Id` is public (`/System/Info/Public` returns it to anyone), so the confirmation is not proof of identity: a device that holds the same LAN address and port on another network and presents a copied `Id` inherits the confirmation (ADR 0001 decision 7, accepted residual risk).
- After the user confirms, the password, access token, and media cross the LAN unencrypted. Anyone on that network can read them. The warning says so.
- No gateway request follows a redirect, authenticated or not. The Axios client uses the fetch adapter with `maxRedirects: 0`, which sets `redirect: "manual"`. Node's fetch then returns the 3xx response, which Axios rejects. A WebView (checked in WebKitGTK 2.54.2) returns an opaque redirect with status 0 instead, and Axios resolves it as a success, because `settle()` in `axios/lib/core/settle.js` resolves any falsy status. The gateway therefore checks both rejected errors and resolved responses: a status of 0 or 3xx becomes an error telling the user to enter the final address, on every call including playstate reports and `POST /Sessions/Logout` (a refused logout is logged as failed, and the local session is still cleared). A server, or anyone on the path, therefore cannot move the token to another origin. The XHR adapter cannot stop a redirect, so it must not be used.
- Media requests authenticate with a header, never a URL. The playback plan is token-free: it holds only token-free stream and subtitle URLs and never the header, so React state, props, and Query caches cannot carry it. The coordinator passes the native engine a reader (`() => gateway.authorizationHeader()`) as `launch`'s second argument; only `NativePlayerEngine` calls it, at launch, to fill the typed `authorization` field of the `launch_playback` request. The browser and e2e engines never call it (the redaction canary test in `player-view.test.tsx` covers the view, the Query cache, and the engine arguments). Rust validates it like the socket header (`MediaBrowserAuthorization` in `src-tauri/src/auth_header.rs`: `MediaBrowser` scheme, a `Token="`, at most 4 KB, a valid header value, so no CR, LF, or other control characters), redacts it from `Debug`, and never logs it. It then sets it as the single `http-header-fields` item `Authorization: …` on the per-session mpv handle before `loadfile`. mpv builds FFmpeg's `headers` option from that list for every network open (`mp_setup_av_network_options`, `stream/stream_lavf.c` v0.41.0 lines 214-225), and `sub-add` opens subtitles through the same stream layer (`cmd_track_add` → `mp_add_external_file` → `demux_open_url`, `player/command.c` line 6343 and `player/loadfile.c` line 862), so external subtitles get the same header. A loopback Rust test checks the exact request bytes for both. The handle is destroyed when the session ends, so the header does not outlive it.
- `http-header-fields` applies to every network open on the handle, not only the validated stream and subtitle URLs. Two kinds of open could otherwise carry the header elsewhere, and both are blocked:
  - Redirects and proxies: `stream-lavf-o=max_redirects=0,http_proxy=direct://` (below).
  - References inside downloaded content (a playlist, PLS, mpv EDL, or HLS playlist served as the movie or as a subtitle, sniffed or by MIME type): libmpv starts with `access-references=no`. mpv documents it as "Follow any references in the file being opened" (`DOCS/man/options.rst`, v0.41.0). With it off, the playlist, EDL, CUE, and libarchive demuxers refuse to open (`demux/demux_playlist.c` line 657, `demux/demux_edl.c` line 635), Matroska ordered chapters are skipped (`demux/demux_mkv_timeline.c` line 527), and every nested FFmpeg demuxer open (HLS segments, concat, MOV references) goes to `block_io_open`, which returns `EACCES` (`demux/demux_lavf.c` lines 909-916 and 1066-1072). Automatic external-file loading never reads a network directory (`player/external_files.c` line 107).
  - Loopback tests (`references_inside_the_stream_body_are_never_opened`, `references_inside_a_subtitle_body_are_never_opened` in `src-tauri/src/player/media_auth_wire/references.rs`) serve each of those bodies and assert that a second origin receives nothing; with the option removed both fail (the second origin is contacted for m3u, m3u-MIME URL lists, PLS, EDL, and HLS as the stream, and for EDL and HLS-MIME through `sub-add`).
  - No FFmpeg `protocol_whitelist` is set: with nested demuxer opens blocked, the only URLs FFmpeg opens are the validated stream and subtitle URLs, and its http protocol nests only `tcp`, `tls`, or a proxy.
  - The generated H.264, HEVC HDR10, AV1, ASS, multitrack, and sidecar MKV samples and the BluRay `.m2ts` still play to first frame over loopback HTTP with these options. Verified with mpv 0.41.0 and FFmpeg 9.0.2 only. This is not a generic option bridge: Rust sets one fixed option from one typed value. Rust also refuses any stream or subtitle URL with a credential query parameter (`api_key`, `ApiKey`, `access_token`, `token`, `X-Emby-Token`, any case).
- Jellyfin 10.11.7 and 12.4.0 serve `GET /Videos/{id}/stream` and the subtitle `Stream.{format}` route without authentication (no `[Authorize]` on `VideosController.GetVideoStream` or `SubtitleController.GetSubtitle`, v12.4 at 83d0d0e; observed 206/200 with no header or a bogus token on both fixtures). Fluster still sends the header, so a server or proxy that does require it works, and a token never travels in a URL that proxies, logs, or browser history keep.
- The stream URL is passed directly from the typed Tauri load request into in-process libmpv. It never appears in a child-process argument, environment variable, or IPC socket.
- Rust exposes load, surface geometry, pause, seek, volume, mute, audio/subtitle selection, fullscreen, and stop. It does not accept arbitrary mpv commands.
- Rust also exposes `discover_servers` (P3-03; a new command, approved by the user on 2026-11-07). It takes no arguments. It sends one fixed datagram, the 22 bytes `who is JellyfinServer?` and nothing else (no token, device id, or user data), from an ephemeral UDP port on `0.0.0.0` to `255.255.255.255:7359`, and closes the socket after 2 seconds. Jellyfin listens on IPv4 only (`AutoDiscoveryHost.cs` at v10.11.7 and v12.4, `IPAddress.Any`), so there is no IPv6 discovery. Only one search runs at a time (a second call fails with fixed text). On desktop the sign-in screen sends it once when it opens, without a click (decision Q20 A, 2026-11-10), and again only when the user presses "Search again"; returning to the server step from a later step reuses the earlier result. Any device on the network can answer, so every reply is untrusted: Rust reads until the 2-second deadline (neither junk nor a full list ends the search early), drops any datagram over 4 KB or that is not JSON with string `Address`, `Id`, and `Name`, accepts only an ASCII id of at most 64 characters, strips control, zero-width, and bidirectional-override characters (U+200B–U+200F, U+202A–U+202E, U+2060–U+2069, U+FEFF) from the name and caps it at 128 characters, and keeps a reply only when its `Address` passes `url_policy::parse_allowed_url` (HTTPS for any host; plain HTTP only for loopback and private-LAN hosts; no user info, fragment, or query), is at most 2 KB, and is not a loopback address unless the datagram itself came from loopback. A refused reply, such as a public `http://` address including CGNAT `100.64/10`, is never listed or probed; Rust returns only a count, and the UI says "A server answered with an address Fluster won't use over plain HTTP." (ADR 0001 decision 9). Rust keeps each distinct (id, address) pair, at most 16, and returns with each the UDP source address the reply claims and whether the address host is that address. The source address can be spoofed on a LAN, so it is a hint for the user, not authentication. When two replies name the same id with different addresses, the id is marked as conflicting; this still holds once the list is full, because Rust keeps reading until the deadline, marks a kept id that a later reply names at another address, and counts the replies it could not list (the UI then says "More servers answered than Fluster can list."). This makes a spoofed reply visible only when the real server's reply also arrives; an attacker that answers alone, or a real server that never hears the broadcast, produces an ordinary-looking entry. The UI shows "Advertised by <ip>", notes when the address points to another device, and shows the conflict. Rust never logs addresses, ids, names, or reply bodies (the `trace_canary` test scans `discovery.rs`), and errors are fixed text; the frontend adapter also replaces every failure with fixed text. Choosing a listed server only fills the server URL: the gateway normalizes and classifies it and sends the unauthenticated `/System/Info/Public` probe, the sign-in view refuses the server with fixed text unless the probe reports the discovered `Id`, and the private-LAN plain-HTTP confirmation follows exactly as for a typed address. The `Id` check only catches an address that points at a different real server: the `Id` is public, so an attacker's own server can copy it and pass. The user-facing defence is the origin line: the Quick Connect and password steps show the exact origin for every sign-in, typed or discovered, so the user can see where the password or approval goes before giving it. Residual risk: a spoofed server can relay Quick Connect, showing the user a code it obtained from the real server, so approving it on another device signs the attacker in to the real account; the origin line is the only cue. A spoofed reply cannot skip the confirmation or receive a credential without the user choosing it and signing in to an origin they can see.
- On Linux, Rust serves MPRIS on the session bus (`src-tauri/src/media_controls/`). Any process on the user's session bus can read what it exposes and send it requests. It exposes only the item title, length, play state, and position; the track id is `/app/fluster/Fluster/Track/<n>` with n a per-run session counter, never an item id, URL, token, or play-session id (`redaction_canary_*` tests in `media_controls`). Requests are a closed set: play, pause, play-pause, seek, set-position, and stop. The first five call the typed `MpvController` methods; stop is the typed `fluster://media-control` event. `OpenUri` fails, so the desktop cannot make Fluster open a URL.
- Rust also exposes `realtime_connect` (server URL and Authorization header) and `realtime_disconnect` for the Jellyfin server socket. The socket lives in Rust because the WebView's WebSocket API cannot send an `Authorization` header and tokens never go in URLs. The server URL must pass the same host-class, no-credentials policy as playback URLs, and the socket uses `ws://` only where `http://` is allowed (`wss://` everywhere else); the header must be a `MediaBrowser` header with a token and no control characters, and is marked sensitive. Rust forwards only typed `user-data-changed` and `connection` events, never logs the URL, header, or server responses, and reports connection failures only as fixed descriptions. `SessionGateway.authorizationHeader()` is the only TypeScript accessor for the header; it is used for this command and, through the coordinator's launch reader, for the native `launch_playback` request.
- tungstenite trace-logs the full socket handshake request, including the `Authorization` header. Fluster installs no `log` or `tracing` logger, and the `logger_guard` Rust test fails if a logger crate enters `Cargo.lock`. Anyone adding a logger must first cap the `tungstenite` and `tokio_tungstenite` targets below trace and prove with a canary test that the header never reaches log output.
- libmpv starts with application-controlled configuration loading and default input bindings disabled, preventing user scripts or config from changing playback policy.
- FFmpeg's http protocol appends its custom `headers` option to every request, including requests to a redirect target on another origin (`http_connect` in `libavformat/http.c`, FFmpeg master at 6eb1078: `if (s->headers) av_bprintf(&request, "%s", s->headers);`; the redirect branch of `http_open_cnx_internal` resets only the HTTP-auth state). mpv builds that option from `http-header-fields` (`mp_setup_av_network_options` in `stream/stream_lavf.c`). Checked locally with mpv 0.41.0 and FFmpeg 9.0.2: a header set with `--http-header-fields` reached a second origin after a 302. Fluster therefore starts libmpv with `max_redirects=0` in `stream-lavf-o`, so FFmpeg fails the open on any redirect (`redirects++ >= s->max_redirects` returns `AVERROR(EIO)`); the same check showed the second origin received nothing. Residual risk: the `max_redirects` AVOption exists in FFmpeg 6.1 and 7.1 and later but not 7.0; with FFmpeg 7.0 mpv ignores the unknown option (logged only at verbose level) and redirects are followed. The release AppImage must bundle an FFmpeg that has it, because with FFmpeg 7.0 the `Authorization` header would follow a redirect to another origin. A loopback Rust test (`redirects_are_refused_while_the_header_is_set`) checks that the redirect target receives nothing while the header is set.
- FFmpeg's http protocol tunnels through the `http_proxy` environment variable unless its own `http_proxy` option is set (`http_open_cnx_internal`, `libavformat/http.c` FFmpeg 9.0.2 lines 252-257), which would hand the header to a proxy. Every handle sets `http_proxy=direct://` in `stream-lavf-o`; a value that does not start with `http://` disables the proxy, and the option overrides both the environment and mpv's `http-proxy`. Test: `static_and_hls_handles_never_use_an_http_proxy`.
- libmpv also starts with `ytdl=no`. The `[libmpv]` built-in profile does not disable it, and the built-in `ytdl_hook` script retries a failed load by running yt-dlp with the full stream URL (which includes the play-session ID) as a process argument.
- Rust errors redact URLs and query strings. The frontend does not log request objects, authenticated URLs, passwords, or tokens.
- Copy diagnostics (Settings, P13-17) writes a fixed, redacted, seven-line text to the system clipboard when the user clicks Copy: the app version, OS, player and libmpv version, renderer, decode mode, Jellyfin server version, and local-or-remote host class. The text never holds the server name, address, user name, token, or play-session id; its input type has no field for them, free-text values pass through `redactText`, and the server version must be plain dotted numbers. The `redaction canary: diagnostics` test covers it. The decode mode is kept in memory only, with the hardware decoder name and nothing about the item played.
- External subtitle URLs must use the stream's origin (scheme, host, and port) and HTTP(S), must not carry credentials, and are authenticated only by the header. Stream, subtitle, and image URLs are built from the normalized server URL, so they share its host class. Rust re-checks stream and subtitle URLs with the same host-class policy before libmpv sees them; Rust does not see the confirmation and does not need it, because a load request only arrives after the gateway has signed in.
- The browser player is development-only. A `<video>` element cannot send an `Authorization` header, so it requests the token-free stream URL and never receives the header. It plays on 10.11.7 and 12.4.0 because their stream route is anonymous; a server or proxy that requires auth there refuses it. It does not persist the URL and does not provide authoritative decode diagnostics.
- Tauri is pinned to an exact version because the native composition accesses platform WebView handles. The WebView CSP allows HTTPS and plain `http:` in `connect-src`, `img-src`, and `media-src` for user-selected Jellyfin servers, but does not load remote fonts or scripts. CSP host sources cannot express CIDR ranges or `*.local` alone in a way that covers IP literals, so the CSP is not the plain-HTTP enforcement point; the gateway (before any request) and the Rust URL policy are. CSP still blocks every other script, style, and font origin. wry documents that the Linux and macOS custom-protocol origins allow mixed-content `http` fetches (`with_https_scheme`, wry 0.55.1 `src/lib.rs`). macOS uses Tauri's private API support and therefore is not intended for Mac App Store distribution.

## Server conversion over HLS (decision 0002, P10-04)

The boundary below is implemented and tested with mpv 0.41.0 and FFmpeg 9.0.2 (Arch Linux, headless). Test names are Rust tests under `src-tauri/src/player/` unless noted.

- Only a launch whose plan carries the typed `delivery: "hls"` field takes this path; there is no new Tauri command and the command allowlist is unchanged. The plan also carries the signed-in `serverUrl` (with any base path) and `mediaKind` (`videos` or `audio`); Rust refuses a plan with a missing or unknown delivery (`launch_requests_need_a_typed_delivery`). `LaunchMedia` (`player/media.rs`) picks the handle options and the loader from that field, so a static plan never gets references and an HLS plan is never loaded with a plain `loadfile` (`loadfile_is_issued_only_by_the_two_typed_loaders` scans the production sources: `loadfile` appears only in `network::load_static` and `network::load_validated_hls`, and only `media.rs` picks a `ValidatedHls` handle). `launch_playback` runs off the main thread, because the checks below fetch over the network before mpv starts. Only one launch may be pending; a second is refused until it becomes a session or fails. The checks run on their own thread under a 60 s deadline (20 s per playlist request, 45 s per subtitle); `stop` (Back, Stop, window close) cancels a pending launch at once: a cancelled launch returns without starting a session, anything it created before the cancel (an mpv handle, the surface attach) is torn down, and an abandoned check sends no further request (`stop_during_a_converted_check_returns_at_once_and_sends_nothing_more`, `a_converted_check_past_its_deadline_times_out`). Those tests cover the pending slot and the check thread only; the controller's re-checks after `Mpv::with_initializer` and before installing the session are untested, because they need a Tauri `AppHandle`. A surface attach is refused while another session's render context exists; a timed-out attach is marked abandoned so a late run installs nothing, the render state holds the mpv core so the core is destroyed only after its render context, and a detach queued behind a failed attach resets the background only for its own session.
- A `TranscodingUrl` is never used as given. Playback Negotiation rebuilds it (`src/lib/jellyfin/hls-url.ts`), and Rust re-checks the result (`player/hls/master_url.rs`) before any request: the URL policy (I5), the signed-in server's origin, the path `{base}/videos/{itemId}/master.m3u8` (or `/audio/` for an audio-only plan; fixed segments in any case) for the plan's item, exactly one `MediaSourceId` naming the plan's source, any `PlaySessionId` equal to the plan's, `EnableTrickplay=false` exactly once, no credential parameter (`ApiKey`, `api_key`, `access_token`, `Token`, `X-Emby-Token`, `ApiToken`, `AccessToken`, any case, after trimming and percent decoding), no `EnableSubtitlesInManifest`, a `SubtitleMethod` of `Encode`, `Embed`, `External`, or `Drop` only (so `Hls` and numeric values are refused), and no parameter name with whitespace or a control character. Every other URL is refused for HLS delivery (`hls_master_urls_follow_the_hls_url_rules`). The 44 plans the TypeScript negotiation builds from the recorded conversions of both servers, on a server with and without a base path, are shared vectors (`tests/fixtures/hls-master-urls.json`, written and checked by `src/lib/jellyfin/hls-rust-vectors.test.ts`); Rust deserializes each as its launch plan, accepts it, and refuses each one-step change (`hls_master_urls_from_the_typescript_rebuild_pass_the_rust_rules`).
- `DynamicHlsController` is `[Authorize]` and reads the header token before any `ApiKey` query, and the server copies the master request's query string into variant and segment URLs, so no HLS URL carries the token (sources in decision 0002, Q1).
- Rust validates every playlist before mpv reads it (E1-B, approved by the user 2026-11-07; E1, trusting server playlists, was rejected because FFmpeg's HLS demuxer does not check the origin of playlist URIs, `hls.c` lines 867-905). Rust fetches the master and every variant with the header, no redirects, no proxy, no cookies, an 8 MiB limit, and a 20 s timeout (`ureq` on rustls/ring), resolves every URI line and every `URI=` attribute (stream, i-frame, media, map, key, session key, image), and refuses the whole launch unless each one is HTTP(S) on the server's origin with no user info, no fragment, and no credential parameter. A body that names a credential parameter anywhere, or contains the token value itself (any ASCII case, after up to three rounds of percent decoding), fails closed. A live playlist (no `EXT-X-ENDLIST`) and `EXT-X-DEFINE` are refused. The served copy keeps only the tags FFmpeg's `hls` demuxer acts on, with every URI absolute and canonical. Tests: `hls_session_refuses_cross_origin_uris_and_never_contacts_the_other_origin`, `hls_session_refuses_redirects_without_following_them`, `hls_session_fails_closed_on_credentials_status_and_size`, and the playlist, URI, and attribute tests in `player/hls/`.
- A launch with a cross-origin variant, segment, or map URI is refused before any mpv handle exists, with the refusal the UI shows as "Jellyfin offered a stream address Fluster won't use" (`unsafe-transcoding-url`), and the second origin receives nothing (`hls_launch_with_a_cross_origin_playlist_is_refused_and_contacts_nobody_else`). Rust's refusal text starts with "Fluster refused the converted stream:" and names no URL; the native engine turns it into the typed refusal and drops the text (`native-player.test.ts`). Network failures (fetch, HTTP status, an oversized playlist, loopback) are ordinary launch errors, not refusals. The signed-in server URL itself must pass the URL policy (`converted_launches_need_an_allowed_server_url`).
- mpv reads only Rust's validated copies, served from a loopback server on `127.0.0.1` with a random 128-bit per-session path. It answers only that session's exact paths, never logs requests, gives each connection a 2 s deadline for its request head, serves at most 16 connections at once (a local process holding 16 can deny a launch; accepted, no data is exposed), and closes when the session's media is dropped at the end of the session. mpv sends the header to it too, because `http-header-fields` applies to every open on the handle.
- `access-references` is on only for HLS handles, which also set `demuxer-lavf-o=protocol_whitelist=[http,https,tcp,tls]`; static handles keep references off and set no whitelist (`static_launches_keep_access_references_off`). mpv loads the loopback master only with per-file `demuxer=lavf,demuxer-lavf-format=hls`, so a failed `hls` open never falls back to mpv's playlist demuxer, which would play each server segment as a top-level file with references on (`hls_failed_hls_open_never_falls_back_to_playlist_entries`). FFmpeg's segment demuxers may not open anything (`nested_io_open`, `hls.c` FFmpeg 9.0.2 lines 1898-1906). The per-file format is cleared after `FileLoaded`, before `sub-add`.
- mpv fetches segments and init sections directly from the server with the header; Rust does not proxy them. `max_redirects=0` and `http_proxy=direct://` reach the nested segment opens. On a full converted launch, Rust's master, variant, and subtitle requests and mpv's map and segment requests each carry exactly one `Authorization` line with the typed value, mpv never reads a server playlist or subtitle, `sub-add` reads only the loopback copy, and a segment the server redirects to another origin sends that origin nothing (`hls_launch_sends_the_header_on_every_request_and_never_follows_a_segment_redirect`; lower-level: `hls_nested_opens_send_exactly_the_typed_header`, `hls_segment_redirects_are_refused_on_nested_opens`, `hls_file_segments_are_refused_with_and_without_the_whitelist`). A refused segment redirect makes FFmpeg skip that segment, not fail the file.
- External subtitles on converted sessions are never `sub-add`ed from the server (approved by the user 2026-11-07): every subtitle track with a delivery URL (embedded text streams the server delivers as files included) is fetched by Rust with the header from the server's origin with no credential query (64 MiB limit), refused unless the body starts like WebVTT, ASS/SSA, SubRip, MicroDVD, SubViewer, or PGS and names no playlist, EDL, or reference format, and served from the same loopback server. A subtitle that cannot be fetched (network, HTTP status, or over its limit; at most 96 MiB of subtitles per session) is left out and the launch goes on without it (`hls_session_leaves_out_subtitles_it_cannot_fetch`); one that fails a safety check (wrong origin, credential, token echo, not a subtitle) fails the launch; TTML and SAMI are refused, so the DeviceProfile must not request them as external files. The PGS check passes any body that starts with `PG` on its magic alone.
- E2 (accepted by the user with a canary test, 2026-11-07): a server that ignores `EnableTrickplay=false` would put the token in a playlist body. `redaction_canary_in_a_playlist_body_fails_the_launch_closed` serves the token in a trickplay `ApiKey`, a variant `api_key`, a segment `X-Emby-Token`, bare in session data, percent-encoded in a segment path, and echoed in a subtitle: each launch fails closed before any mpv handle exists and mpv never reaches the server, and the token is absent from the returned error and its `Debug` and redacted forms. Player events and diagnostics come only from a session's event loop, which needs an mpv handle, so a launch that fails here produces none. The converted path has no print or trace call (`redaction_canary_the_converted_path_never_prints`), Fluster installs no logger (`logger_guard`), and Fluster does not request libmpv log messages; the UI shows only the fixed refusal copy.
- Live (P10-04 acceptance 7): a Transcode plan built by the gateway for the ISO sample (forced fallback) on Jellyfin 10.11.7 and 12.4.0 reaches `playback-restart` in headless libmpv through Rust-validated playlists with header auth only (`live_fixture_transcode_plan_reaches_playback_restart`). The BluRay folder sample did not: both servers serve its variant as `live.m3u8` and answer it with HTTP 500 (server FFmpeg exit 183); a live playlist would be refused anyway (P10-09, P10-12).
- Track switching on a converted session stays local and maps only what the conversion carries: the one audio track (to the master URL's `AudioStreamIndex`) and the loopback subtitles (by add order). Changing to a track the conversion lacks is P10-08.
- `DELETE /Videos/ActiveEncodings` carries `deviceId` and `playSessionId` in its query, like the static stream URL carries `PlaySessionId`. Neither is a credential; both stay out of logs, errors, and diagnostics (I4).
- The streaming limit is a non-secret preference and may be stored in WebView storage.
- Untested: the AppImage's bundled FFmpeg, macOS libmpv, and other FFmpeg builds must pass the same loopback tests before release; `max_redirects` does not exist in FFmpeg 7.0.

No player preferences are persisted in this slice. Authentication secrets must not be added to persisted Query caches, analytics, crash payloads, or diagnostic exports.

In-process rendering intentionally trades fault isolation for integrated presentation. A native libmpv or graphics-driver crash can terminate the application; normal playback errors and end-of-file events are recovered in the player lifecycle.
