## Goal

Back returns to a browse screen exactly as it was left: same data with no skeleton, same sort and filters, every page that was loaded, the same scroll position, and the same focused card. To do that, Home, library, collection, series, detail, and search-result queries stop being dropped on unmount (`gcTime: 0` today, `src/features/query-scope.ts:3-5`) and are instead kept for as long as their account is the active one; they are removed from the cache when the account changes, signs out, or the app closes. A library's (and a collection's) sort and filters move from component state into the route. Scroll position joins the in-memory, per-history-entry record that P13-24 already keeps for focus.

## Approach

### 1. Keep screen data while the account is active

- In `query-scope.ts` export `export const ACCOUNT_GC_TIME = Number.POSITIVE_INFINITY;` with a one-line comment: kept until `dropOtherAccounts` removes it.
- Replace `gcTime: 0` with `gcTime: ACCOUNT_GC_TIME` at exactly these sites (`a904886`): `home/home-data.ts:23,24,25,31`; `home/home-hero.tsx:16,25,33,41`; `home/home-empty.tsx:20`; `browse/library-grid.tsx:58`; `browse/browse-view.tsx:25`; `browse/collection-view.tsx:25`; `browse/series-view.tsx:39`; `browse/series-queries.ts:11,19,28`; `detail/item-detail-view.tsx:37`; `detail/episode-strip.tsx:30,38`; `search/search-results.tsx:40`.
- Leave every other `gcTime` as it is: the player (`player/index.tsx:64`, `use-server-name.ts`, `use-media-segments.ts`, `use-auto-play-next.ts`), settings, the nav views, and the 30 s detail prefetches. TanStack Query v5 (`^5.107.1`) keeps a query's `gcTime` at the largest value any observer set (`Query.updateGcTime` uses `Math.max`), so a detail viewed on its screen stays kept even though the player observes the same key with `gcTime: 0`.
- Every kept key already has the gateway scope at index 1 (`["home", scope, …]`, `["browse", scope, …]`, `detailKey` → `["detail", scope, …]`, `["search", scope, …]`); keep it that way. Add a sentence to the `query-scope.ts` comment: "Every account-scoped key puts `scopeFor(gateway)` at index 1."
- Nothing to change for "no skeleton": the views already render `isPending ? skeleton : content`, and a cached success is not pending.
- Library and search pages: the kept `useInfiniteQuery` holds every page; a stale remount refetches all loaded pages in order (v5 behaviour), showing the kept pages meanwhile.

### 2. Drop it when the account changes, signs out, or the app closes

- `query-scope.ts`:
  - `scopeOfKey(key: readonly unknown[]): number | undefined` returns `key[1]` when it is a number.
  - `dropOtherAccounts(queryClient: QueryClient, gateway: SessionGateway | undefined): void`: `const keep = gateway ? scopeFor(gateway) : undefined; const predicate = (query) => keep === undefined || scopeOfKey(query.queryKey) !== keep;` then `void queryClient.cancelQueries({ predicate })`, `queryClient.removeQueries({ predicate })`, and `queryClient.getMutationCache().clear()`. Removing every query outside the new scope (not only the old scope) also drops unscoped player queries and anything a future key forgets to scope, and never removes the new account's in-flight queries. Signed out (`undefined`) removes everything.
- `session.tsx`: add `onAccountChanged?: (gateway: SessionGateway | undefined) => void` to `SessionProvider`, held in a ref like `onServerDataChanged`. In a `useEffect` on `[gateway]`, compare with a `previous` ref; when the gateway changed and the previous one was defined (a sign-out or a replacement), call `onAccountChanged(gateway)`. Do not call it on the first sign-in after launch (nothing to drop) — calling it is harmless, but the test pins the stated behaviour. It runs after commit, so the old account's screens (which render nothing without a gateway, e.g. `LibraryPage`) have already unmounted and cannot rebuild the removed queries with the old gateway.
- `App.tsx`: `onAccountChanged={(next) => resetAccountData(queryClient, next)}` (memoised with `useCallback`). `resetFocusReturn` already exists (`focus-return.ts`) and also clears the new scroll record; today records clear only when the hash becomes `#/next/sign-in`, which a future account switcher (P3-20, P13-21) will not pass through.
- Close: `QueryClient` is created in memory in `main.tsx`; move its construction to `src/app/query-client.ts` (`createQueryClient()`, same options: `retry: 1, staleTime: 30_000`, mutations `retry: false`) so the restart test uses the real configuration. No persister is added.

### 4. Scroll position on a return

The page scrolls the window (`app-shell.tsx:36,56` read `window.scrollY`; no inner scroller).

- `focus-return.ts`:
  - At module init (beside the listeners), `if ("scrollRestoration" in history) history.scrollRestoration = "manual";` so the browser's own traversal restore does not fight ours.
  - `const scrolls = new Map<string, number>()`, capped by `capSet` like `records` and `slots`; cleared in `resetFocusReturn` and in `onHashChange`'s sign-in branch.
  - A passive `window` `scroll` listener, throttled to one `requestAnimationFrame`, stores `Math.round(window.scrollY)` under `currentEntryId()`; also store it in `remember()` (focusin/click), so activating a card records the place even without a scroll event. While a return is pending, ignore scroll events (the destination's layout is still settling).
  - `PendingReturn.record` becomes optional and gains `scrollY?: number`. `onPopState`: start a pending return when the target entry has a focus record **or** a scroll record (and the hash changed, as today). A scroll-only return restores the scroll and lets the screen's opening focus proceed through `finishReturn`'s deferred element.
  - `tryRestoreScroll()`: once per pending return, when `document.documentElement.scrollHeight - window.innerHeight >= pending.scrollY` (the page is tall enough), `window.scrollTo({ top: pending.scrollY, behavior: "instant" })` and mark it done.
  - `tryRestore()`: the card is **not focused, and so the return does not end, until the scroll has been applied** (`tryRestoreScroll()` returns false while the page is shorter than the recorded position). Otherwise a card that renders before the page reaches its recorded height would end the return and lose the scroll. Once the scroll is applied, focus with `target.focus({ preventScroll: true })`, then if the target's rect is outside the viewport call `target.scrollIntoView({ block: "nearest", inline: "nearest" })` (horizontal rows need the inline part; `block: "nearest"` leaves a visible card's vertical position alone). `finishReturn()` (the screen settled, or the wait ran out): apply the scroll clamped to the page height if not yet done, then focus the fallback the same way.
  - Add `wheel` and `touchstart` to the "user has taken over" listeners that clear the pending return.
  - Fresh visits never restore (DESIGN.md §9 line 543): only `popstate` to a stamped entry starts a return, unchanged.
- `use-focus-return.ts`: call `tryRestoreScroll()` at the top of `check()`, so the scroll lands as soon as kept data renders, not after background refetches settle.
- `routes.ts` `replaceRoute` changes the URL of the current entry; `focus-return.ts` listens for `ROUTE_REPLACED_EVENT` and sets `lastHash = window.location.hash`, so a later traversal compares against the replaced URL.

### 5. Background refresh

- `query-scope.ts` `markAccountDataStale(queryClient)`: `void queryClient.invalidateQueries({ predicate: (q) => ["browse", "detail", "search"].includes(String(q.queryKey[0])), refetchType: "none" })`. Kept queries become stale without a request; the next mount refetches in the background while showing kept data.
- `App.tsx` `refreshRows`: `refreshHomeRows(queryClient)` (unchanged, P3-15) then `markAccountDataStale(queryClient)`.
- `use-flag-mutation.ts` `onSettled`: add `markAccountDataStale(queryClient)` beside `refreshHomeRows`, so a card's watched or favourite mark is fresh on Back. (The detail key it invalidates is under `"detail"` too; that refetch stays as it is.)
- Global `staleTime: 30_000` is kept: a return after 30 s always refetches in the background.

## Risks and out of scope

- **Memory growth.** `gcTime: Infinity` keeps every visited screen for the account's session; one library page is 60 cards. Acceptable for a desktop session; if dogfood shows growth, a later task can cap it. Append to `tasks/backlog.md`: "Cap kept browse data per account if memory grows (P13-31)".
- **Stale data briefly visible.** A return within 30 s of the last fetch shows kept data without a refetch, except after a server event or a flag change (Approach 5). A playback ended on the native player updates the server; the realtime `UserDataChanged` event then marks data stale.
- **Infinite refetch cost.** A stale return to a library with three pages refetches three pages in order. Acceptable; not changed.
- **"Reload" in acceptance item 4.** Sign-in is held only in memory until P3-02/P3-19, and `LibraryPage` sends a signed-out visitor to sign-in, so a real reload loses the route. The spec proves "a reload restores them" as "opening the URL fresh restores them" (unit test on App plus e2e 3). Returning to the pre-sign-in route after sign-in is out of scope; append to `tasks/backlog.md`: "After sign-in, return to the route that sent the visitor to sign-in (P13-31)".
- **Collections.** The task names "a library's sort and filters". Collections share `LibraryGrid`, so they get the same route parameters for consistency (one controlled grid, no second state path). Decided here; no product choice is involved.
- **Ordering of removal.** Removing queries before the old screens unmount would let a mounted observer rebuild a query with the old gateway. The effect-after-commit order in Approach 2 avoids it; the switch test covers it.
- **Kept default-sort pages on a fresh visit.** Because infinite queries are kept, a fresh nav-bar visit to a library shows every default-sort page loaded earlier, at the top, and the card focus and scroll do not restore. The design review (acceptance 12) should confirm this fits DESIGN.md §9 "A fresh visit never restores"; the question is logged in `tasks/backlog.md`.
- **Remembering sort and filters between visits** (`tasks/backlog.md:40`) stays out of scope; a fresh nav click still opens the default (DESIGN.md §9 "A fresh visit never restores").
- **Search hints, nav views, the player, settings** keep `gcTime: 0`.
- Out of scope: P3-20/P13-21 account switcher UI (this task only provides the hook it will use), disk persistence (D1 C, rejected), P2-10 route consolidation (waits for this task).

## Decisions taken in this spec

1. Kept data uses `gcTime: Infinity`, not a finite time: a film-length visit to the player must not drop the library behind it (D1 B: kept while the account is active).
2. Account change removes every query outside the new account's scope, after commit, through a `SessionProvider` callback; focus-return records and scroll records are cleared at the same time.
3. Sort and filters are written with `history.replaceState` (no new history entry per sort change) plus an app event, not `location.replace` (which would drop P13-24's entry stamp and remount the grid).
4. Default sort and empty filters are omitted from the URL, so the bare library URL still means defaults and existing journeys keep their URLs.
5. Collections carry sort and filters in the route too.
6. Scroll is restored for any return to a stamped entry, including one with no focused card, because DESIGN.md §9 says Back restores the scroll position without condition.
7. Browse, detail, and search data is marked stale (not refetched) on server events and flag changes; Home rows keep P3-15's active refetch.

## Implementation notes (decisions and deviations found while building)

1. Per-view "no skeleton on return" tests live in `src/app/account-data.test.tsx` (one shared harness: unmount, wait, remount with the same client and a gateway whose later requests never answer), not in each view's test file, because they need the account and cache plumbing. They cover Home, a library, search results, an item's detail, and a series. A mutation check (library `gcTime: 0`) fails the library case.
2. `App.test.tsx` cannot sign in with real services, so "a route replace does not remount" is covered by the Library e2e journeys (the Sort trigger keeps focus, the URL changes without a new entry) and `browse-view.test.tsx` (the controlled grid follows the hash). `App.test.tsx` covers that library and collection routes with a view query are screens.
3. `App` keeps `{ hash, visit }`. `hashchange` raises `visit` only when the hash differs from the rendered one: Chromium can deliver a push's `hashchange` after a quick Escape, which would otherwise remount the restored screen and drop the restored card.
4. `focus-return.ts` moves `lastHash` on every `popstate` (not only on `hashchange`), for the same late-`hashchange` reason.
5. `remember()` records the scroll position only together with a card record, and a non-card focus in `main` forgets both, so "forgets the record when a non-card in main takes focus" keeps its meaning. A scroll-only return exists for entries that were scrolled (by scroll events) with no card record.
6. Restored cards can leave in the background refetch of stale kept data. `tryRestore` records the card as "settling"; when the screen has settled (no fetches, two quiet frames) and focus fell to the page, `settleFocus` focuses the same place in the row. User input ends it. This keeps "Fallback: a card that is gone ..." passing; that journey now marks the item watched first (the flag mutation marks kept Home rows stale, so they refetch on the way back, since kept fresh data is shown without a refetch for 30 s).
7. Mock server: `liveDelay: { libraryMs, rowsMs }` is set by a test while it runs, to prove a screen shown again does not wait for the server.
8. No plan file was made: the work was one session and one domain.
