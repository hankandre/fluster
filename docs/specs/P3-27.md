## Goal

When Home's hero shows a series (today only when Continue watching and Next up are empty and the first non-empty Latest row starts with a series), its primary button resolves "the first episode of the first regular season" with its own lookup (`src/features/home/home-hero.tsx:19-35`) and always plays it from the start (`hero-facts.ts:37-41`). The series page instead asks the server for the next episode (`seriesNextUp`), resumes it when it has a saved position, and only falls back to the first episode of the season that would open (`src/features/browse/series-body.tsx:27-47`). The two disagree for any series the viewer has started. This task makes the hero use the series page's exact rule, so both offer the same episode with the same words, and Resume continues from the saved position.

The settled decision P13 Q4 A (`docs/specs/decisions-P13.md:35`) already allows this: "a series hero's primary button is 'Play S1 · E1' (or its Next Up)". The proposal that added the task calls it a defect with no design choice (`docs/plans/proposals/discovery-and-profiles.md:203`, `:428`, `:442-452`).

## Approach

### 1. One shared rule (`series-next.ts`)

Lift the decision the series header makes today (`series-body.tsx:30-47`) into a pure function, so the hero cannot drift from it.

```ts
export interface Loaded<T> { status: "pending" | "error" | "success"; data?: T }

// "S1 · E2", or undefined without both numbers. The label and the hero's facts token both use it.
export function episodeNumbering(season: number | undefined, episode: number | undefined): string | undefined;

// The season whose first episode is offered when the server has no next episode.
export function fallbackSeasonOf(seasons: Season[] | undefined): Season | undefined {
  return seasons ? initialSeason(orderSeasons(seasons), undefined) : undefined;
}

export interface SeriesPrimaryState { pending: boolean; primary?: SeriesPrimary }

export function seriesPrimaryState(
  nextUp: Loaded<SeriesNextUp | null>,
  seasons: Loaded<Season[]>,
  fallback: Loaded<EpisodeCard[]>,
): SeriesPrimaryState;
```

Semantics, identical to today's `series-body.tsx`:

- `nextUp.status === "pending"`: `{ pending: true }`.
- `"error"`: `{ pending: false }` (no action; the series page shows its existing "Couldn't load your next episode." notice, the hero shows only More info, as when its lookup fails today).
- success with an episode: `{ pending: false, primary: seriesPrimary(nextUp.data, undefined) }`.
- success with `null`: `fallbackSeason = fallbackSeasonOf(seasons.data)`; `pending = seasons.status === "pending" || (fallbackSeason !== undefined && fallback.status === "pending")`; `primary = seriesPrimary(undefined, fallback.data?.[0], fallbackSeason)`.

`labelled()` is rewritten on top of `episodeNumbering()` (same output). `SeriesPrimary` gains `numbering?: string`, set in both branches of `seriesPrimary` from the same numbers as the label (`nextUp.seasonNumber/episodeNumber`, or `fallback.seasonNumber ?? fallbackSeason?.indexNumber` and `fallback.episodeNumber`). The series page ignores `numbering`.

React Query's `status` values are exactly `"pending" | "error" | "success"`, so callers pass `{ status: query.status, data: query.data }`. A disabled query reports `"pending"`; that matches today, because the fallback branch is only reached once its query is enabled (or `fallbackSeason` is undefined, which short-circuits).

### 2. The hero's queries (`home-hero.tsx`)

For `card.kind === "Series"` only (all queries `enabled: isSeries && ...`, `gcTime: 0`, `retry: false` as today):

- `["home", scope, "hero-next-up", card.id]`: `async ({ signal }) => (await gateway.seriesNextUp(card.id, signal)) ?? null`.
- `["home", scope, "hero-seasons", card.id]`: `gateway.seasons`, enabled only when Next Up succeeded with `null`.
- `["home", scope, "hero-episodes", card.id, fallbackSeason?.id ?? ""]`: `gateway.episodes(card.id, fallbackSeason.id)`, enabled when Next Up is `null` and `fallbackSeason` is defined.

Keys stay under `"home"` so `refreshHomeRows` (`home-queries.ts`) refetches them after playback progress or a watched toggle, as it does the current `hero-episode` key. They do not share the series page's `["browse", ...]` cache; sharing would skip that refresh, and with `gcTime: 0` it would not save a request anyway.

Then:

- `const series = isSeries ? seriesPrimaryState(...) : undefined;`
- `primary` for the `Hero`: for a series, from `series.primary` with `progress: series.primary.progress` when present; otherwise `primaryAction(card)` with the existing card-progress rule.
- `primaryPending = isSeries && series.pending`.
- `facts = heroFacts(card, detail.data, series?.primary?.numbering)`.

Remove the `HeroEpisode` import and the old `hero-episode` query. Update the file's header comment ("a series resolves the episode its series page would offer").

- `heroFacts(card, detail?, seriesEpisode?)`: for `Series`, `parts.push(seriesEpisode, detail?.year?.toString(), ...genres.slice(0, 2))`. Default per Open question 1, option A. With no token (pending, error, no numbers) the line is as today.
