## Goal

1. One function, exported from the core and free of test-runner and Node imports, runs both shared URL files against the host's own `URL` and `URLSearchParams` and returns a per-vector report. Node runs it in Vitest now; the app runs the same function under Hermes in T3-02.
2. A plain-HTTP server address is admitted as loopback or private LAN only when its host is written in plain ASCII with no `%`, and its parsed host is plain ASCII with no `xn--` label. Everything else is public. The verdict for such an address is the same whether the host's URL parser throws, converts the name to punycode, maps it to ASCII, or passes it through.
3. An HLS master URL whose host is not written in plain ASCII is refused, even when a WHATWG parser would map it onto the server's origin.
4. The rules are written without reference to a parser, so the Kotlin classifier (T3-03) and the Kotlin master-URL check (T8-08) can mirror them from the same vectors.

## The rules

Written so that any language can mirror them from the vectors. "Plain ASCII authority" is a test on the string as written, before any parser sees it.

**R1. Plain ASCII authority.** A string has one when, after trimming leading and trailing whitespace (JavaScript's `trim()`; no vector has leading or trailing whitespace, so a port may trim a narrower set or none and still agree on every vector), it matches this pattern, with no case-insensitive flag and no Unicode flag:

```text
^[Hh][Tt][Tt][Pp][Ss]?://(?:[A-Za-z0-9._-]+|\[[0-9A-Fa-f:.]+\])(?::[0-9]*)?(?:[/?#]|$)
```

That is: `http://` or `https://`, then a host of ASCII letters, digits, `.`, `_` and `-` or a bracketed IPv6 literal, then an optional port, then `/`, `?`, `#` or the end. It refuses a non-ASCII character, `%`, user info, a backslash, a tab or newline inside the authority, and the `http:host` and `http:/host` spellings. It is a gate that can only refuse; the parsed host is still what gets classified (decision 0001, edge case 2).

**R2. Plain ASCII parsed host.** A parsed hostname is plain when it is a bracketed IPv6 literal, or every character is one of `A-Z a-z 0-9 . _ -`. A hostname that is not plain is `public`. A name with a label that starts with `xn--` in any ASCII case is `public`.

**R3. Server address class.** `classifyServerAddress(address)`:
1. not R1 → `public`;
2. the host's `URL` cannot parse it → `public`;
3. otherwise `classifyHost(parsed)`, which applies R2 first and then today's rules.

The gateway uses this class for the plain-HTTP refusal and for `hostClass`. HTTPS still connects to every host (decision 0001); an HTTPS address that fails R1 or R2 simply reports `public`.

**R4. HLS master URL host.** `rebuildMasterUrl` refuses with detail `host` when:
- `context.serverUrl` fails R1. This is the function's first step, before `new URL(context.serverUrl)` (`hls-url.ts:59`, which sits outside any `try` today), so a parser that throws on such a server URL cannot turn the refusal into a throw; or
- the trimmed `TranscodingUrl` is absolute (it does not start with a single `/`) and fails R1; or
- the parsed hostname of the resolved URL or of the server URL fails R2's plain-host test.

An `xn--` label in an HTTPS host that passes R1 is not refused here: decision 0001 admits every host over HTTPS, and item 3 names non-ASCII hosts only. The server-URL check runs first; every existing test passes an ASCII server URL, so none changes. The other two run after the existing `unparsable`, `scheme` and `user info` refusals and before `other origin`, so every existing refusal detail in `hls-url.test.ts` stays as it is. On a host whose parser throws for an absolute URL that fails R1, the existing `unparsable` refusal answers instead of `host`; the shared vectors record only the verdict, so they pass either way.

### The suite

```ts
export interface UrlConformanceFailure {
  file: "host-classes" | "hls-master-urls";
  // The vector's `url` (host classes) or `name` (HLS). Fixture text only.
  vector: string;
  expected: string;
  // A class, "accepted", "refused", "rebuilt differently" or "threw". Never an error message.
  actual: string;
}

export interface UrlConformanceReport {
  total: number;
  passed: number;
  failures: UrlConformanceFailure[];
}

export function runUrlConformance(): UrlConformanceReport;
```

Checks, one per vector, each inside its own `try`:

- `host-classes.json` `vectors`: `classifyServerAddress(url) === class`.
- `hls-master-urls.json` `vectors`: `rebuildMasterUrl(plan.streamUrl, …the plan's own serverUrl, itemId, mediaSourceId, mediaKind, playSessionId)` is `ok` with `url === plan.streamUrl`.
- `hls-master-urls.json` `refusals`: `verdict: "refuse"` → not `ok`; `verdict: "rebuild"` → `ok` with `url` equal to the recorded one. This is the check `hls-url.test.ts:184-198` makes.

The JSON is cast through `unknown` to small local interfaces, as `hls-url.test.ts:179` does. A non-test JSON import under `packages/core/tsconfig.json` (`resolveJsonModule: true`) is expected to type-check but is **unverified**; `pnpm typecheck` in milestone 2 settles it.

### Decision log

- **D1. The suite takes no URL argument.** The core reads `URL` as a host global (`host-globals.d.ts`), so the implementation under test is whatever the host installed. A parameter would test something the core does not use, and a URL port would be an architecture change no task asks for. T3-02's "URL … through the ports" is that task's wording to resolve.
- **D2. The written address is checked, and decision 0001 edge case 2 still holds.** That rule says "classify the parsed host, not the typed string". R3 still classifies the parsed host; R1 only adds a precondition that can turn a verdict into `public`, never the reverse. The acceptance text requires it: Node maps `ｎａｓ.local` to `nas.local` before any classifier runs. The decision record is not edited; `docs/security.md` §3 states the rule, and the PR calls this out as a change to how I5 is enforced.
- **D3. `%` in the written host fails closed.** Node decodes `%6eas.local` to `nas.local`, and `%EF%BD%8E` would carry a fullwidth letter past both a non-ASCII scan of the text and an ASCII check of the result.
- **D4. No host extractor.** R1 is an anchored pattern over a fixed shape, not a parser that finds the authority in an arbitrary URL. A string in another shape is refused, so a disagreement with the real parser can only refuse.
- **D5. Spelled-out classes, no `i`, no `u`.** Probed: `/iu` lets U+017F and U+212A through. Two vectors pin it.
- **D6. HTTPS to an internationalized name is unchanged.** Item 2 is scoped to plain HTTP and decision 0001 admits HTTPS for every host. On a host whose parser punycodes, the normalized server URL is ASCII and conversions work; on one that does not, R4 refuses them (fails closed).
- **D7. R2 narrows the admitted ASCII set.** A plain-HTTP name with `~`, `!`, `$`, `&`, `'`, `(`, `)`, `*`, `+`, `,`, `;` or `=` (which WHATWG allows in a host) becomes `public`. No vector or recorded fixture has one; DNS and mDNS names use letters, digits, `-` and sometimes `_`.
- **D8. New module under `src/conformance/`.** It must import `jellyfin/hls-url.ts` and the fixtures, which `domain-is-pure` forbids under `domain/`.
- **D9. The test writer adds the vectors and freezes both JSON files**, as T2-04 froze its fixtures. The three existing readers go red with the new vectors until milestone 1; they are not frozen and the implementer updates them as listed.
- **D10. No vector asserts what a parser outputs for an internationalized name.** Each new vector's verdict is fixed by R1 before parsing, or by R2 whatever the parser returns, so T3-02 can pass under any URL implementation that gets the existing ASCII vectors right.
