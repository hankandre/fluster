## Goal

The libmpv engine already knows what it is decoding and how far ahead it has buffered, but the frontend sees only decoder diagnostics. This task adds typed video and audio facts and a buffered position to `PlaybackSnapshot`. It uses only observed libmpv properties and adds no command. The Info sheet then gets Video and Audio sections (values in Mono, redacted like every other engine value), and the scrubber draws the buffered range. DESIGN.md §7.14 marks both as deferred today (lines 292 and 299). This task ships them and updates those two sentences.

## Invariants and hard rules this task touches

- **Never add a generic mpv command, property, or option bridge.** Each new property is named in Rust's fixed `observe_properties` list or read by a named Rust function. Its value is mapped into a typed field. No property name or raw mpv node crosses to TypeScript.
- **Treat every new Tauri command as an architecture change.** No command is added. `ALLOWED_COMMANDS` in `src-tauri/src/command_allowlist.rs` and its test do not change. The new data rides the existing `fluster://player-event` snapshots (`Loaded`, `State`, `TracksChanged`, `Ended`).
- **Never log, persist, or display tokens, passwords, authenticated URLs, or play-session IDs.** The new fields come from libmpv runtime properties, never from plan fields. Every new string goes through the Info sheet's `plain()` (redaction plus URL hiding) before display. The Rust redaction canary and the TS redaction test both cover the new fields.
- **Show every server conversion and its reason in the player.** Unchanged. The Playback section stays first, and the chip, OSD, and loading text are untouched (Q15 C, Q16 A).
- **Keep `src/domain/` free of React, SDK, Tauri, and HTTP imports.** The new TS types go in `src/domain/playback.ts` as plain types.
- **Keep player commands typed and narrow** and **keep native surface and mpv work serial.** Milestone 1 is native and runs alone.
- **Never use the browser player as a fallback for the native player.** The browser engine only fills what an HTML video element can honestly report (buffered end). It never fakes codec facts.
- **Design:** values in Mono (§4), tokens only (no hard-coded colour), no `--text-3` over video (§3.1), arrows/Enter/Escape alone, reduced motion, the TV 22 px floor (§6/§8), and the title-safe insets.
- **Tests:** never skip, weaken, or delete a test. All e2e changes only add assertions.

## Approach

### 1. Snapshot shape (Rust, `model.rs`)

```rust
#[derive(Debug, Clone, Copy, Default, PartialEq, Serialize)]
#[serde(rename_all = "kebab-case")]
pub enum VideoRange { #[default] Unknown, Sdr, Pq, Hlg, DolbyVision }

#[derive(Debug, Clone, Default, PartialEq, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct VideoFacts {
    #[serde(skip_serializing_if = "Option::is_none")] pub codec: Option<String>,              // short name, e.g. "hevc"
    pub range: VideoRange,
    #[serde(skip_serializing_if = "Option::is_none")] pub dolby_vision_profile: Option<u64>,
}

#[derive(Debug, Clone, Default, PartialEq, Serialize)]
#[serde(rename_all = "camelCase")]
pub struct AudioFacts {
    #[serde(skip_serializing_if = "Option::is_none")] pub codec: Option<String>,              // short name, e.g. "truehd"
    #[serde(skip_serializing_if = "Option::is_none")] pub channel_count: Option<u64>,        // decoded source
    #[serde(skip_serializing_if = "Option::is_none")] pub sample_rate: Option<u64>,
    #[serde(skip_serializing_if = "Option::is_none")] pub output_format: Option<String>,     // audio-out-params/format, e.g. "floatp" or "spdif-eac3"
    #[serde(skip_serializing_if = "Option::is_none")] pub output_channel_count: Option<u64>,
}
```

`PlaybackSnapshot` gains `pub video: VideoFacts`, `pub audio: AudioFacts`, and `#[serde(skip_serializing_if = "Option::is_none")] pub buffered_seconds: Option<f64>`. `Default` sets them to default and `None`.

Decisions settled here:

- **Resolution is not duplicated.** `diagnostics.width`, `height`, and `bit_depth` are already typed snapshot fields fed by `width`, `height`, and `video-params/bit-depth` (`properties.rs:20-22, 181-201`). The Info sheet reads them. Moving them into `VideoFacts` would change `last-decode.test.ts:27`, whose purpose is to prove that extra diagnostic fields do not leak, so they stay. The redundancy of `diagnostics.video_codec` (the long description) and the new short `video.codec` is logged to the backlog, not fixed here.
- **"Output format" means the audio output:** the sample format and channel count written to the audio device (`audio-out-params`). That is the one fact that differs from the source (downmix, resample, and later passthrough in P5-03). The video output (VO, GPU context, hwdec interop) is already shown in Decoder and Renderer.
- **"Range" is what the engine reports for the picture**, not the server's metadata. A Dolby Vision profile on the track reports the track's signalling, not proof that mpv rendered the enhancement layer (it may show only the PQ base layer of profile 8), so the DV row is the container's claim and the other rows are the engine's. `video-params/gamma` gives `pq` (PQ HDR), `hlg`, or an SDR curve (`bt.1886`, `srgb`, `gamma2.2`, ...; `--target-trc` lists the names). The Dolby Vision profile on the selected video track (`current-tracks/video/dolby-vision-profile`) wins over gamma. libmpv cannot tell HDR10 from HDR10+ by gamma, so the engine reports `Pq`, not `Hdr10`.
- **New `Option` fields skip serialization when `None`,** so the TS types can stay optional (`?:`) and be truthful. Existing fields keep their current behaviour.

### 2. Where each value comes from (Rust)

Append to `observe_properties` (`properties.rs:9-32`), keeping the order of the existing ids:

| Property | Format | Field |
|---|---|---|
| `video-params/gamma` | String | `RuntimeState.gamma`, which recomputes `video.range` |
| `audio-params/channel-count` | Int64 | `audio.channel_count` |
| `audio-params/samplerate` | Int64 | `audio.sample_rate` |
| `audio-out-params/format` | String | `audio.output_format` |
| `audio-out-params/channel-count` | Int64 | `audio.output_channel_count` |
| `demuxer-cache-time` | Double | `buffered_seconds` |

Read (not observed) by `stream_facts::read_current_codecs(mpv, &mut snapshot) -> bool` (true when anything changed), using `string_property` and `get_property::<i64>`:

- `current-tracks/video/codec` → `video.codec`
- `current-tracks/video/dolby-vision-profile` → `video.dolby_vision_profile`, which recomputes `video.range`
- `current-tracks/audio/codec` → `audio.codec`

Reading on reconfiguration avoids relying on change notification for computed `current-tracks/...` paths. Whether mpv notifies observers of those paths is unverified. `events.rs` calls it once on `FileLoaded` (after `refresh_selected_streams`, before the `Loaded` emit) and at the top of the `AudioReconfig | VideoReconfig` arm, before the existing `TracksChanged` emit, so that emit carries the new codec. If it returns true and no `TracksChanged` was emitted, set `pending_state = true`. It takes the `RuntimeState` (not just the snapshot) because the range is recomputed from the stored gamma. A track switch (`aid`) causes `AudioReconfig`, so the codec follows the selection.

`apply_stream_property(state, name, data) -> Option<PropertyUpdate>` follows the style of the existing arms. It returns `None` when the value is unchanged, and returns `Some(PropertyUpdate::Ordinary)` otherwise. All of these updates are coalesced at 5 per second (`STATE_EVENT_INTERVAL`). None of them is `Immediate`. Negative `Int64` values become `None` through `u64::try_from(...).ok()`, as `width` does. A non-finite or negative `demuxer-cache-time` becomes `None`. `apply_property`'s `_` arm calls `apply_stream_property` instead of returning `None`. Because the stream arms return early, `dropped_frames` is not recomputed on them. That is correct, since they do not touch the drop counters.

Range derivation (pure, tested):

```rust
pub(super) fn video_range(gamma: Option<&str>, dolby_vision_profile: Option<u64>) -> VideoRange
// DV profile present → DolbyVision; "pq" → Pq; "hlg" → Hlg; a known SDR curve (bt.1886, srgb, linear, gamma*, prophoto, st428) → Sdr; anything else or None → Unknown.
```

`buffered_seconds` is mpv's estimate of the last buffered timestamp (manual: "returns the last timestamp of buffered data in demuxer"). Whether it is on the same timeline as `time-pos` (for direct play and for the validated HLS conversion) is unverified: the manual does not say. The native real-video check below covers it. The frontend draws it only when it is ahead of the position.

### 3. TypeScript types (`src/domain/playback.ts`)

```ts
export type VideoRange = "unknown" | "sdr" | "pq" | "hlg" | "dolby-vision";
export interface VideoFacts { codec?: string; range: VideoRange; dolbyVisionProfile?: number }
```

These fields are optional, so the browser engine, the e2e engine, and existing fixtures compile unchanged. The reducer (`session-state.ts`) keeps the whole snapshot already. No reducer change is needed.

### 4. Labels (`src/features/player/chrome/stream-facts.ts`)

These are pure functions. They reuse `codecName` and `channelLabel` from `src/features/detail/format.ts`, following the precedent `src/features/player/index.tsx:9` imports from `../detail/`. Each returns `string | undefined`, and the sheet shows `Unknown` for `undefined`. The copy below is the recommended answer to open question 2. Build it only once the human confirms.

- `videoCodecLabel(video)`: `codecName(video?.codec)`, for example "HEVC".
- `resolutionLabel(diagnostics)`: `${width}×${height}` (the Detail `videoLabel` form, U+00D7), or `undefined` if either value is missing.
- `rangeLabel(video, bitDepth)`: `sdr` → "SDR"; `pq` → "HDR (PQ)"; `hlg` → "HDR (HLG)"; `dolby-vision` → "Dolby Vision" or "Dolby Vision, profile 8"; `unknown` → `undefined`. When `bitDepth` is set, " · 10-bit" is appended.
- `audioCodecLabel(audio)`: `codecName(audio?.codec)`, for example "TrueHD".
- `channelsLabel(audio)`: `channelLabel(channelCount)` plus " · 48 kHz" when `sampleRate` is set (`sampleRate / 1000`, at most one decimal place, so 44.1 kHz shows as "44.1 kHz").
- `audioOutputLabel(audio)`: an `outputFormat` that starts with `spdif-` → `Passthrough (${codecName(rest)})`; any other format → `PCM, ${channelLabel(outputChannelCount)}` (or "PCM" without a count); absent → `undefined`.

### 5. Info sheet (`info-sheet.tsx`)

The section order is Playback, **Video**, **Audio**, Decoder, Renderer (pending open question 2). Each new section is `<section className="player-sheet-section"><h3>Video</h3><dl>…</dl></section>` with these rows:

- Video: `Codec`, `Resolution`, `Range`.
- Audio: `Codec`, `Channels`, `Output`.

With no snapshot yet, every row reads "Not playing yet", matching `decodeLine`. With a snapshot, a missing value reads "Unknown". Every value goes through `plain()`. The helpers return plain strings, so `plain()` is the single choke point. The sections hold no focusable element and need no new CSS, because the existing `dt` and `dd` rules apply. If `info-sheet.tsx` nears 400 lines, the two sections move into an `info-sheet-streams.tsx` part. The expected size is about 175 lines.

### 6. TV form and overflow

## Risks and out of scope

Risks:

- **Property names and values.** The manual marks the `video-params/gamma` values "subject to change". `pq` is confirmed by the local 0.41 manual's `--target-trc` list. The exact string mpv reports for HLG (expected `hlg`) is unverified until the HDR or HLG sample plays. Only an explicit list of SDR curve names maps to `Sdr`. Any other value maps to `Unknown`, so the sheet never claims SDR for a curve it does not know.
- **Observing `current-tracks/...`.** This is avoided by reading on reconfig. A codec change without a reconfig event (unlikely) would be missed until the next one.
- **`demuxer-cache-time` churn.** It changes often, but updates are coalesced at 5 per second like `time-pos`. MPRIS `publish` already runs on every coalesced update. No new cost class.
- **Buffered estimate accuracy.** The manual calls cache ranges approximate, and after a backward seek the value can briefly sit behind the position. The bar hides in that case.
- **TV overflow** of the Info sheet: see Approach §6.
- **Dolby Vision is signalling, not rendering.** `Range` shows "Dolby Vision" whenever the track carries a profile, even if mpv renders only the PQ base layer. The sheet cannot say which. Backlog: show the gamma next to it if the human asks.
- **Unavailable properties keep stale values.** libmpv2 5.0.3 drops `PropertyChange` events with `MPV_FORMAT_NONE` (`libmpv2-5.0.3/src/mpv/events.rs:267-270`), so audio facts and `demuxer-cache-time` keep their last value when a property becomes unavailable. Logged to `tasks/backlog.md`.
- **Duplicate codec fields** (`diagnostics.videoCodec` long description vs `video.codec` short name): logged, not fixed.

Out of scope:

- Track-row labels with codec and channels (P13-29).
- The "Buffering…" delay and `--text-3` over video (P13-33).
- Audio passthrough (P5-03). This task only reports a `spdif-*` output format if mpv already uses one.
- A "seeking" status (logged by P13-13 and still unowned). Add it to `tasks/backlog.md` if it is not there.
- HDR metadata (max-cll and similar), dropped frames in the sheet, and bitrate.
- Removing `diagnostics.width`, `height`, `bit_depth`, and `video_codec` duplication (backlog).
- Copy diagnostics in Settings (fixed seven lines, unchanged).
