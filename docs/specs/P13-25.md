## Goal

Turn the P13-01 screenshot harness (`pnpm test:visual`) into a required visual-regression check. Every capture is compared against a committed baseline PNG. A pull request whose UI changes any capture fails CI until the same pull request commits the new baseline. The many UI tasks queued after this one (P13-20, P13-17, P13-18, and the rest) are then protected against unintended visual change.

## Approach

1. **One capture, two uses.** In `screens.spec.ts`, replace `page.screenshot({ path, ... })` with `const image = await page.screenshot({ fullPage, animations: "disabled", caret: "hide", scale: "css" })`. Write `image` to the existing `visual-captures/<size>/<name>.png` path, so the contact sheet, `build-visual-index.mjs`, and PR attachments keep working. Then, when compare mode is on, run `expect(image).toMatchSnapshot([size, \`${scenario.name}.png\`])`. A single screenshot means the gated image and the artifact image are byte-identical, which is what makes the accept script correct. `scale: "css"` is already Playwright's default for desktop devices, but stating it pins the size.

2. **Compare mode.** Set `const compare = Boolean(process.env.CI) || process.env.FLUSTER_VISUAL_COMPARE === "1"` in both the config and the spec. CI always compares. A local `pnpm test:visual` stays capture-only by default, because baselines are rendered on the CI host (`ubuntu-22.04` with Playwright's bundled Chromium 1.64.1). A developer's machine (Arch here) may rasterise glyphs and gradients a little differently. Without this split, every local run would fail on host noise and `pnpm test:visual` in this task's own `verify` line would go red without a real regression. `FLUSTER_VISUAL_COMPARE=1` lets a developer compare locally on purpose. This narrows nothing that CI enforces.

3. **Config.** Add `snapshotPathTemplate: "{testDir}/baselines/{arg}{ext}"`, so the baselines mirror `visual-captures/<W>x<H>/<name>.png` exactly. Add `updateSnapshots: process.env.CI ? "none" : "missing"`. Add `expect: { toMatchSnapshot: { threshold: 0.2, maxDiffPixels: 0 } }`. `threshold` 0.2 is Playwright's per-pixel colour tolerance default, and `maxDiffPixels: 0` lets no pixel exceed it. Do not set `maxDiffPixelRatio`. If the bootstrap shows nondeterminism between two CI runs of the same commit, fix the cause in `settle` or the scenario (an image still decoding, a missed animation). Do not loosen the comparator. If a cause cannot be found, stop and report it as a blocker rather than adding tolerance. Keep `retries: 1` and `workers` unchanged. Replace the header comment with one line saying that CI gates on the baselines and that locally compare mode is opt-in.
   - How `{arg}` and `{ext}` resolve for an array name (the segments joined as a path, with the extension split off) is Playwright behaviour documented under `snapshotPathTemplate` and is unverified here. Confirm it on the first run by checking that the expected-file path in the failure message is `e2e/visual/baselines/1440x900/01-signin-server.png`.
   - Also confirm that with `updateSnapshots: "none"` a missing baseline fails the test and does not write a file. The bootstrap run proves this.

4. **CI.**
   - `visual` job: remove `if: github.event_name == 'pull_request'`. `linux-wayland-beta` runs with `if: always()` and fails on any result other than `success`, so a job skipped on push to `main` would turn `main` red.
   - Keep `runs-on: ubuntu-22.04`, the browser cache, and `pnpm exec playwright install --with-deps chromium`. That host is the one that renders the baselines, and the environment does not change.
   - Keep the `visual-captures` upload on `always()`. It is both the review artifact and the candidate baseline set.
   - Add a second upload, `if: failure()`, of `test-results/visual-run/` as `visual-diffs` (expected, actual, and diff PNGs), with 14-day retention.
   - Replace the job comment ("Output only: not required...") with a description of the gate.
   - `linux-wayland-beta`: change to `needs: [frontend, rust-checks, rust-release, tripwire, visual]`, add `VISUAL: ${{ needs.visual.result }}` to `env`, add it to the echo line, and add `test "$VISUAL" = success`. Update the comment above the job, which lists what it waits for.
   - No ruleset change is needed, because the required check name stays `linux-wayland-beta`. Keep every action pinned by SHA as today; add no new action.

5. **Orphan baselines.** In compare mode, add one test, `baselines match scenarios`. It builds the expected set `<W>x<H>/<name>.png` from `scenarios` and the viewport rule already used in the loop, then lists `e2e/visual/baselines/**.png` and asserts the two sets are equal. A missing baseline already fails its own scenario test. This test catches the reverse case: a stale baseline left behind by a renamed or removed scenario.

6. **Accept script** (`scripts/accept-visual-baselines.sh <run-id>`, `set -euo pipefail`):
   - Require one numeric argument.
   - `gh run download "$1" -n visual-captures -D "$tmp"`, with `tmp` from `mktemp -d` and cleaned up by a `trap`.
   - Fail unless `$tmp` contains only the expected size directories (`[0-9]+x[0-9]+`) and `index.html`.
   - Sync with `rsync -a --delete --include='*/' --include='*.png' --exclude='*' "$tmp/" e2e/visual/baselines/`.
   - Print `git status --short e2e/visual/baselines`.
   - The script never commits. The developer reviews the diff in the artifact's contact sheet and commits the baselines with the UI change.
   - The script uses no token beyond `gh`'s own auth and prints no URL beyond the run id.

7. **Bootstrap for this PR.**
   - Push the code with no baselines. CI fails on every capture as missing.
   - Run `pnpm test:visual:accept <run-id>`, review the contact sheet, and commit the baselines in a separate commit (`test(visual): add CI baselines (P13-25)`).
   - Push. CI should go green.
   - Then do the A2 change-and-revert proof. Push it as two commits, or as one commit that is dropped by rebasing your own branch and pushing with `git push --force-with-lease`, as `AGENTS.md` allows.
   - Before the final push, run CI twice on the same commit (re-run the job) and confirm both runs pass. That shows determinism.

8. **Docs.**
   - `WORKFLOW.md` §5: "`pnpm test:visual` writes captures to `visual-captures/` (contact sheet `index.html`). CI compares every capture with `e2e/visual/baselines/` and fails on any difference or missing or extra baseline. When a UI change is intended, run `pnpm test:visual:accept <run-id>` on the failed run, check the changed images, and commit the baselines in the same PR. After a rebase onto a branch that changed baselines, accept again from the new run; never hand-merge PNGs."
   - Make the matching one-line change in `.claude/skills/verify/SKILL.md`.

## Risks and out of scope

- **CI change (call out in the PR).** `linux-wayland-beta` gains a dependency, so every PR now needs a green `visual` job, and the job now also runs on push to `main` (about 20 minutes at most, per its `timeout-minutes`). This is a process invariant change; `ARCHITECTURE.md` invariants and `docs/security.md` are not touched.
- **Repo growth.** About 24 MB of PNGs land in the first commit, and every intended UI change adds the size of its changed captures. A token or shell change can re-baseline most of the set. See open question 1.
- **Host drift.** If GitHub updates the `ubuntu-22.04` image, or Dependabot bumps `@playwright/test` (and with it Chromium), rendering can shift, and CI goes red on PRs that did not touch the UI. The fix is a baseline-only PR accepted from CI. Note this in `WORKFLOW.md`. Pinning a Playwright container image would reduce drift, but it adds an image to maintain and a Node 26 setup inside it, so it is left out.
- **Rebase churn.** Two UI PRs that both touch baselines conflict on binary files. The documented fix is to re-accept from CI after the rebase.
- **Flakiness.** P13-01 recorded identical hashes over two local runs, but CI determinism has not been verified yet. If a capture is unstable, fix `settle` or the scenario. Never add tolerance, skip, or delete a scenario (hard rule: never skip or weaken a test).
- **Hard rules touched:**
  - Never skip, weaken, or delete a test.
  - Use fixtures; never commit credentials or copyrighted media.
  - Never log or display tokens or authenticated URLs. Captures come only from the mock server, and the accept script prints only the run id.
  - Never put the dogfood server URL in the repo. Captures contain only the mock addresses `127.0.0.1` and `192.168.50.10`, which are not the dogfood host.
  - Call out CI changes in the PR.
  - Never claim a check passed without output.
  - Change only `status`, `owner`, `passes`, and `evidence` in `tasks/prd.json`.
- **Out of scope:**
  - New scenarios or TV-form captures (P13-18 adds those and their baselines).
  - Fixing the stale `test-results/visual/` path in `docs/design/rework-plan.md` and the audit sync (P13-19).
  - Making `pnpm check` run the visual suite.
  - A container-pinned renderer.
  - Native (mpv/Tauri) visual checks.

## Open questions (all answered)

1. **Where the baseline PNGs live** (about 24 MB now, plus the changed captures on every UI PR).
   - A: Plain git under `e2e/visual/baselines/`. This is the simplest option and works with `gh run download` and rebases. The repository grows by tens of MB over the P13 UI tasks.
   - B: Git LFS for `e2e/visual/baselines/**`. The repository stays small, but it needs `git lfs` on every clone and in CI checkout (`lfs: true`), and it uses GitHub LFS storage and bandwidth quota.
   - C: Plain git, but gate only one desktop size (1440×900) and keep 1920×1080 as an ungated capture. This halves the size, but a 1920-only layout regression would pass, which arguably weakens what is gated.
   - Recommendation: A. The repository is small, the gate's value is in the P13 tasks right now, and moving to LFS later is a one-time migration.
   - **Answer: A, plain git (human, 2026-11-12).** Settled.
