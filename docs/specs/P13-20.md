## Goal

Mount the existing `ToastProvider` (`src/features/shared/ui/toast.tsx`, built in P13-03) once at the app root, so any feature can raise a toast through `useToast()`. Use it first on Detail: the Watched and Favorite toggles confirm with a toast when the server takes the change, and a failure shows an error toast that stays until dismissed, replacing today's inline `role="alert"` paragraphs (`src/features/detail/detail-actions.tsx:100-101`). No toast ever appears on the player routes (DESIGN.md §7.16).

## Approach

1. **Provider at the root.** In `App`, wrap the returned tree: `<ToastProvider suppressed={isPlayerHash(hash)}>` around `<SessionProvider>`. `isPlayerHash(hash)` returns true for `hash === "#/next/player"` or `hash.startsWith("#/next/play/")`. This is the set of routes that show the player; it is not the same as `chromeFor`'s "none" set (`#/next/player` keeps the nav). Keep the two next to each other. Keep the default `durationMs` (5 s, DESIGN.md §7.16).
2. **Suppression in the primitive.** `toastReducer` gets `case "clear": return [];`. `ToastProvider` keeps `suppressed` in a ref so `show` stays stable; `show` returns the id without dispatching while suppressed. A `useEffect` on `suppressed` dispatches `clear` when it becomes true. While suppressed, render the region with empty lists (keep the live regions in the DOM so screen readers keep them registered). Decision: toasts raised just before entering the player are dropped, not held, so a stale error never reappears after playback.
3. **Detail copy** (DESIGN.md §10 voice; settled here, added to the §10 table):
   - Watched on: "Marked as watched." (tone `ok`)
   - Watched off: "Marked as unwatched." (tone `ok`)
   - Favorite on: "Added to favorites." (tone `ok`)
   - Favorite off: "Removed from favorites." (tone `ok`)
   - Watched failed: "Couldn't update watched state. Try again." (tone `error`)
   - Favorite failed: "Couldn't update favorite. Try again." (tone `error`)
   The failure sentences keep today's inline copy so nothing new is invented; "Favorite" keeps the US spelling of the button label. No toast carries an action: pressing the toggle again is the way out, and an Undo/Retry button would add a second control for the same thing (DESIGN.md §7.16 makes the action optional). Never put `error.message` or any server text in a toast (hard rule "Map errors to plain copy").
4. **Where toasts are raised.** In `useFlagMutation`, `const toast = useToast();` and a `useRef<number | undefined>` holding this flag's last toast id. In `onSuccess(_, value)` and `onError(...)` (after the existing rollback), call `toast.dismiss(lastId)` if set, then `lastId = toast.show(...)`. This keeps one toast per flag, so quick on/off does not stack "Marked as watched." over "Marked as unwatched.", and a later success clears an earlier error for the same flag. Use `useMutation` option callbacks (not `mutate(..., { onSuccess })`). Verified in this task with a test: the callbacks still run after the Detail view unmounts, so a late answer still confirms (see the plan decision log).
5. **Remove the inline alert.** `DetailMessages` becomes `DetailMessages()` with only the player-unavailable block; `detail-body.tsx` stops passing `played`/`favorite` to it. `.detail-message` CSS stays (still used).
6. **Gallery.** Remove the local provider; the gallery route renders inside `App`, so `useToast` resolves to the root provider. Scenario `83-ui-gallery-toasts` keeps working unchanged.
7. Follow AGENTS.md style: `switch` in the reducer, two-space indent, semicolons, no new files needed.
