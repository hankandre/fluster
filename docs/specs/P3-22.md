## Goal

Fluster stores one non-secret preference today: the streaming limits, in their own `fluster.streamingLimits` localStorage record (`src/lib/browser-streaming-limits.ts`). Later tasks need more preferences: auto-play, skip, volume, and others. This task adds one versioned, validated preferences record for this computer and moves the streaming limits into it, keeping the values users already stored. The owner settled the scope in product review: one set of settings for this computer, not one per account (Q9 A, `docs/plans/proposals/product-review.md:789-793` and `:55`; `DESIGN.md:329` "Settings are one set per computer, not per account").

Nothing changes for the viewer. The Settings pickers, the toast, the limit sent in PlaybackInfo, and the mid-playback renegotiation all behave as before.

## Approach

1. **`src/lib/preference-store.ts` (shell-neutral core).** Header comment: non-secret preferences for this computer (Q9 A); one versioned record; never holds a token, credential, URL, play-session ID, user id, or anything derived from them; a shell that can persist supplies its own `PreferenceStore`. Contents:
   - `export const PREFERENCES_VERSION = 1;`
   - `export interface PreferenceValues { streamingLimits: StreamingLimits; }` (later tasks add fields here, each with a default and a validator).
   - `export const DEFAULT_PREFERENCES: PreferenceValues = Object.freeze({ streamingLimits: NO_STREAMING_LIMITS });`
   - `export function sanitizePreferences(value: unknown): PreferenceValues`. A non-object gives the defaults. Otherwise, each known field goes through its validator (`streamingLimits` through `sanitizeLimits`, which already gives `{}` for a non-object and keeps only offered values). Unknown keys are dropped. Use a `switch`-free explicit build: `return { streamingLimits: sanitizeLimits(record.streamingLimits) };`.
   - `export function parseStoredPreferences(value: unknown): PreferenceValues` for adapters: a version-1 object gives `sanitizePreferences(value)`; anything else gives `DEFAULT_PREFERENCES`.
   - `export function storedPreferences(values: PreferenceValues): { version: number } & PreferenceValues` returns `{ version: PREFERENCES_VERSION, ...sanitizePreferences(values) }`, the only shape an adapter writes.
   - `export interface PreferenceStore { get(): PreferenceValues; update<K extends keyof PreferenceValues>(key: K, value: PreferenceValues[K]): void; subscribe(listener: () => void): () => void; }` with the same listener contract as `StreamingLimitStore` (called after every update, once `get()` returns the new value).
   - `export class MemoryPreferenceStore implements PreferenceStore`, built on `LimitListeners` (reuse it as is; renaming it is out of scope).
   - `export function streamingLimitsOf(store: PreferenceStore): StreamingLimitStore`: `get` returns `store.get().streamingLimits`; `set(limits)` calls `store.update("streamingLimits", sanitizeLimits(limits))`; `subscribe` delegates to `store.subscribe`. A listener may therefore run on a change to another preference; today's only subscriber, `checkLimit` (`use-playback-session.ts:348-357`), returns early when the limit for this server is unchanged, so that is safe. Document this in the function comment.
2. **`src/lib/browser-preference-store.ts` (adapter).** `export const PREFERENCES_STORAGE_KEY = "fluster.preferences";` and `export const LEGACY_STREAMING_LIMITS_STORAGE_KEY = "fluster.streamingLimits";`. `class BrowserPreferenceStore implements PreferenceStore` with a private `MemoryPreferenceStore` fallback and its own `LimitListeners`, like `BrowserStreamingLimits` today:
   - `get()`: `try { return this.read(); } catch { return this.memory.get(); }`.
   - `read()`: `raw = localStorage.getItem(PREFERENCES_STORAGE_KEY)`. If `raw` is non-null: best-effort remove the legacy key if present (before parsing, so a corrupt new record still removes it), then `JSON.parse` (a parse error gives the memory value, as today) and `parseStoredPreferences`. If `raw` is null: call `migrate()`.
   - `migrate()`: `legacy = getItem(LEGACY_...)`. If null, return `this.memory.get()` (defaults, or a value set while storage was blocked). Else compute the limits with today's legacy rules (JSON, object, `version === 1`, `sanitizeLimits`; anything else is `{}`), set them into `this.memory`, then in its own `try`: `setItem(PREFERENCES_STORAGE_KEY, JSON.stringify(storedPreferences(...)))` and then `removeItem(LEGACY_...)`. If the write throws, keep the legacy key and return the values.
   - `update(key, value)`: start from `this.get()`, apply the change, `this.memory.update(...)` with the result, write `storedPreferences(this.memory.get())` in a `try`, then notify. Reading first keeps fields this call does not change.
   - `subscribe` delegates to the listeners.
   - Module singletons, one per launch so the memory fallback outlives a gateway: `export const preferences = new BrowserPreferenceStore();` and `export const streamingLimits = streamingLimitsOf(preferences);`.
   - A record with an unknown version (for example a newer build's) reads as defaults and is overwritten on the next `update`. Record this in the decision log.

## Risks and out of scope

Risks:

- **Downgrade.** After migration the legacy key is gone, so an older build run on the same computer shows No limit for both limits. Fluster is pre-release (`package.json` version `0.1.0`), so this is accepted; noted in the decision log. Writing both records was rejected: it keeps two sources of truth.
- **A newer build's record** (version above 1) reads as defaults in this build and is overwritten on the next change. Same reason; noted.
- **Listener breadth.** `streamingLimitsOf(...).subscribe` fires on any preference change. Safe today (see Approach 1); a future subscriber that is not idempotent must compare values itself.
- **Storage reads per call.** Like today, `get()` parses localStorage each time. The gateway reads once per negotiation and Settings once per mount, so cost is negligible.
- **Settings and the player in one window.** Unchanged: the Settings section reads the store on mount and the player subscribes. No cross-window `storage` event is handled; Fluster has one window.

Out of scope:

- New preferences (auto-play P3-23, skip P3-24, volume P3-26, and the rest). This task adds only the store and moves the limits.
- Putting the store into the React context (`src/app/preferences.tsx`); the first task with a new preference does that.
- Moving `fluster.installId` (an identity seed, `ARCHITECTURE.md:98`) or `fluster.lanHttpConfirmations` (a security record under ADR 0001) into the store. Both have their own rules; neither is a preference.
- Per-account or synced preferences (Q9 A chose per computer; `docs/plans/proposals/streaming-wishlist.md:135` notes it may be revisited with the TV shell).
- A Rust-side or file-based store for non-WebView shells. The port allows one later.
- Renaming `LimitListeners` to a generic name.
