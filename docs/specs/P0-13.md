# P0-13 Keep the window drawing after playback stops

Task: `tasks/prd.json` P0-13 (domain Player Engine; model opus; skill `native-player`; `human: false`; no dependencies). No plan file names this task (`grep -r P0-13` finds only `tasks/prd.json`), so this spec is the plan and holds the decision log. Domains touched: Video Surface & Window (`DOMAINS.md` §7) and Player Engine (§6). Implementer: `native-engineer` (Opus; all code changes are under `src-tauri/`). Reviewer: `guardian` (render-context lifetime and `unsafe`-adjacent FFI ordering). Native work is serial (`AGENTS.md` "Parallel work").

## Goal

After the user leaves playback, the Tauri window must keep painting: the previous screen appears, input works, and resize or maximize redraws the whole window. Today, on Wayland with NVIDIA, the window stops drawing after every Back (task evidence, 2026-11-10): native stop completes ("stop acknowledged"), the GTK thread and the WebKit web process are idle, the last video frame stays, and areas exposed by maximize show the desktop.

## Findings from the code (what the fix starts from)

1. **Render context freed without its GL context current (prime suspect).** `detach` in `src-tauri/src/surface/linux.rs:291-333` drops `RenderState` at line 308, which calls `mpv_render_context_free` (`libmpv2-5.0.3/src/mpv/render.rs:432-441`). Nothing makes the `GLArea` context current first. `attach` does (`linux.rs:204`), and the `render` signal has it current by GTK contract. libmpv requires it for every `mpv_render_*` call: "the OpenGL context must be 'current' in the calling thread, and it must be the same OpenGL context as the mpv_render_context was created with. Otherwise, undefined behavior will occur" (`/usr/include/mpv/render.h:67-70`, mpv 0.41.0). At detach time the current context on the GTK thread is whatever GDK or WebKitGTK last used, so mpv deletes its framebuffers, vertex arrays, programs, and hardware-decode interop in a foreign context. That it is this defect that freezes the window is **unverified**; it needs the hardware run in Approach step 1.
2. **The free happens while video is still active.** `stop` only sets `finished` (`player/controller.rs:318-337`); the event thread then calls `finalize_session` → `surface::detach` (`controller.rs:366-368`) with the core still playing. `render.h:727-728` says video is then "disabled forcefully", which tears down the decoder interop (NVDEC/CUDA on the reporting machine) inside the same call. This makes finding 1 worse on NVIDIA; it is allowed by libmpv and is not changed here unless step 1 shows it must be.
3. **The surface keeps its last frame.** The `render` handler returns without drawing when there is no render state (`linux.rs:100-102`), `auto_render` is off (`linux.rs:91`), and `set_frame` ignores `visible: false` (`linux.rs:279`), so after detach the `GLArea` stays at player size holding the last video frame under the WebView. This matches "the last video frame stays" and is fixed regardless of finding 1.
4. **Not the cause, checked:** the frontend removes `native-playing` on unmount (`src/components/PlayerView.tsx:116-122`), so the page background returns to opaque; `set_background_color` only swaps a CSS provider on the GTK window and sets the WebKit view colour (`tao-0.35.3/src/platform_impl/linux/event_loop.rs:400-414`, `wry-0.55.1/src/webkitgtk/mod.rs:767-775`). The repo sets no `WEBKIT_*` or `GDK_*` environment variable.

## Approach

One milestone per step; clippy and tests green before the next.

1. **Reproduce and confirm (no code kept).** On the reporting machine run `pnpm dogfood`, play, press Back, confirm the freeze. Then apply only step 2's `make_current` and repeat. Record both results in the Decision log below. If the freeze remains, run the bisect in "If step 2 is not enough" before writing more code. Do not skip this: finding 1 is a rule violation that must be fixed either way, but it is not yet proven to be the cause.
2. **Free the render context in its own GL context.** In `detach`, before taking `RENDER_STATE`: call `ui.gl_area.make_current()`, then check `ui.gl_area.error()` as `attach` does (`linux.rs:204-207`). If the context cannot be made current, still drop the render state (leaking mpv's GL objects is better than keeping the surface owned, and the core must not outlive it, see the `_core` field comment at `linux.rs:33-37`), and trace a fixed string. The drop stays on the GTK thread and outside any update callback (`render.h:65-66`); the callback only schedules work with `MainContext::invoke`, so this already holds.
3. **Clear and collapse the surface.** In the `render` handler's no-state branch, clear the colour buffer to opaque black instead of returning without drawing (a `gl::ClearColor` + `gl::Clear` pair in one `unsafe` block with a `SAFETY:` comment: the render signal has the context current and `gl` is loaded once any attach has run; guard with a "GL loaded" flag set in `attach`, because `gl::load_with` runs first at `linux.rs:208`). After the drop in `detach`: `fixed.move_(&gl_area, 0, 0)`, `gl_area.set_size_request(1, 1)`, `gl_area.queue_render()`. In `set_frame`, apply the same collapse when `frame.visible` is false and no render state exists; with a live session keep today's behaviour so a late hidden frame from the previous view (`src/components/NativeVideoSurface.tsx:100-113`) cannot shrink a new session's surface. Keep the `GLArea` mapped; the existing comment at `linux.rs:313-315` records why unmapping is unsafe.
4. **Restore composition and force a full paint.** Keep `set_composition_background(LIBRARY_BACKGROUND)` for the owning session only (P10-04 behaviour). Then `fixed.queue_resize()`, `webview.queue_draw()`, and `queue_draw()` on the toplevel (`gl_area.toplevel()`), so the whole window is damaged, not just the WebView.
5. **Make the order testable.** `teardown.rs` holds a small trait with one method per step (`make_current`, `free_render_context`, `collapse_surface`, `restore_background`, `queue_redraw`) and one function that runs them in that order and returns early, doing nothing, when the session does not own the surface. A `make_current` error is traced (fixed string) and the remaining steps still run. A `restore_background` error (`set_composition_background` returns `Result`) does not stop `queue_redraw`; the sequencer returns that error after the redraw is queued. `surface/linux/detach.rs` implements the trait over `UI` and `RENDER_STATE`. No generic bridge, no new public API.
6. **Paint trace (debug builds only).** After the redraw is queued, register a one-shot handler on the toplevel's frame clock `after-paint` and call `native_trace`-style output with the fixed string "window painted after detach". Fixed strings only: `trace_canary` fails any trace that mentions "session" or formats an id (`src-tauri/src/trace_canary.rs:10-15`). The handler disconnects itself after one call.
7. **Docs and task fields.** Update `docs/validation.md` and `docs/architecture.md`; fill P0-13 `evidence` with command output summaries and the manual results.

### If step 2 is not enough

Run these on the reporting machine, one change at a time, and record each result in the Decision log. They are diagnostics, not shippable fixes.

- `WAYLAND_DEBUG=1 pnpm dogfood`: after Back, do `wl_surface.commit` and `wl_surface.frame` requests continue for the toplevel? No commits means GTK's frame clock is stalled; commits with stale content means WebKit or the overlay is not producing pixels.
- `WEBKIT_DISABLE_DMABUF_RENDERER=1` and, separately, `WEBKIT_DISABLE_COMPOSITING_MODE=1`: does the freeze disappear? (`ARCHITECTURE.md:34` lists WebKitGTK transparency and DMA-BUF issues on Wayland/NVIDIA as a known risk.)
- `testForceSoftware` launch (`docs/validation.md` gate 5): does the freeze need hardware decoding? If only hardware decode freezes, stop the core before freeing the context: have the event thread issue the mpv `stop` command on its own client after its loop exits and before `finalize_session` (the comment at `controller.rs:330-333` forbids a stop from another thread while the event client unwinds, not from the event thread itself). That is a Player Engine change and needs a `guardian` review.
- Skip the `set_composition_background` calls: does the freeze disappear?

If the only working remedy is `WEBKIT_DISABLE_DMABUF_RENDERER=1` or `WEBKIT_DISABLE_COMPOSITING_MODE=1`, follow Human confirmation 1 as planned in Decision log 4. If the only working remedy is any other change outside `src-tauri/src/surface/` and the stop ordering above, stop and report.

## Test plan

1. **Rust unit tests** in `surface/teardown.rs` with a recording fake:
   - owning session: steps run exactly once, in the order make current → free → collapse → restore background → queue redraw;
   - `make_current` fails: the render context is still freed, and background and redraw still run;
   - `restore_background` fails: `queue_redraw` still runs, and the sequencer returns the background error;
   - a second detach of the same session after a successful one runs no step;
   - another session owns the surface, or none does: no step runs (covers the double detach from `request_finish` and `finalize_session`, `controller.rs:354-368`, and the P10-04 rule that another session's surface keeps its background).
2. **Scripted log check**, documented in `docs/validation.md`: run `pnpm dogfood`, do ten play-and-back cycles, then compare the counts of "dropping render context" and "window painted after detach" in the newest `release-evidence/dogfood/*.log`. Equal and at least ten passes. This is the only definition of the scripted check. It detects a stalled GTK frame clock only; it does not prove pixels reached the screen, so it supports but never replaces M1-M3. The log is already redacted by `scripts/dogfood.sh`.
3. **Manual checks**, written into `docs/validation.md` and recorded in `evidence` with compositor, GPU, driver, and `hwdec-current`:
   - M1: play a direct-play item, press Back; the previous screen appears within a second; move focus with arrow keys and click a card. Repeat with Escape, and with natural end.
   - M2: after Back, resize by dragging, maximize, restore, enter and leave fullscreen from a second playback; no stale frame, no see-through region.
   - M3: ten play-and-back cycles in a row, alternating a direct-play item and a converted (HLS) item; the window never freezes and playback starts each time.
4. **Existing suites unchanged:** `command_allowlist` (no command added), `trace_canary` (new trace strings pass), `pnpm check`. No test is skipped, weakened, or deleted.
5. **Untested, to list in the PR:** AMD and Intel GPUs; other compositors than the reporter's; X11 (unsupported, `linux.rs:55-61`); macOS (its `detach` at `macos.rs:274-299` has the same missing-current-context pattern but is out of scope and not reproducible here); the release AppImage.

## Risks and out of scope

- **Root cause unconfirmed.** Finding 1 is a real contract violation but may not be the whole cause. Step 1 and the bisect list exist for that; the Decision log must say which change removed the freeze.
- **Cannot be verified in CI.** No display, no GPU. A green `pnpm check` does not prove acceptance 1-3.
- **`make_current` at detach changes which GL context is current on the GTK thread.** GTK and WebKitGTK make their own context current before drawing, and `attach` already does the same thing, so this is expected to be safe; confirm in M3.
- **Clearing to black under the WebView** is invisible while pages are opaque; if a see-through page ever shows it, that is a page bug, not a surface bug.
- Out of scope: the macOS surface; the planned Wayland subsurface and `gpu-next` path; any DeviceProfile, negotiation, or frontend change; pinning or patching WebKitGTK; changing `transparent: true` in `tauri.conf.json`.
