# T1-13: Give agents a task CLI so nobody reads tasks/prd.json whole

- Domain: Workflow (`DOMAINS.md` §Process and Workflow: "the rule files, `tasks/`, `.claude/`, CI, and the checks in `scripts/`").
- Model: sonnet. Implementer: **`implementer`** (Node and TypeScript tooling only; nothing under `modules/`, `apps/tv/android/`, or the PlayerEngine port).
- Depends on: T1-09 (done on origin/main, PR #226).
- Risk: routine. No playback, network, token, or native change, so no Jellyscale wire test applies.

## Goal

Agents read and update tasks through a small CLI, `pnpm task`, instead of loading the 174 KB `tasks/prd.json` into context. The CLI prints one task or one line per task, and it changes only `status`, `owner`, `passes`, and `evidence`, byte for byte, and nothing else. `pnpm check` fails when the file grows past 250 KB or any evidence field runs past 600 characters. The workflow, the skills, the agent prompts, `AGENTS.md`, and `WORKFLOW.md` point at the CLI.

## Facts this spec rests on

- `tasks/prd.json` is exactly `JSON.stringify(parsed, null, 2) + "\n"`. Running `node -e` on the file returned `true 173673 173673 true`. A parse, edit, and re-stringify therefore keeps the file's formatting and changes only the edited values.
- Each task has the keys `acceptance, depends_on, domain, evidence, human, id, model, owner, passes, skill, status, title, verify`. Each phase has the keys `exit, goal, id, name, tasks`. `status_values` is `["todo","in_progress","blocked","done"]`.
- `passes === (status === "done")` holds for every task today (a jq check found no mismatches). `src/tasks/prd.test.ts` enforces it, and it also enforces that `passes: true` has non-empty evidence.
- The longest evidence today is 551 characters (T0-01), so the 600-character check passes on main. The file is 173,673 bytes, so the 250 KB check passes.
- T0-02, T0-03, and T0-04 are in progress and their evidence names only a branch. Rules 2 and 12 in `prd.json`'s `rules` require evidence for blocked tasks, usually before any PR exists.
- No task skill exists. `ls .claude/skills` lists `change-review doc-gardening exec-plan jellyfin-api native-player ship verify`. `git log --all -- '.claude/skills/task*'` is empty, and `~/.claude/skills` has none either.
- Run in this worktree before the script exists, `pnpm task` executed a `task` binary on PATH (go-task printed "Recently upgraded to 3.5.0…"). A package.json script named `task` must take precedence over that binary.
- In a worktree without `node_modules`, pnpm 11 first installs and writes "Lockfile is up to date… Done in …" to **stdout**. This was seen with `pnpm test:workflow 2>/dev/null`. Once the tree is installed it prints nothing extra.
- `vitest.config.ts` includes `scripts/**/*.test.ts`, and `tsconfig.json` includes `scripts/**/*.ts`. `scripts/check-ghost-terms.mjs`, `.d.mts`, and `.test.ts` set the pattern for a script with exported pure functions, a type declaration, and a Vitest test.
- `.claude/workflows/task.js` never reads `prd.json` itself. It only tells agents to (lines 183, 256, 261, 302, and the Ship prompt).

## Approach

1. **Locating the file.** `TASK_FILE = fileURLToPath(new URL("../tasks/prd.json", import.meta.url))`. The file is found from the script's own location, never from the cwd. Agent shells reset to the main checkout, so `pnpm -C <worktree> task …` (or running the worktree's own script) edits the worktree's copy and never main's.
2. **Reading.** `next`, `show`, and `list` parse the file in the CLI process and print only their slice. The agent's context never sees the whole file. Pretty JSON goes to stdout. Errors go to stderr as `ERROR task: …` with exit 1. No arguments, or an unknown subcommand, prints usage to stderr and exits 1.
3. **Writing (`set`).**
   - Read the text and parse it.
   - Refuse with `ERROR task: tasks/prd.json is not in its canonical 2-space JSON format; refusing to reformat it` when `JSON.stringify(parsed, null, 2) + "\n" !== text`.
   - Find the task and assign `status`, `passes = status === "done"`, `owner` (if given), and `evidence` (if given) in place, so key order is kept.
   - Validate as in rows 3 and 4.
   - Stringify, then write to `tasks/.prd.json.<pid>.tmp` and `renameSync` over `prd.json`.
   - Print the updated task's one `list` line.
   - Leave the top-level `updated` field and everything outside the task untouched.
4. **Check.** `checkTaskFile(bytes, prd)` is pure. The real-file assertion lives in `scripts/task.test.ts`, so `pnpm test`, and with it `pnpm check` and CI, fails with the ERROR lines.
5. **Prompts and docs.** Apply the row 6 edits. In `task.js`, keep the prompts' meaning and swap only how agents read and set the task. Example implement line: "Set the task to in_progress with `${taskCli} set ${task} --status in_progress --owner ${implAgent} --evidence-file <a mktemp file outside the repo>`; the evidence must name a commit (`commit <sha>`) or PR (`PR #n`) and stay within 600 characters." The implement, follow-up and Ship prompts all state this rule through one shared `evidenceRule` string; the follow-up sets done before any PR exists, so its evidence must contain `commit <sha>`.
6. **Dogfood.** After the work is committed, the implementer sets T1-13 to in_progress with `pnpm task set` and evidence naming the commit. The follow-up step sets it to done the same way.

## Risks and out of scope

- **Stdout noise on a fresh worktree.** pnpm 11's pre-run install prints to stdout, so the first `pnpm task …` in an uninstalled worktree is not JSON-only. Mitigation: `task.js` prompts call `mise exec -- node <worktree>/scripts/task.mjs …` directly, with no pnpm and no install. This matters most for the spec and check phases, which run `show` in a just-created worktree. The CLI's own stdout is only JSON or lines. `pnpm -C <worktree> <script>` was confirmed from the main checkout on the installed worktree (`pnpm -C ../octave-T1-13 test:workflow` ran the worktree's tests), but the prompts do not rely on it. The CLI's usage text notes that a machine consumer should call the script with node.
- **`task` name clash.** A `task` binary (go-task) exists on at least one dev PATH. pnpm runs a package script before falling back to PATH. This is unverified against pnpm 11 docs, so the validation below checks `pnpm task next` prints the expected JSON.
- **Naming rule not in `pnpm check`.** Acceptance item 5 gates the check on size and length only. Adding the naming rule there would fail main today on T0-02, T0-03, and T0-04. Naming is enforced at write time by `set`.
- **Concurrent writers in one checkout.** Each task works in its own worktree, and the atomic rename keeps the file from being left half-written. Lost updates between two simultaneous `set` calls in the same checkout are out of scope.
- **Out of scope:**
  - moving finished phases out of the file (the Product Owner's job; there is no done.json per prd rule 17)
  - `tasks/backlog.jsonl` (T1-10)
  - the frozen-test diff check (T1-12)
  - scanning evidence for secrets
  - an `--owner` clear option
  - including human tasks in `next`, which the owner can still read with `show`
  - rewriting `src/tasks/prd.test.ts`

## Decision log

- **Naming rule scope (spec-check note 1, owner may veto).** Acceptance item 4 says evidence "must name the PR or commit". This implementation enforces that in `set` for `in_progress` and `done` only, and exempts `blocked` and `todo`, because prd rules 2, 11 and 12 require blocked evidence before any PR or commit exists. This is an interpretation, not an edit: the acceptance text is unchanged. The PR body calls it out so the owner can veto it.
- **Prompt tests (note 4).** `task.test.mjs` slices `task.js` by the anchors `const common =`, `Implement the approved spec.` to the `implement ${task}` label, `Fix these review findings` to the `follow-ups ${task}` label, and `const shipPrompt`, so each assertion names the prompt that holds it.
- **jq scan (note 5).** The frozen `\bjq\b` scan also bans a legitimate `gh ... --jq` in future skills. Accepted, and stated in the test's description.
- **Spawn tests (note 6).** They run `process.execPath`, not `node` from PATH.
- **Flag errors (note 7).** `parseSetArgs` uses `allowPositionals: true` and maps `ERR_PARSE_ARGS_UNKNOWN_OPTION` to the fixed refusal message.
- **Tests after code.** The CLI file was written before its tests in this run; the tests were then checked against the docs edits (the jq scan failed red until the docs were edited), and no test was weakened.
- **Review fix (medium).** `list` now parses its filters with `parseListArgs` (`parseArgs`, strict), so `--status=todo` works and a misspelled flag, a missing value or a stray positional exits 1.
