## Goal

Replace the Markdown backlog with `tasks/backlog.jsonl`. The new file has one JSON object per line. Git merges it with the built-in `union` driver, so two branches that each append an entry never conflict. A validator that runs in `pnpm check` keeps every line well formed. Entries that still apply to the TV app move across, and desktop-only entries are dropped. `tasks/backlog.md` is deleted, and the rule files point at the new file and say how to add an entry.

## Approach

### 1. Validator first (tests first, prd rule 9)

1. Write `scripts/check-backlog.test.ts` with the unit cases from rows 1, 3, 4 and 6 and the real-file test from row 5.
2. Watch the tests fail.
3. Implement `scripts/check-backlog.mjs`.

`validateBacklog(text)`:

- If the text is non-empty and does not end with `\n`, report it.
- Split on `\n` and drop the final empty piece.
- For each line, check in this order:
  - `\r`, then empty
  - `JSON.parse` in a try block
  - a plain object: `v !== null && typeof v === "object" && !Array.isArray(v)` (check this before `Object.getPrototypeOf`, which throws on `null`)
  - unknown keys
  - the required string fields (missing, not a string, or blank)
  - `size`
  - `date`: `/^\d{4}-\d{2}-\d{2}$/`; then `const d = new Date(s + "T00:00:00Z")`, reject when `Number.isNaN(d.getTime())` (so `2026-13-01` never reaches `toISOString`, which throws a RangeError on an invalid date), and finally require `d.toISOString().slice(0, 10) === s` (rejects `2026-02-30`)
  - `taken_by`
- Exact repeats are tracked in a `Map<string, number>` of raw line to first line number. Repeated `what` values are tracked the same way, on the trimmed `what`.

One malformed line can give several errors; all are reported. Messages put `ERROR` on the same line as the cause (`WORKFLOW.md`, Oracles). Each message ends with a fix, for example `; use one of S, M or L` or `; this entry was kept twice by a union merge, so keep the newer line and delete the other`.

#### 2.1 Classification rule

**Carry** a source entry when its subject still exists or is planned for the TV app:

- a viewer-facing feature or product decision that does not depend on the desktop shell
- a Jellyfin or Jellyscale API fact, request, or test
- code that still exists on main: `src/domain/`, `src/lib/` (including `redact.ts`, `safe-reason.ts`, `diagnostics.ts`, `preference-store.ts`, `src/lib/jellyfin/`, `src/lib/player/`), `tests/integration/`, `tests/fixtures/`, `scripts/`, `.claude/`, `.dependency-cruiser.cjs`, and the rule docs
- the libmpv engine to come, only when `docs/mpv-options-checklist.md` does not already hold the point
- security tests from decision 0005

Before carrying an entry that cites a file or line, check that the path still exists (`git ls-files <path>`) and that the problem is still there. If the cited file is gone and the subject is shell-specific, the entry is desktop-only.

**Drop as desktop-only** an entry whose subject was removed with the desktop app:

- the Rust layer, GTK, the desktop window or WebView, glib
- the desktop release, Windows, macOS, or Flatpak packaging
- the DOM UI under `src/features/` and its CSS
- the Playwright end-to-end and visual suites and their helper scripts
- keyboard shortcuts, pointer clicks
- the desktop CI jobs (`rust-audit`, the sharded visual job)
- the desktop player engines (`BrowserPlayerEngine`, `native-player.ts`)
- the libmpv binding crate

**Close** an entry, without carrying it or counting it as desktop-only:

- Struck through and either declined by the owner, out of scope, or taken by a desktop task that was `done` at the tag. Check the task with `git show desktop-tauri-final:tasks/prd.json | jq` on that one id, or with the PR or commit named in the entry.
- A bookkeeping line: "Tasks now: …", "The owner answered …", "Applied by the coordinating agent …", "Waiting for …", "Owner decisions:".
- A note for a desktop task's spec that holds no work of its own.
- A note or duplicate folded into another carried entry (for example lines 111, 113, 114, 135, 139 and 141).

**A struck entry whose taking desktop task was not done at the tag**, or that was taken only by a branch, is treated as open. Classify it by the carry and drop rules above. Example: line 429, personal ratings, taken by P16-14 to P16-17, all `todo` at the tag. It is carried with `source` naming the desktop tasks and no `taken_by`, so the Product Owner can triage it. Keep its findings short and point at `tests/fixtures/jellyfin/README.md` "Personal ratings (P16-13)" for the API facts.

#### 2.3 Field derivation

- **`what`**: one sentence naming the work, in the backlog's plain style (`AGENTS.md`: short imperative sentences). It must be unique in the file.
- **`why`**: the reason or evidence from the entry (votes, a finding, an owner request, the risk). It is never blank; if the entry gives none, state the problem it fixes. Fold notes and duplicates here. Keep it to a few sentences; long findings point at their doc.
- **`source`**: the original origin: a task id, PR (`#207`), commit, doc path, or "owner, 2026-11-16". Desktop task ids (`P…`) are kept as they are; `WORKFLOW.md` says they live in the tag.
- **`size`**:
  - Keep `S`, `M` or `L` as given.
  - A range ("S to M") takes the larger value.
  - "M each" or "S, M, M" splits into one line per item, each with its own size.
  - An entry with no size gets the implementer's estimate, using the same scale as its neighbours. List the estimated ones in the PR body.
- **`date`**:
  - Use the date written in the entry, or else in its section heading.
  - Otherwise use the date the line first appeared: `git log --reverse -S'<a unique snippet>' --date=short --format=%ad desktop-tauri-final -- tasks/backlog.md | head -1`.
  - Never use `git blame` on main, which the rename commit skewed.
- **`taken_by`**: set it only to a T task id, and only when that task's acceptance clearly covers the entry. Read the task with `pnpm task show <id>`, never just its title. Leave it out otherwise. P ids never go in `taken_by`.

## Risks and out of scope

- **Classification is judgment.** Sonnet could drop a TV-relevant entry. Mitigations:
  - the rule in §2.1, which wins over the table
  - the per-section table with its exceptions
  - the PR's list of every dropped and closed entry with its old line number, so the reviewer and the owner can contest any of them
  - the tag keeps the whole old file, so nothing is lost
- **Work taken by unfinished desktop tasks.** Without the "struck but not done at the tag" rule, features such as personal ratings would vanish. §2.1 carries them for the Product Owner to triage.
- **Union merge limits.**
  - `union` keeps both sides of a conflicting hunk. If two branches edit the same line, for example both setting `taken_by`, or one edits the last line while the other appends, both versions survive. The duplicate-`what` check catches that and says to keep the newer line.
  - A line without a final newline can be glued to the next one; the final-newline check catches it.
  - Whether GitHub's pull-request conflict check honours `merge=union` is **unverified**. Local `git merge` and `git rebase` do honour it, and the test proves that. The `ship` skill already resolves conflicts by rebasing locally. Logged in §2.6.
- **Branches in flight that append to `tasks/backlog.md`.** After this merges, they hit a modify/delete conflict. Whoever rebases moves the appended lines into `backlog.jsonl` as JSON. Before shipping, re-read `origin/main`'s `tasks/backlog.md` for entries added since `8b34681` and migrate them too.
- **`git` in unit tests.** CI's runner has git, and the tests isolate config. A machine without git fails these tests loudly rather than skipping them; skipping would weaken them.
- **Out of scope:**
  - triaging, re-prioritising, or turning entries into tasks (the Product Owner's job, T1-12)
  - editing `prd.json` rules
  - a backlog CLI like `pnpm task`
  - rewriting `docs/research/` citations
  - checking that `taken_by` ids exist in `prd.json`, which a Product Owner trim of finished phases would break
  - a size cap on the file
