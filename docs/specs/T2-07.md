## Goal

1. The source decision reads what the device can play. It returns direct play only when an engine on this device can play the source's video and its audio.
2. When the server offers direct play for a source the device cannot play, the gateway sends exactly one more PlaybackInfo for that media source with direct play and video stream copy off, in body and query, and uses the answer.
3. The plan built from that answer carries a client-side conversion reason, and the indicator says this device cannot play the original.
4. When the answer is not a conversion the device can use, the result is a typed refusal that says this device cannot play the file. The forced request is never sent twice.
5. A host that states no device limit, and a device that can play the source, send exactly the requests sent today.
6. The DeviceProfile does not change. What the device can decode never reaches the server.

## The rules

### Capability states

The source decision takes `DeviceCapabilities`, which is `"full"` or a `PlayerCapabilities` value.

| State | Meaning | Decision |
|---|---|---|
| `"full"` | The host states no device limit: Node tests, the tripwire's full run (T2-09), a gateway built without a capability source | Every source is playable. Requests are exactly today's |
| `{ probe: "complete", … }` | The engine read the device | The playability rule below |
| `{ probe: "failed" }` | Cannot tell (T8-07: "never as can play") | Nothing is playable; every direct-play offer takes the forced conversion |

`"full"` is a negotiation-side value. An engine cannot report it: `readCapabilities` returns only the two `probe` shapes.

### Playability (`probe: "complete"`)

The device can play a source when it can play the judged video stream and the judged audio stream.

- **Video.** The judged stream is the first `MediaStreams` entry with `Type: "Video"`. A decoder in `videoDecoders` matches when all hold:
  - `decoder.codec` equals the stream's `Codec`, lower-cased;
  - `decoder.profile` is absent, or equals the stream's `Profile` (trimmed, case-insensitive);
  - `decoder.maxBitDepth`, `maxWidth` and `maxHeight` are each absent, or the stream's `BitDepth`, `Width` and `Height` is a number not above it.
  - A limit the decoder states and the source does not give a value for is not a match, as `exceeds` already treats unknown values (`source-acceptance.ts:139-144`).
  - Hardware and software decoders both count (`PLAYBACK_POLICY.allowSoftwareDecode` is `true`).
- **Audio.** The judged stream is the audio stream the request names (`AudioStreamIndex`, a viewer's pick or a renegotiation), else `DefaultAudioStreamIndex`, else the first `Type: "Audio"` stream. It is playable when its `Codec`, lower-cased, is in `audioDecoders`, or the device passes it through: `ac3` with passthrough `ac3`; `eac3` with `eac3` or `eac3-joc`; `dts` with `dts` or `dts-hd`; `truehd` with `truehd` (decision 0003, item 2: Media3 is the engine for passthrough).
- **Missing data.** A source with a video stream and no audio stream is judged on video alone, and the reverse. A source with neither, a judged stream without a `Codec`, and a codec outside the capability vocabulary are not playable.
- **Not read:** the `hdr` list, audio channels, level, frame rate, and every stream other than the two judged ones. See "Risks and out of scope".

### Source decision (amends `ARCHITECTURE.md` §3)

- **Rule 3** gains its last condition for real: direct play only when the device can play the source.
- **Rule 5.** The server offered direct play (rule 3's other conditions hold), and the device cannot play the source: `decideSource` returns `force-conversion` with what cannot be played (`video`, `audio`, or both). The gateway sends one more PlaybackInfo for that `MediaSourceId`:
  - `EnableDirectPlay: false` and `AllowVideoStreamCopy: false`, always (acceptance item 2);
  - `AllowAudioStreamCopy: false` when the judged audio is what the device cannot play, otherwise `true`. This closes the clause `ARCHITECTURE.md` rule 5 left open: the profile's `AudioCodec` list (`aac,ac3,eac3,opus,flac,mp3`) lets the server copy audio the device has no decoder for;
  - every other flag, the stream indices, the streaming limit and the DeviceProfile exactly as on the first request, in body and query.
- **The answer to the forced request** is decided once, for that source only. The first matching row wins:

  | Answer | Result |
  |---|---|
  | Any refusal of rules 1 and 2 (`missing-source-data`, `live-source`) | The answer's own refusal |
  | A conversion whose rebuilt URL carries `AllowVideoStreamCopy=false`, and `AllowAudioStreamCopy=false` when audio was turned off (names and values matched in any case) | An HLS plan with `clientConversionReason: "DeviceCannotPlay"` |
  | A conversion without those parameters | Refuse `device-cannot-play` (detail `stream copy not turned off`): the URL does not show the stream is re-encoded, and the recorded forced-fallback answers show such a URL copies the source codec |
  | A `TranscodingUrl` that is not HLS or fails the rebuild | The answer's own refusal (`unsafe-transcoding-url`) |
  | No `TranscodingUrl`, and direct play offered again | Refuse `device-cannot-play` (detail `direct play offered again`). This holds whatever `SupportsTranscoding` says: acceptance item 3 names this answer |
  | No `TranscodingUrl`, no direct play, and `SupportsTranscoding` is `false` | Refuse `conversion-not-allowed`: the server says this account may not convert (the recorded `no-conversion-user` answers), and that copy tells the viewer what to ask for |
  | No `TranscodingUrl`, no direct play, and `SupportsTranscoding` is not `false` | Refuse `device-cannot-play` (detail `no conversion offered`): the server may convert and offered nothing |

- **Never a third request** means: the forced-conversion request is sent at most once per negotiation, and never together with the disc forced-fallback request.
- **A viewer's audio pick** keeps its settled rule, "a pick never costs a direct play… a direct-play answer to either wins" (`ARCHITECTURE.md` §3):
  - First answer `force-conversion` because the video cannot play: the plain request is skipped (it judges the same video), and the forced request carries the pick. Two requests.
  - First answer `force-conversion` because only the picked audio cannot play: the plain request (no index) is sent. If it direct plays, it wins: the original plays with the source's default audio, and the plan's `defaultAudioStreamIndex` is the source's default, not the pick. If it does not, the first decision is kept and the forced request carries the pick. Three requests at most.
  - A first answer that was refused and a plain answer that is `force-conversion` also ends in the forced request. Three requests. The forced request carries the pick, as the disc path does (`streams`), so `carriesPick` is `true` for the resulting plan; the audio flag is judged on the picked track.
  - So a negotiation sends at most three PlaybackInfo requests, only with a pick, and at most one of them is the forced conversion. This reading of "never a third request" follows from the settled pick rule; `decisions-T2-07.md` does not cover it, so the PR calls it out for the owner.
  - **No notice for a dropped pick.** When the plain answer direct plays because the device cannot play the picked track, the plan carries the source's default audio (`defaultAudioStreamIndex`) and nothing tells the viewer. No copy is invented here; a backlog entry asks the owner for it.
- **Order of rules.** Rule 4 (a disc) runs before rule 5: a disc has no probed streams, so it keeps today's forced fallback with `EnableDirectPlay: false` only.
- **Several versions.** The first DirectPlay source wins, then the first DirectStream, then the first Transcode, then the first source that needs the forced conversion, then the first disc that needs the forced fallback, then the first refusal. So a version the device can play always beats one it cannot.
- **Renegotiation** on a converted session goes through the same path: the first request offers direct play again, the decision is `force-conversion` again, and the forced request carries the new stream indices.

### Copy

Confirmed by the owner on 2026-11-21 (`docs/specs/decisions-T2-07.md`). Use these strings exactly.

- Chip: `Converting on server: this device cannot play the original`. The client reason leads the chip, before a bitrate reason.
- Info panel reasons: the client reason first, then the server's reasons except `DirectPlayError` ("playing the original file failed" would be untrue here; the server sends it for every `EnableDirectPlay: false` request). `plan.conversionReasons` keeps what the server sent.
- Refusal: `This device cannot play the file, and the server offered no conversion.`
- A plan with a client reason always uses the "Converting on server" chip, whatever method `confirmedPlan` later sets: the original is what the device cannot play, so "Repackaging on server, original quality" would be untrue. Tested with a `DirectStream` plan.
- `playOriginalAvailable` is `false` for a plan with a client reason: the original is what the device cannot play. (A consequence of the rule, not a wording choice.)

### Decision log

- **D1. Capabilities reach the gateway through a constructor port, not the coordinator's call.** The frozen coordinator tests pin that call. A getter (as `StreamingLimitStore.get`) because the engine is initialised after sign-in. T8-07 passes the engine's answer.
- **D2. The default is `"full"`.** Frozen gateway tests build the gateway without it and expect today's requests. The cost: an app that forgets to pass a source direct-plays everything, and the engine then fails with `decoder-unavailable`. T8-07's emulator test ("asserts the requests sent") is the guard, and a backlog entry asks T8-07 to fail the app's composition when no source is passed.
- **D3. `"full"` is a separate value, not a long list.** It must mean exactly today's behaviour. A list cannot call playable a source with no `MediaStreams`, an unlisted codec, or a missing value a decoder limits, and existing tests are free to use such sources (which of them do is unverified).
- **D4. Strict on unknowns.** T8-07 says a failed probe is never "can play"; the same holds for a missing codec, profile or size the decoder limits.
- **D5. A forced answer must show stream copy is off.** Without it, a server that honours only `EnableDirectPlay: false` returns a URL that copies the undecodable codec (the recorded forced-fallback answers). It also gives the refusal for a Jellyscale that ignores one or both flags.
- **D6. The client reason is its own field.** `CONVERSION_REASONS` mirrors the server's enum and is filled from URL values; a server must not be able to set the client reason, and `confirmedPlan`'s spread keeps a separate field.
- **D7. The device conversions are not HLS vectors.** `hls-master-urls.json` is frozen. Adding them is a Product Owner ruling; a backlog entry asks for it before T8-08.
- **D8. `AllowVideoStreamCopy: false` is sent even when only the audio cannot play.** Acceptance item 2 and the amendment say so. A backlog entry proposes keeping video copy in that case.
- **D9. A forced answer that offers nothing is `device-cannot-play` unless the server says the account may not convert.** The confirmed refusal copy ("…and the server offered no conversion") is true for it. `SupportsTranscoding: false` is the signal both Jellyfin versions send for a user who may not convert (the recorded `no-conversion-user` answers), and `conversion-not-allowed` then tells the viewer more. "Direct play offered again" is always `device-cannot-play`, because item 3 names it. This keeps item 8 true for more Jellyscale answers than the first draft's table did.
- **D10. The Jellyscale fixture comes from T2-08's pinned server** (`decisions-T2-07.md`, decided by the coordinator, owner may veto). It is recorded by a raw request in its own recorder mode and stored in the pin folder under a `device-` name. The acceptance text is unchanged.
- **D11. Tests find the Jellyscale folder from the compose pin**, never from a literal `b920b193cd6f`. A pin bump then fails the new test for a missing file until the fixture is recorded again, which is the wanted signal (T10-08 will do exactly that).
