## Goal

Every task run writes its failing tests before any implementation, and nobody but a Product Owner step can change those tests afterwards. Concretely:

1. The task workflow gains a **Tests** phase between Check and Implement. A `test-writer` agent turns each acceptance item into a failing test, lists the test files in a manifest, and commits both.
2. A **red gate** runs each test and stops the whole run if any of them already passes.
3. A **frozen-test check** (`pnpm lint:flow`) fails the run and CI when a frozen test file differs from the version the test writer, or a later Product Owner step, committed.
4. A **Product Owner** agent (Fable 5.2) is the only step that adds, drops, reorders or rewords tasks in `tasks/prd.json`, working from `tasks/backlog.jsonl` through a narrow script. The same check fails CI when anyone else does it.
5. `WORKFLOW.md` lists the steps in the order they run.

### Items that cannot be failing tests

A human check, a Shield check, a review, or a step only CI can produce cannot be a failing test. The spec's Acceptance table names each such item as a **gate**, with one of the kinds `owner`, `device`, `review`, `ci`, and the test writer copies it into the manifest. A fifth kind, `met`, is for an item that is already true on `main`: the spec names the existing test that proves it. The spec names a gate by writing `gate: <kind>` in the item's "How it is tested" cell; `check-red.mjs` parses those cells and refuses a manifest gate the spec does not name, and a spec gate the manifest runs. The gated items are in the red gate's JSON, the run logs them, and the Review prompt lists them so the reviewer checks each against the spec. `spec-checker` checks the gates. For this task: none. The CI proof belongs to item 3 and is an extra ciStep, not a gate.

## Approach

### 1. The manifest

The test writer commits `docs/specs/<ID>.tests.json` together with the tests:

```json
{
  "task": "T4-02",
  "files": ["src/lib/catalog/shelf.test.ts"],
  "items": [
    { "item": 1, "run": ["pnpm", "vitest", "run", "src/lib/catalog/shelf.test.ts", "-t", "item 1"] },
    { "item": 2, "gate": "owner", "why": "a Shield check" }
  ]
}
```

- `files`: every test file, fixture and snapshot the test writer wrote or changed. These are the frozen files. The manifest itself is frozen too.
- `items`: one entry per acceptance item, numbered from 1 in the task's order. Each has a `run` (an argument list, started without a shell, whose first word is `node` or `pnpm`) or a `gate` with its `why`. Each `run` must select only that item's tests, so one already-passing item cannot hide behind another's failure.
- `validateManifest(manifest, id, acceptanceCount)` returns one `ERROR` line per problem: wrong `task`, an item number missing or repeated, an entry with neither or both of `run` and `gate`, a gate kind other than the five, a `run` whose first word is not `node` or `pnpm`, an empty `files` when any item has a `run`.

The freeze is the commit that **adds** the manifest. It is found from history, not from a hash the run holds, so it survives the Ship rebase. It applies only while that commit is ahead of `origin/main`; once the branch merges, later tasks may change those tests through their own test writer.

### 2. `scripts/check-flow.mjs` (`pnpm lint:flow`)

Usage: `node scripts/check-flow.mjs [--repo <dir>] [--base <ref>] [--task <ID>] [--json]`. The base defaults to `origin/main` and the repository to the current directory. It reads only git. Agent shells do not keep a working directory, so the run always passes `--repo`.

Range:

- It fails with an `ERROR` line when the base does not resolve, when no merge base exists, or when `git rev-parse --is-shallow-repository` prints `true`. The message says to fetch full history. It never passes because it could not read the range.
- Tip: `HEAD`, except when `HEAD` has two parents and `HEAD^1` is an ancestor of the base (the `pull_request` merge ref, also when `main` moved after GitHub built it); then the tip is `HEAD^2`, so a change that `main` made to a test file is not blamed on the branch. Tested against git in `task.test.mjs`.
- Commits: `git rev-list --reverse --no-merges <merge-base>..<tip>`. For each, its changed paths (with rename sources) and its trailers.
- On `pull_request` the range is the PR's commits; on `merge_group` it is the queued commits; on a push to `main` it is empty and the check prints `0 commits ahead of origin/main` and passes.

Frozen tests, per manifest added in the range (path `docs/specs/T<n>-<nn>.tests.json`, found with `--diff-filter=A` over the range, so a later deletion cannot hide it):

- The freeze commit is the commit that added it. The manifest read at that commit is validated; the acceptance count comes from `tasks/prd.json` at the tip.
- For each frozen path (the manifest and its `files`), the **authorised commit** is the last commit in the range that is the freeze commit or carries `Frozen-Test-Change: <path> -- <reason>` for that path and changes it. A trailered commit that changes the manifest also updates the frozen file list.
- The path's blob at the tip must equal its blob at the authorised commit. A missing file counts as different. Because this compares end states, a mistaken edit that is reverted passes.
- Problem line: `ERROR frozen test: <path> differs from the test writer's version (<short sha>); restore it with git checkout <sha> -- <path>. If the test is wrong, return it in frozenTestProblems; only the Product Owner step may change it.`
- With `--task <ID>`, a missing manifest for that task is a problem and the JSON carries `"missingManifest": true`. Without it (CI), a branch with no manifest passes.
- Two manifests added in one range that freeze the same path (two queued PRs in a `merge_group`) are a problem: `ERROR frozen test: <path> is frozen by two manifests (<ID>, <ID>)`. A manifest that already exists at the merge base and is changed in the range was not added, so nothing is frozen; with `--task` it is `missingManifest` with the message "the manifest already exists on the base". A reopened task is a follow-up (Deferred).

Task list:

- The **shape** of `tasks/prd.json` is the parsed file with `status`, `owner`, `passes` and `evidence` removed from every task.
- If the shape at the merge base equals the shape at the tip, pass.
- Otherwise the authorised commit is the last commit in the range that carries `Product-Owner-Pass: <text>`, changes `tasks/prd.json`, and changes `tasks/product-owner-log.md`. The shape at the tip must equal the shape at that commit.
- Problem line: `ERROR task list: tasks/prd.json changed outside status, owner, passes and evidence; only a Product Owner pass adds, drops, moves or rewords tasks. Append the work to tasks/backlog.jsonl instead.`

Output: `ERROR` lines on stderr and exit 1, or a short summary and exit 0. `--json` prints one line: `{"ok":bool,"commits":n,"manifests":[{"task","freeze","files"}],"changes":[{"path","commit","reason"}],"frozen":[{"path","blob"}],"taskListChanged":bool,"missingManifest":bool,"problems":[...]}`.

Exports for the tests: `validateManifest`, `shapeOf`, `findFrozenProblems`, `findTaskListProblems` (pure, over plain commit data), and `readRange` (git).

`frozen` lists each frozen path with its blob at its authorised commit; the run pins those blobs (§4).

What it cannot prove: every agent commits under one identity, so a trailer can be forged. It also cannot see an amend or squash into the freeze commit, because the freeze commit is what it trusts; CI has no pinned blobs, so only the run (§4) catches that. The check makes a change to a frozen test or to the task list deliberate, visible in the commit and in the PR, and impossible by accident. The run closes most of the gap (§4): it accepts trailered changes only for the paths its own Product Owner step returned.

### 3. `scripts/check-red.mjs`

Usage: `node scripts/check-red.mjs <ID> [--repo <dir>] [--expect red|green]`. It reads `docs/specs/<ID>.tests.json` and `docs/specs/<ID>.md`, validates the manifest, compares its gates with the spec's ("Items that cannot be failing tests"), runs each `run` with `spawnSync` (no shell, `process.execPath` when the first word is `node`), and prints one JSON line: `{"task","expect","red":[items],"green":[items],"gates":[{item,kind,why}],"blobs":{path: blobId},"problems":[...]}`; `blobs` is `git rev-parse HEAD:<path>` for each frozen file and the manifest. A command that cannot start is a problem, not a red item. Exit codes: 0 when every `run` is red, 1 when at least one item is green, 2 for problems only, so a broken manifest is never reported as a passing test. `--expect green` (default `red`) inverts the check: exit 0 when every `run` passes, 1 when one still fails. The run uses it after the follow-ups step, so a `run` that `pnpm check` does not cover (another `node --test` file, later `pnpm tv:native:test`) cannot ship red.

### 4. `task.js`

- `MODELS` gains `tests: { routine: 'sonnet', native: 'opus' }`, `owner: 'fable'` and `gate: 'haiku'`. `resolveModels` throws on an override of `owner`, so a frozen-test ruling always runs on Fable.
- A new pure block, `// GATE-BEGIN/END`:
  - `STOP_OUTCOMES = ['denied', 'tests-green', 'frozen-tests']`.
  - `decideRed(gate)` takes `{ exitCode, output }` and returns `{ action: 'pass' | 'stop' | 'retry', detail, blobs, gates, unreadable }`: `stop` when the JSON lists a green item; `retry` for problems, a missing result, or output that is not the expected JSON line (`unreadable: true`); `pass` only for exit 0 with no green item, carrying the frozen blobs and the gated items.
  - `decideGreen(gate)` (the `--expect green` result): `pass` for exit 0, `blocked` for a red item or a problem, `retry` with `unreadable` for output it cannot parse.
  - `decideFrozen(gate, approvedPaths, pinned, final)` returns `{ action: 'pass' | 'stop' | 'blocked' | 'retry', detail, unreadable }`. It fails closed: a non-zero exit, a `changes` path that is not in `approvedPaths`, and a `frozen` blob that differs from `pinned` (or a pinned path that is missing) for a path not in `approvedPaths` are `stop`. Unreadable output is `retry` until `final` is true, then `stop`. `missingManifest` alone is `blocked`. `pinned` is the red gate's `blobs`; a resumed run has none and skips that comparison.
  - `runGate(command, label, phase, decide)` runs the gate agent, maps its `deniedCommands` to the `denied` outcome, and runs it once more when the decision is `unreadable`, so one relay slip does not end the batch.
- `decideStep` returns `{ action: 'owner' }` when the result lists `frozenTestProblems`; the order is `none`, `denied`, `owner`, `done`, `retry`, so a green result that also lists problems goes to the owner. `WORK` gains `frozenTestProblems` (strings).
- A `gate(command, label)` helper starts an agent with no agent type on `models.gate`, never the implementer: "Run exactly this command, change nothing, and return its exit code and the last line it printed." The command is self-contained: `mise exec -- node <worktree>/scripts/<script> --repo <worktree> …`. Schema: `{ exitCode: integer, output: string, deniedCommands }`.
- Phase 3, Tests (skipped when `from` is `implement` or `review`; `from: "tests"` is new):
  1. `test-writer` on `models.tests`, with the spec-check notes: write behaviour-level tests for each acceptance item from the spec's Acceptance table and Test plan; search the existing tests for expectations the spec changes and update them in the same commit; write the manifest; run each `run` and confirm it fails for the intended reason; commit the tests, fixtures and manifest as one commit, `test(<ID>): freeze failing acceptance tests`; write no implementation and no stub.
  2. Red gate.
     - `stop` returns the outcome `tests-green` with the green items, and the run ends. The coordinator then either has the refiner mark the item as a `met` gate in the spec (the behaviour exists) or reruns with `from: "tests"` after the weak test is fixed.
     - `retry` sends the problems back to the test writer once. It must **amend** the freeze commit, because a second commit that touches frozen files fails the frozen check. A second `retry` returns `blocked` for this task and the run moves on.
     - The first Tests prompt says the same when `docs/specs/<ID>.tests.json` already exists on the branch (a rerun with `from: "tests"`): amend the freeze commit with `git commit --amend`, never add a commit that touches the manifest or a test.
     - On `pass` the run keeps `blobs` as `pinned` and logs the gated items.
- Phase 4, Implement: the prompt adds "Never change or delete a file listed in the manifest; add tests in new files. If a frozen test is wrong, change nothing and return it in frozenTestProblems."
- `guarded(prompt, label, phase)` wraps `work()` and is used at all three call sites (implement, follow-ups, CI fix), so a wrong test found by the review or by CI is handled the same way:
  1. Run `work()`.
  2. On `action: 'owner'`, if the task's one ruling is unused: the `product-owner` agent on `models.owner` rules on each reported test. To change one it edits the test (and the manifest when the file list changes), commits with one `Frozen-Test-Change:` trailer per path, and returns `{ rulings, changed }`. `changed` is added to `approvedPaths`, and `work()` runs again with the rulings.
  3. If the result still lists `frozenTestProblems`, or the ruling was already used, return `blocked` with the problems. They are never carried into Ship as ciSteps.
  4. Frozen gate: `check-flow.mjs --repo <worktree> --task <ID> --json`, decided with `approvedPaths` and `pinned`. `guarded` returns `{ out }` to its caller, or `{ stop }` holding the task's result (`blocked`, `frozen-tests`, `denied` or `failed`); every call site returns `stop` when it is set, the CI-fix site included. `stop` returns `frozen-tests` and ends the run. `blocked` (no manifest) returns `blocked` for this task with the message "no manifest: rerun with from: \"tests\", or pass preFlow: true for a branch that predates the flow".
- `preFlow: true` (single task, logged) is for a branch that was implemented before this flow existed. The gate then runs without `--task`, so it still checks any manifest and the task list but does not require a manifest. It is never inferred.
- After the follow-ups step (and its frozen gate), a gate agent runs `check-red.mjs <ID> --repo <worktree> --expect green` (`decideGreen`); anything but `pass` returns `blocked`. It is skipped with `preFlow`.
- Review prompt: also judge whether each frozen test really checks its acceptance item, and check each gated item the red gate listed against the spec.
- Ship prompt: fill the PR's "Frozen tests" section from `check-flow.mjs --json` (`changes`, or "none changed").
- New args: `from: "tests"`, `preFlow: true`, and `approvedFrozen: [paths]` for a resumed run. `notes` now reach the Tests and Implement steps; the comment at lines 24 to 27 and the `meta` text are updated.
- The outer loop breaks when `STOP_OUTCOMES` includes the outcome.
- Comment lines mention `work(` and `guarded(`; the source-count tests strip full-line and trailing comments before counting.
- Keep the additions compact. If the file passes about 450 lines, move prompt text into constants at the top; do not move logic out of the tested blocks.

### 5. The Product Owner pass

`scripts/task-owner.mjs apply <ops.json> --date <YYYY-MM-DD>` applies a list of operations to `tasks/prd.json` and `tasks/backlog.jsonl`, all or nothing, and keeps the canonical format:

- `add`: `{ phase, after | before, task, takes }`. `task` has `id, title, domain, model, skill, human, depends_on, acceptance, verify`; the script writes the keys in file order with `status: "todo"`, `owner: null`, `passes: false`, `evidence: ""`. The id must be new and match the phase. `takes` lists at least one backlog `what`, each matching exactly one line with no `taken_by`; the script sets `taken_by` on those lines.
- `drop`: `{ id, why }`. Refused for a task that is `in_progress` or `done`, or that another task depends on.
- `move`: `{ id, phase, after | before }`.

## Risks and out of scope

- **A forged trailer.** Covered in §2; the run's `approvedPaths` narrows it, CI cannot.
- **A gate agent that misreports.** The run's gates rely on a small agent relaying an exit code and one line. They fail closed, and CI runs the frozen check again without an agent. The red gate has no CI repeat, since the tests are green by then.
- **A test that fails for the wrong reason** (a typo, a bad command) counts as red. The test writer must confirm the reason, and the review judges the tests.
- **Red branch.** Between the freeze commit and the implementation, `pnpm check` is red on the task branch. That is intended; nothing is pushed in that state.
- **Whole files are frozen.** The implementer adds tests in new files. A test writer that touches a large shared test file freezes all of it for that branch.
- **Full-history clone** in the `checks` job costs a few seconds on this repository.
- **`task.js` size.** It will pass 400 lines. The harness is not known to load a second file, so the logic lives in `scripts/` and the file holds steps and prompts.
- **In-flight branches.** Tasks already in progress have no manifest. CI does not require one (deferred below); the run requires one unless it is started with `preFlow: true`.

## Decision log

- **The freeze marker is the commit that adds the manifest**, not a hash held by the run, because Ship rebases. It ends at merge.
