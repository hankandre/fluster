## Goal

The error panel's Retry calls `playback.retry()` with no position (`src/features/player/index.tsx:223` for the refusal notice, `:241` → `src/components/PlayerView.tsx:227` and `:291` for the error and command-error panels). `PlaybackCoordinator.retry(undefined)` then reuses `this.choice`, the start choice the session was launched with (`src/lib/player/coordinator.ts:111-113`, `:142-144`). A viewer forty minutes past their resume point who hits a network error and presses Retry goes back forty minutes.

After this task, once the failed item has shown a first frame, Retry asks Playback Negotiation for a new plan at the last position the player reported. A failure before any frame keeps today's behaviour. Nothing else about the request changes.

## Approach

All in `PlaybackCoordinator` (`src/lib/player/coordinator.ts`). The hook's `retry(startPositionTicks?)` and every caller stay as they are, so the refusal-notice Retry, the error-panel Retry, and the command-error Retry all get the new behaviour from one place.

1. **New state.** Two private fields:
   - `firstFrameShown = false`: true once the current attempt has delivered `first-frame`. Reset in `resetAttempt()` (`:426`), so each attempt starts false.
   - `lastPlayedTicks?: number`: the last position, in ticks, reported by any attempt of the current item after that attempt's first frame. It is **not** reset per attempt, so it survives a later attempt that fails before its first frame. Clear it in `start()` (with `this.selection = undefined`, `:104`), in `stop()` (with `this.choice = undefined`, `:177`), and in the `default` branch of `finishSession` (`:415-422`, natural end or explicit stop). Do **not** clear it in the `retry`/`renegotiate`/`error` branches.

2. **Recording, in `handleEvent` (`:293`).** Right after the existing `if ("snapshot" in event && event.snapshot) this.snapshot = event.snapshot;` line (`:296`), for the current attempt only (the existing `attempt !== this.attempt` guard already covers this):
   - On `first-frame`: set `firstFrameShown = true`, and if `this.snapshot` is set, record its position.
   - On any event carrying a snapshot (`loaded`, `state` of any cause, `tracks-changed`, `ended`): if `firstFrameShown`, record `secondsToTicks(snapshot.positionSeconds)` (`src/domain/playback.ts:325`, which rounds and clamps at 0).
   Recording happens before the `switch`, so it does not depend on `this.plan`, and it adds no report. A `loaded` snapshot that arrives before `first-frame` is not recorded on its own; it is recorded when `first-frame` arrives (it is then the position the player reported).

3. **Using it, in `retry` and `restart`.** `retry(startPositionTicks?)` keeps its signature. `renegotiate` is unchanged. In `restart` (`:137`), the position for a `"retry"` with `startPositionTicks === undefined` is resolved **after** `await this.stopAttempt(reason)` and the second `assertCurrentSession` (`:152-155`), not at the top of the method, so the failed session's final `ended` snapshot (the same snapshot its Stopped report carries) is included:
   - `reason === "retry"`, no explicit position, `lastPlayedTicks !== undefined` → `{ kind: "resume", startPositionTicks: lastPlayedTicks }`.
   - otherwise → today's rule: explicit position → `resume` at it; no position → `this.choice`.
   Assign `this.choice` from the result as today (`:156`), so a second Retry after a pre-first-frame failure of the retried attempt still asks for the same position. Update the doc comment on `retry()` (`:108-110`) to say this in one or two lines.

   Why only `"retry"`: `renegotiate` always gets an explicit position from the hook when a snapshot exists (`use-playback-session.ts:310-314`), and Play original passes it too. Leaving it alone keeps acceptance 4 narrow.

4. **What stays the same (acceptance 3, 4, 5).** The selection and fallback logic (`:157`, `:164-168`), the play-session reuse check (`:226-228`), `stopEncoding` (`:161`), the Stopped report (`finishSession`), and every gateway argument other than the position are untouched. For acceptance 3: after a failed track change at position P, Retry ("Back to previous tracks") asks for the fallback streams at `lastPlayedTicks`, which is the old session's last reported position (P, or the stop snapshot just after it), or at the renegotiated attempt's own last position if it showed a frame.

5. **Kind of choice.** The retried choice has `kind: "resume"`. `kind` never reaches the gateway (`createPlaybackPlan` receives only `startPositionTicks`), so a recorded 0 is equivalent to start-over.

## Risks and out of scope

- **Native `ended` snapshot after an mpv error.** The native `Ended` event carries the last accumulated snapshot (`src-tauri/src/player/events.rs:124-129`). Whether mpv resets `time-pos` to 0 before `END_FILE` on an error is unverified. If it did, the Stopped report would already carry that 0 today; this task would make Retry follow it. A real-hardware check is a dogfood gate (list it in the PR as untested on Wayland/GPU/Jellyfin). Do not add a "never move backwards" rule: a seek backwards must be honoured (Coordinator test 3).
- **Failure in the last seconds.** Retry resumes near the end and may reach end of file at once. That matches "where it stopped" (UX audit G2 says "No owner choice") and is not special-cased.
- **Browser engine's "first frame".** The dev engine emits `first-frame` on `loadedmetadata`. That is the engine's existing meaning and is not changed here.
- **File size.** `coordinator.ts` stays over 400 lines; already in `tasks/backlog.md:189`.
- **Out of scope:** the error title "Playback could not start" for a mid-film failure (P13-19 owns it); any auto-retry; rewinding a few seconds before the failure point; changing `renegotiate`; the Rust player.
