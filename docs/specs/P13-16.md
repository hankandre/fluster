## Goal

Make sign-in a calm, three-step flow built from the shared primitives: find the server, approve a Quick Connect code or type a password, and land on Home. Servers found on the network come first, every error is a plain sentence, and the unencrypted-connection warning is a real `Dialog`.

Today (`94e52b4`):

- Every step draws a kicker ("STEP 01 / CONNECTION") and a `--type-hero` heading through `Shell` (`src/features/sign-in/sign-in-shell.tsx:14-24`, `src/styles.css:12-13`).
- Errors pass `Error.message` straight to the screen (`errorMessage`, `sign-in-shell.tsx:3-5`), so a wrong password shows "Request failed with status code 401" (`audit.md:54`).
- Discovery runs only when the user presses "Find servers on this network", and the panel sits **below** the address form (`sign-in-view.tsx:139`, `server-discovery.tsx:61-63`).
- The unencrypted-connection warning is a whole step with a hero headline and a hand-made `role="alertdialog"` (`sign-in-view.tsx:147-214`).
- Quick Connect shows the code as one string, with **Cancel** as the primary button (`sign-in-view.tsx:306-326`).
- Buttons and inputs are raw elements with legacy classes (`primary-button`, `text-button`, `login-form`), not `Button` and `TextField`.

After this task:

- Each step has one `h1` in `--type-title` and no kicker. The Quick Connect and password steps show the server origin as a chip under the heading.
- On desktop the server step searches the network once by itself and lists the servers found **above** the address field, as large rows (name, address in Mono) with their warnings folded into the row. "Search again" repeats the search.
- The unencrypted warning is the shared `Dialog` over the server step. Cancel has focus, Escape cancels, and focus returns to where it was.
- The Quick Connect code is the hero: grouped digits in Mono. There is no primary button; "Use password" is secondary and "Change server" is quiet.
- Every sign-in error comes from one mapper. No transport text reaches the screen.

Behaviour that stays put (`rework-plan.md` Approach 3): the stage machine, the probe, the discovered-Id check, the confirmation store, Quick Connect polling and its abort rules, the origin line on both sign-in steps, the address field's label "Server URL" and its initial focus, and the route to Home after sign-in.

## Invariants and hard rules touched

- **Never log, persist, or display tokens, passwords, authenticated URLs, or play-session IDs.** The mapper never returns `Error.message` from a transport error, so an Axios message (which can carry a request URL with the Quick Connect `secret` query, `gateway.ts:300-311`) can no longer reach the screen. This is stricter than today. The only address shown is `gateway.origin`, which has no path, query, or user info (`normalizeServerUrl` refuses user info, `gateway.ts:119-121`). The Quick Connect secret, the password, and the token are never rendered, put in a `title` or `aria-*`, or logged. No `console` call is added.
- **Never store tokens in WebView storage, Query caches, or React state.** Unchanged. The lifted discovery result (Approach 3) holds only names, ids, and addresses from discovery replies.
- **Map errors to plain copy; never show a transport error message** (Design rules). This task closes the rule for sign-in (Approach 2).
- **`docs/security.md` changes (call out in the PR).** Q20 A changes *when* the discovery datagram is sent: once per visit to the sign-in screen on desktop, without a click. The datagram, the Rust command, the reply checks, the Id check, and the confirmation are untouched. `docs/security.md:19` and `docs/architecture.md:17` are edited to say so (Files to touch).
- **Treat every new Tauri command as an architecture change; never add a generic mpv bridge.** None added. `discover_servers` is called exactly as today, through the `ServerDiscovery` port.
- **Private-LAN plain-HTTP confirmation (ADR `docs/decisions/0001-private-lan-http.md:45-51`).** The copy, "Cancel has focus by default", and "Pressing Escape cancels" are kept word for word. `confirmUnencryptedConnection()` is still called only from the "Connect without encryption" button, before any sign-in request. A public `http://` address is still refused before any request (`sign-in.spec.ts` "a public HTTP server is refused without any request").
- **Discovery replies are hints (`docs/security.md:19`).** Each row keeps "Advertised by {ip}", the "address points to another device" note, and the conflict warning; the refused and dropped lines stay. The origin chip stays on both sign-in steps: it is the user's only cue against a spoofed reply.

### 2. Error mapper

`src/domain/sign-in-failure.ts`:

```ts
export type SignInFailureKind =
  | "invalid-address" | "public-http" | "redirect" | "unsupported-version"
  | "unexpected-response" | "not-confirmed";
export class SignInFailure extends Error {
  constructor(readonly kind: SignInFailureKind, message: string) { super(message); this.name = "SignInFailure"; }
}
```

The gateway throws it, with the **same message text**, at: `normalizeServerUrl` (`gateway.ts:114`, `:117`, `:120` as `invalid-address`; `:123` as `public-http`), `refuseRedirect` and the three `isRedirectError` sites (`:145`, `:887`, `:898`, `:909` as `redirect`), `connect` (`:219` and `:227` as `unexpected-response`, `:224` as `unsupported-version`), `requireTransportConsent` (`:261` as `not-confirmed`), `initiateQuickConnect` (`:297`) and `startSession` (`:340`) as `unexpected-response`. `SignInFailure` extends `Error`, so every existing `toThrow(MESSAGE)` assertion in `gateway.test.ts` and `gateway-redirects.test.ts` passes unchanged. The redirect sites also serve signed-in calls; the class name is the only thing those callers could notice, and none inspects it (`git grep -n "instanceof Error" -- src` before changing, to confirm).

`src/features/sign-in/sign-in-errors.ts`:

```ts
export const WRONG_PASSWORD_COPY = "That username and password didn't work.";
export const GENERIC_COPY = "Something went wrong. Try again.";
export function unreachableCopy(address: string): string;   // "Couldn't reach {address}. Check the address and that the server is running."
export function isAbort(error: unknown): boolean;            // moved, unchanged
export function signInErrorCopy(error: unknown, address?: string): string;
```

| Input | Result |
|---|---|
| `SignInFailure` (any kind) | its `message` (a fixed sentence written in the gateway; `public-http` is `PUBLIC_HTTP_REFUSED_MESSAGE`, the new §10 row) |
| object with `response.status === 401` | `WRONG_PASSWORD_COPY` |
| object with no `response` and `code` of `ERR_NETWORK`, `ECONNABORTED`, `ETIMEDOUT`, or `ECONNREFUSED`, or `message === "Network Error"`, and an `address` | `unreachableCopy(address)` |
| anything else (other statuses, bare `Error`, non-Error) | `GENERIC_COPY` (today's fallback text, `sign-in-shell.tsx:4`) |

Rules: duck-type the shape as `isNotFound` does (`sign-in-view.tsx:17-20`); do not import axios. Never return `error.message` except for `SignInFailure`. `address` is always `gateway.origin`. ### 3. Server step and discovery (Q20 A)

`useServerDiscovery(discovery?: ServerDiscovery)` lives in `SignInView`, so the result survives moving between steps:

- State: `idle | searching | found | failed` (today's `DiscoveryState`). With no `discovery` (browser mode) it stays `idle` and nothing is rendered.
- On mount it searches once. A `started` ref makes the effect a no-op the second time, because `StrictMode` (`src/main.tsx:15`) runs mount effects twice in development and Rust refuses a second search while one runs (`src-tauri/src/discovery.rs:42-48`), which would show the failure text on every dev start.
- `searchAgain()` does nothing while a search is in flight.
- Resolution of "once when the server step opens": one automatic search per visit to the sign-in screen (one `SignInView` mount). Returning to the server step from Quick Connect or the password step shows the earlier result and does not broadcast again. This sends fewer datagrams than Q20 A allows, never more.

Server step layout, top to bottom:

1. `h1`.
2. Desktop only, `section[aria-labelledby]` with `h2` "On this network" (`--type-heading`) and `ServerList`:
   - searching: `role="status"` "Looking for Jellyfin servers on this network…" with one row-shaped `Skeleton`, so the form below moves little when results arrive.
   - found: `ul[aria-label="Servers found on this network"]` of rows. Each row is one `<button class="sign-in-server" data-roving-item>`: name (`--type-label`), address (`--type-mono`), then "Advertised by {ip}" with " · address points to another device" when `addressIsSender` is false (`--type-meta`, `--text-2`), then, when `conflicting`, a `TriangleAlert` icon and "Conflict: more than one device claims to be this server. Check the address before you connect." in `--danger`. Rows are at least `--control-h` tall, `--surface-2`, `--radius-control`, with the shared focus ring. The list uses `useRovingFocus("column")`: one Tab stop, Up and Down between rows.
   - no servers and none refused: `role="status"` "No servers answered. The server may be on another network or have discovery turned off. Enter its address below."
   - `refused > 0` and `dropped > 0`: the two existing sentences, each with an icon.
   - failed: `InlineError` with `DISCOVERY_FAILED_MESSAGE` and `retryLabel="Search again"`.
   - A quiet `Button` "Search again" under the list in the found states; it reads "Searching…" and is disabled while a search runs.
3. The form: `TextField` label "Server URL", `type="url"`, `required`, `autoFocus`, placeholder `https://jellyfin.example.com`, `error` set to the mapped copy; then a primary `Button type="submit"` "Connect" ("Connecting…" and disabled while busy). On desktop a line "Or enter its address" (`--type-meta`) sits above the field.

Details that matter:
