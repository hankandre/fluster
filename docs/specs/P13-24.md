## Goal

When the user goes Back (Escape, Backspace, the browser Back button, or leaving the player through history) to Home, a library or collection, Search results, a series page, or an episode's detail page, focus lands on the card or episode row they left, scrolled into view. When that card is gone, focus lands on the card now at the same place in the same row; when the row is gone too, the screen's normal opening focus applies. The episode strip ("More from Season N") opens positioned at the current episode. Both work in the desktop and TV forms with arrows, Enter, and Escape alone.

## Approach

### 1. What is recorded

A record is `{ row: string; id: string; part: number; index: number }`:

- `row`: the `data-focus-row` value of the nearest ancestor that has one (visible row names such as "Continue watching", "Latest in Movies", "Episodes", "More from Season 1", "Season 1 episodes", and the fixed "Library" for the grid).
- `id`: the `data-focus-id` of the nearest ancestor that has one (item id, or `see-all`).
- `part`: the index of the focused `[data-roving-item]` among the roving items inside that `data-focus-id` element (0 for a card, 1 for an `EpisodeRow`'s Details link).
- `index`: the position of the `data-focus-id` element among the `[data-focus-id]` elements of that row.

Records live in a module-level `Map<string, FocusRecord>` keyed by the current history entry's id (Approach 2a) at the time of the event. Cap it at 50 entries (delete the oldest key on insert). Keying by entry, not by hash, means the same hash at two places in history (Home, detail, Home, detail) keeps two records, and a fresh visit to a hash never sees the record of an older visit. No other storage.

Why ids and not hrefs: play hrefs carry `?start=<ticks>`, which changes after watching, and the same item appears in several rows on Home (Q3 A), so the row name plus id is the stable key.

### 2a. Stamping history entries

`popstate` cannot tell Back from a fresh navigation on its own: per the HTML fragment-navigation algorithm, a `location.hash` assignment, a link click, `history.back()`, and `location.replace` all fire `popstate` and then `hashchange` (the spec check observed exactly that in Playwright Chromium; WebKitGTK unverified, but stamping works whether or not it fires `popstate` on a push). What does differ is the entry's state: a push or a replace lands on a new entry whose `history.state` is `null`, while a traversal lands on an entry that already carries whatever state it had.

- `loadId`: a random string made once per module load (for example `Math.random().toString(36).slice(2)`; it is not a secret, it only has to differ between page loads). `history.state` survives a reload, so ids from an earlier load must never match this load's records.
- `currentEntryId()`: returns `history.state.focusEntry` when `history.state` is an object whose `focusEntry` is a string starting with `` `${loadId}:` ``, else `undefined`.
- `stampEntry()`: if `currentEntryId()` is `undefined`, call `history.replaceState({ ...(stateObject ?? {}), focusEntry: `${loadId}:${++counter}` }, "")`, where `stateObject` is `history.state` when it is a non-null object. It never overwrites an existing id from this load, so a traversed entry keeps its id and its record. It keeps other keys such as `playerFromDetail` and `playerOpenedFromItem`. `replaceState` fires neither `popstate` nor `hashchange`.
- Stamp once on module install (the entry the app loaded on), and on every `hashchange` as the first thing that listener does.
- `openPlayer` order: hash assignment (push; `popstate` with `state: null`), then its own `replaceState({ playerFromDetail, ... })`, then later the `hashchange` task, where the stamp merges into that state. `use-auto-play-next.ts` and `App.tsx:50` use `location.replace`, which yields a new entry with `state: null`: its `popstate` arms nothing, and the `hashchange` stamp gives it a fresh id, never the replaced entry's.
- If some later code replaces an entry's state without merging, that entry loses its id; Back to it then simply does not restore (safe failure). Note this in a one-line comment on `stampEntry`.

### 2. When it records

Module-level listeners, installed once on import (the same pattern as `use-back-key.ts`'s `hashchange` listener), guarded by `typeof window !== "undefined"`:

- `focusin` (document, capture): if the target is inside a `[data-focus-id]` that is inside a `[data-focus-row]`, set the record for `currentEntryId()`. Else, if the target is inside `main`, delete the record for `currentEntryId()` (the user left from something that is not a card, such as the hero's buttons, the toolbar, the search field, or Load more, so there is nothing to restore). Focus outside `main` (nav, dialogs, sheets portalled outside `main`) leaves the record alone. If `currentEntryId()` is `undefined` (between a push and its `hashchange`), do nothing.
- `click` (document, capture): same rule as `focusin` for restorable targets only (WebKit does not focus links on mouse click, unverified for WebKitGTK; the click record covers it either way).
- `hashchange`: first `stampEntry()`. Then, if the new hash is `#/next/sign-in`, clear the whole map and any pending return. If a pending return exists for a different entry id than `currentEntryId()`, cancel it.

### 3. When it restores

- `popstate` (window): read the entry id from `event.state` with the same rule as `currentEntryId()`. If it is a stamped id from this load and the map has a record for it, set `pending = { entry, record, startedAt }`. A push or a replace also fires `popstate`, but with `event.state === null` (the new entry is not stamped yet), so it never arms a return; a traversal (Back or Forward) to an entry stamped earlier does. `popstate` fires before `hashchange`, so `pending` is set before `App` re-renders the destination. Every in-app Back goes through history traversal: `useBackKey` (`history.back()` when `navigatedInApp`), `leavePlayer` and `leaveToDetails` (`history.back()` when the player was opened in-app), and the browser or mouse Back button. Forward to a recorded entry also restores, which is acceptable (it is a return to that same visit).
- `tryRestore()`: if pending and `currentEntryId() === pending.entry`, look in `document.querySelector("main")` for `[data-focus-row="<row>"] [data-focus-id="<id>"]` (values escaped with `CSS.escape`), take its `part`-th `[data-roving-item]` (else the first), and `focus()` it. Focus scrolls it into view; `MediaRow` and the grid's own `onFocus` handlers keep the gutter and the toolbar clearance. Clear pending and return `true`.
- `finishReturn()`: called when the screen has settled without an exact match. Try the same row at `record.index` clamped to the row's last item (`part` 0). If the row is gone, focus the deferred default element (Approach 4) if it is still connected and focus is on `body`, `main`, or nothing. Clear pending.
- Pending is also cleared, with no focus move, on the first `keydown` or `pointerdown` after `popstate` (the user has taken over), on a `hashchange` that lands on another entry, and on sign-in clear.

### 4. Screens defer their opening focus while returning

`deferDefaultFocus(element: HTMLElement): boolean` returns `false` when nothing is pending (the caller focuses as today). While pending, it stores `element` as the deferred default for that return and returns `true` (the caller does not focus). Callers:

- `useHeadingFocus` (item detail, series, collection, library): `if (settled && !wasSettled.current && !primaryHasFocus && !deferDefaultFocus(heading.current)) heading.current.focus()`.
- `useTvPrimaryRef`: when `free`, `if (!deferDefaultFocus(element)) element.focus()`.
- Home's TV first-card effect (`home-view.tsx`): defers the same way. Keep `focusedFirstCard.current = true` only when it actually focused or deferred.
- `SearchBox`'s mount effect: `if (input && !deferDefaultFocus(input)) input.focus()`. The effect also runs when the route term changes from outside; that path is never a pending return for the current entry unless it was a Back, in which case deferring is correct.

### 5. Driving a pending return: `useFocusReturn()`

Called once in `App` (inside the `QueryClientProvider`, which `App` already relies on through `useQueryClient`). It subscribes to the module (a tiny listener set, as `use-tv-form.ts` does) and, while a return is pending:

- Runs a `MutationObserver` on `document.body` (`childList`, `subtree`, and `attributes` filtered to `aria-busy`) and calls `tryRestore()` on each batch.
- Reads `useIsFetching()` (exists in `@tanstack/react-query` 5; `build/modern/index.d.ts`). When it is `0`, `tryRestore()` has not matched, and no element in `main` has `aria-busy="true"`, it calls `finishReturn()` in the next `requestAnimationFrame` (re-checking the same conditions there).
- Starts a safety timer, `RETURN_WAIT_MS = 10_000` (a named constant; this is a give-up time, not a motion duration), after which it calls `finishReturn()`.
- Cleans up the observer, frame, and timer when pending clears or the hook unmounts.

Rule for screens: anything that must still load before its returned card can appear marks its section `aria-busy="true"` during render (Library and Search do this while catching up, Approach 6-7). Rows already set `aria-busy` while pending (`media-row.tsx`, `library-grid.tsx`, `search-results.tsx`).

### 6. Library and collection (`library-grid.tsx`)

Library sort and filters are React state, and the grid is paged (`PAGE_SIZE = 60`) with `gcTime: 0`, so a fresh mount after Back would show page one of the default order and the card left could be absent. While on a library hash, the grid writes `rememberForReturn("library", { sortId, filters, pages: query.data?.pages.length ?? 0 })` (keyed by `currentEntryId()`, same lifetime and cap as Approach 1). On mount, if `readOnReturn("library")` returns a value (only during a pending return whose entry is the current entry), it seeds `sortId` and `filters` from it instead of `initialSort` and `[]` and keeps the remembered page count in a ref (the pending return clears as soon as the card is focused, so later renders must not call `readOnReturn` again), and while `pages.length < remembered.pages && hasNextPage && !isFetchingNextPage && !isError` it calls `fetchNextPage()` from an effect and renders the section with `aria-busy="true"`. A fresh visit, including a nav click to the same library hash, is a new unstamped entry with no pending return and behaves as today: URL sort, no filters, page one (rework-plan.md Approach 3, "not remembered between visits"). Owner answer A (below).

`readOnReturn` and `rememberForReturn` take a slot name so Search and Series reuse them; the value type is checked by each caller (`switch`/guards, no `any`).

### 7. Search results and series seasons

- `search-results.tsx`: remember `{ pages }` under slot `"search"`; on return, catch up to that page count with `fetchNextPage()` and `aria-busy="true"` as in Approach 6. The term is in the route, so nothing else is needed. Q14 A ("Load more" paging) is unchanged.
- `series-seasons.tsx`: remember the shown season id (`selected.id`) under slot `"season"` on each render; on return, seed `chosenId` from it when that season still exists, otherwise Q10 A's `initialSeason` applies as today.

### 8. Row and item markup

- `MediaRow`: `<ul ... data-focus-row={title ?? label}>`, `<li key={id} data-focus-id={id}>`, See all `li` gets `data-focus-id="see-all"`. Row names are unique on each screen today (Home row titles, Search group titles, one strip per detail page); if two rows ever share a name, the first match wins, which is acceptable.
- `LibraryGrid`: `<ul className="media-grid" ... data-focus-row="Library">`, `<li key={card.id} data-focus-id={card.id}>`.
- `EpisodeList`: `<ul className="episode-list" ... data-focus-row={label}>`; `EpisodeRow` `li` gets `data-focus-id={id}`. Both the desktop list and the TV horizontal row use these components (`episode-row.tsx` switches on `useTvForm()`), so one change covers both forms; on TV `part` is always 0 (no Details link).

### 9. Episode strip start (`episode-strip.tsx`, `media-row.tsx`)

- `EpisodeStrip`: `const current = query.data.findIndex((card) => card.id === item.id)`; `startIndex = current < 0 ? 0 : Math.min(current, others.length - 1)`.
- `MediaRow` `startIndex`: pass it to `useRovingFocus("row", { spatial: true, preferredIndex: startIndex })` (moves the Tab stop only, never focus, `roving-focus.ts` docs). In a `useLayoutEffect` that runs once when `status` first becomes `"ready"` with `startIndex > 0`, compute `const gutter = parseFloat(getComputedStyle(list).paddingInlineStart) || 0` and set `list.scrollLeft += card.getBoundingClientRect().left - list.getBoundingClientRect().left - gutter` for the `startIndex`-th `[data-media-card]`. Instant, not smooth. Then call `measure()` so the page arrows update.
- Down from the action bar still reaches the strip through `moveToAdjacentRow`, which picks the nearest card by horizontal centre (DESIGN.md §9); with the strip scrolled that is near the current episode. That is the intended behaviour; the Tab stop is the start card.

## Risks and out of scope

Risks:

- **Existing focus assertions after Back.** A journey that left through a non-card (Play button, hero action, search field) and asserts heading focus after Back keeps passing, because focusing a non-card in `main` deletes the record. A journey that left from a card and asserted heading or field focus after Back would now see the card; none was found in `e2e/` (`grep -rn "goBack\|Escape" e2e/*.spec.ts` before starting; any such assertion must be updated to the new, specified behaviour and called out in the PR, never deleted).
- **Auto-play next and `location.replace`.** `use-auto-play-next.ts:35` replaces the player entry, which drops `history.state` (`playerFromDetail`), so leaving a second episode replaces the route with its detail page instead of going Back; no `popstate`, no restore. Unchanged here; log in `tasks/backlog.md`.
- **Restoring over a stale page.** Home rows refetch on return (`gcTime: 0`), so a finished item can drop out of Continue watching; the same-index fallback covers it.
- **WebKitGTK click focus** (unverified): covered by the `click` record; checked manually.
- **WebKitGTK `popstate` on fragment navigation** (unverified): the stamp makes the result the same whether it fires `popstate` on a push or not; traversal `popstate` is checked manually.
- **State overwritten without merging.** Any future `history.replaceState` that drops `focusEntry` makes that entry non-restorable (safe failure). `openPlayer` is the only `replaceState` in `src/` today (`grep -rnE "history\.(replaceState|pushState)" src`), and it runs before the stamp.
- **Reload.** `history.state` survives a reload; the per-load prefix keeps old ids from matching, and the records map is empty after a reload anyway.
- **`useIsFetching` counts unrelated queries** (nav views, prefetch); the return then waits a little longer, bounded by the safety timer.
- **File size:** `library-grid.tsx` is 182 lines; if the return logic pushes it past about 250, move it to `src/features/browse/use-library-return.ts`.

Out of scope (append to `tasks/backlog.md`):

- Restoring after auto-play next (above).
- Restoring scroll position for screens with no restorable card.
- Persisting any of this across app restarts (never: memory only).

## Decisions taken in this spec

1. The strip "opens at the current episode" means the Tab stop and scroll start at the card right after the current episode (the previous one when the current is last), because P13-09 Decision 6 keeps the current episode out of the strip.
2. When the card left is gone, focus goes to the card at the same position in the same row, then to the screen's normal opening focus.
3. Leaving through anything in `main` that is not a card or episode row (hero buttons, action bar, toolbar, search field, Load more) restores nothing; the screen opens as today.
4. Series restores the season tab that was shown on Back; a fresh visit still uses Q10 A.
5. Records are memory only, keyed by a history entry id stamped into `history.state` (the only thing written there), capped at 50, and cleared on sign-in. Back and Forward to a recorded entry restore; a push or replace, even to the same hash, never does.
6. Library restores sort, filters, and loaded pages on Back only (owner answer A, 2026-11-13).
