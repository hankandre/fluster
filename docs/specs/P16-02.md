## Goal

Home today shows a hero, then two rows, "Continue watching" (`/UserItems/Resume`) and "Next up" (`/Shows/NextUp`), then one "Latest in {library}" row per library (`src/features/home/home-view.tsx:101-119`). The hero always prefers the first Resume item over any Next Up item, whatever their dates (`src/features/home/hero-pick.ts:20-45`). Nothing ages out: a film abandoned in January sits beside last night's episode.

This task, following the owner's answers Q1 A, Q2 B, Q4, and Q14 B (`docs/plans/proposals/discovery-and-profiles.md:7-35`):

1. Fixes Home's row order and documents it.
2. Orders what the viewer is watching by most recent activity: one merged "Continue watching" row **[Q1 A]**, or two rows with the hero following the most recent activity across both **[Q1 B]**.
3. Leaves out anything last played longer ago than a window (14 days by default; 7, 14, 30 days, or Keep everything in Settings), except that a new episode brings back a series the viewer had caught up on.
4. Moves the choice of "Up next" into a pure function in `src/domain/` that implements the five rules of proposal §2.2, so the hero and the row(s) can never disagree.

Nothing is lost when an item ages out: no server write is made, its position stays on the server, and its own page still offers Resume.

## Decisions this spec makes

Decisions D2 to D14 follow from the task, the docs, and the code. D1 depends on open question 1. Parts of D7, D8, D12, and D13 depend on open questions 2 to 4, and say so.

- **D1. Row shape: open question 1.** The owner's Q2 B answer reads "one merged row, most recent first. Two rows if P16-01 shows the lists can't be ordered by last play" (proposal `:14`). P16-01 found that the lists can't be ordered from their own items (F2). The spec's proposal is that a second source (D2) supplies the missing date, so the lists **can** then be ordered, and the merged row is buildable. That is a reading of an owner-written condition, so the owner confirms it (open question 1). Either branch needs D2: acceptance 2's fallback ("the hero follows the most recent activity across both") needs the same missing date for the hero.
  - **[Q1 A] One merged row.** A Next Up item's activity date is the `LastPlayedDate` of the newest finished episode of its series in the recently-played list. This matches 12.4's own ordering exactly and 10.11.7's within one in-progress-then-reset edge (F4).
  - **[Q1 B] Two rows.** "Continue watching" holds the filtered Resume items in server order (already newest first, F1). "Next up" holds the filtered Next Up items in server order (already by series last play, F4). The hero is whichever of the two rows' first cards has the newer activity date (same dating as Q1 A). Each row keeps `HOME_ROW_LIMIT` (16) cards.
- **D2. The "recently played" request.** `GET /Items?userId&recursive=true&includeItemTypes=Movie,Episode&filters=IsPlayed&sortBy=DatePlayed&sortOrder=Descending&limit=100&enableUserData=true&enableImages=false&enableTotalRecordCount=false`. No `fields`, because `SeriesId` and `UserData.LastPlayedDate` come without them (fixtures show `SeriesId` with only `PrimaryImageAspectRatio` requested). It also gives the "last thing finished" that §2.2 rules 3 and 4 and, later, P16-05 anchor on. P16-05's text says "the last title the server marks played", hence `IsPlayed`. The limit of 100 costs no images. A Next Up series not found in a full list is handled by D5.
- **D3. The window is applied in the client, and Next Up is fetched with no `nextUpDateCutoff`.** Acceptance 6 says "as P16-01 verified". P16-01 verified that the cutoff drops exactly the new-episode case that acceptance 5 requires, and it recommends the client rule (F5). So Fluster sends no cutoff, and a pure function filters. That function is unit tested at the boundary and for the new-episode case. The PR states this in one line that cites the source, so the reviewer can check acceptance 6 directly, for example: "Home sends no `nextUpDateCutoff`: on 10.11.7 and 12.4.0 a cutoff after the series' last play keeps a caught-up series out even when its new episode is newer than the cutoff (`docs/research/discovery-api.md` §3; fixture `tests/fixtures/jellyfin/{10.11.7,12.4.0}/discovery-nextup-new-episode-cutoff-mid.json`), which defeats acceptance 5. The window is the pure filter in `src/domain/up-next.ts`."
- **D4. Home's Next Up request changes.** It now sends `enableResumable=false` (F3: no duplicate with Resume, no double card for one series) and `fields=PrimaryImageAspectRatio,DateCreated` (F6). The rest is as today. The series-page `seriesNextUp` call (`gateway.ts:550-570`) is unchanged.
- **D5. The window rule** (pure, `now` passed in; `start = now - days × 86 400 000 ms`; "Keep everything" means no start). The same rule applies in both Q1 branches:
  - An in-progress item stays when `lastPlayedAt >= start` (inclusive). An item with no `LastPlayedDate` (not seen on either version, F1; possible on other servers) stays and sorts after every dated item. A date can't prove it old, and nothing should vanish for want of one.
  - A next episode's activity date is its series' date from D1. It stays when that date is `>= start`, **or** when the episode's `DateCreated >= start` and `DateCreated` is later than the series' last play. The second case is the new-episode rule: the episode arrived after the viewer last watched, so they had caught up. It then ages out a window after it arrived. There is no limit on the gap between the last play and the arrival (acceptance 5: "even when its last play is older than the window").
  - A series not found in the recently-played list: if the list came back shorter than the limit, the series has no finished episode in it, so it counts as older than any start. If the list is full, its last play is at or before the list's oldest date (the horizon). When the horizon is before `start`, it counts as outside the window. Otherwise Fluster can't tell, so the item stays. Either way, such items sort after the dated ones, in the server's order.
  - When the recently-played request fails, every next episode is "can't tell": it stays, sorts after the in-progress items, and keeps the server's order. The row still shows. Only its interleaving (or, in Q1 B, the hero's choice between rows) degrades.
  - The function also returns **`agedOutIds`**: every Resume id and every Next Up id the window removed, plus the `seriesId` of every removed episode (Resume or Next Up). The series ids are there so that a Latest row's Series card for an aged-out series is never the hero: P3-27 plays a Series card from its next-up episode, which is the aged-out item (acceptance 3: "never the hero").
- **D6. Ordering.** **[Q1 A]** Dated cards sort by activity date, newest first. Ties keep the order they arrived in (Resume before Next Up, then server order), so the result is deterministic. Undated cards follow, Resume's first, then Next Up's. New-episode cards sort by their series' last play, as "most recently played first" in acceptance 2 literally says. The row keeps `HOME_ROW_LIMIT` (16) cards. **[Q1 B]** Each row keeps its server order after filtering (D1). A tie between the two rows' first cards goes to Continue watching (today's preference).
- **D7. Up next (§2.2).** Rules, first match wins:
  1-2. **Row**. **[Q1 A]** Q2 B's option text says "the hero is its first item" (proposal `:588`), so rules 1 and 2 become "the merged row's first card", and a rule-3 or rule-4 hero never contradicts a non-empty row. **[Q1 B]** The newer of the two rows' first cards (D1, D6).
  3. **Sequel**: the anchor (D2's newest entry; whether it must be inside the window is open question 4) is a Movie in a collection, and that collection has an unplayed film **after** it. Members are sorted by `PremiereDate,ProductionYear,SortName` ascending. Rule 3 takes the first unplayed member after the anchor. If the only unplayed members come before the anchor, rule 3 does not match. On a server whose collections route answers 404 (10.11.7), behaviour is open question 3.
  4. **Similar**: the first item of `/Items/{anchor}/Similar` that is not played. For an Episode anchor, this uses the series' Similar (`SeriesId`).
  5. **Newest**: the first Movie, Episode, or Series of the first non-empty Latest row, as today (`hero-pick.ts:36-43`).
  No rule ever picks an aged-out item: rules 3 to 5 skip any card whose `id` is in `agedOutIds` (D5), and any Series card whose `id` is in `agedOutIds`. Rule 3 and 4 candidates must also be unplayed and have no resume position.
- **D8. Where the pending logic lives.** `src/domain/up-next.ts` holds the pure rules over plain data. `src/features/home/hero-pick.ts` keeps the "wait while an earlier source is pending, so the hero never jumps" behaviour (today's `Source<T>` pattern), and it calls the domain function once the sources it needs have settled. Rules 3 and 4 fetch lazily. Their queries are enabled only when the row(s) are empty and an anchor exists (subject to open question 4), so a normal Home makes no extra request.
- **D9. Row states.** The row(s) are `pending` until Resume, Next Up, **and** recently-played have each settled, so the order never reshuffles after first paint (N2). **[Q1 A]** The merged row shows the `InlineError` "Couldn't load Continue watching." (`DESIGN.md` §10 "Couldn't load {row}.") when Resume or Next Up fails. Retry refetches the failed ones. **[Q1 B]** Each row keeps its own error and Retry, as today. A recently-played failure is silent (D5). A row hides when empty after filtering (`DESIGN.md` §7.4, as today).
- **D10. `now`.** The row and hero use `now` = the newest `dataUpdatedAt` of the three source queries. It is not `Date.now()` at render, so re-renders and focus moves never move the boundary. The boundary moves only when the data is refetched (after playback, through `refreshHomeRows`). Tests that mount Home pin the clock (see Test plan), because `dataUpdatedAt` comes from `Date.now()`.
- **D11. Fixed order** (acceptance 1, Q1 A of the proposal, proposal §2.4): **[Q1 A]** hero, Continue watching, then each "Latest in {library}" in `/UserViews` order. **[Q1 B]** hero, Continue watching, Next up, then each "Latest in {library}". P16-05 ("Because you watched") and P15-09 (Favorites) will add their rows at places their own tasks set. `DESIGN.md` §7.4 says so without promising a slot. The order never depends on data, account, or ranking. An empty row hides, and the others keep their relative order.
- **D12. Rules 3 and 4 add gateway methods now**: `similarItems`, and, unless open question 3 drops rule 3 entirely, `itemCollections` and `collectionItems`. P16-04 will reuse `similarItems` for "More like this". The P16-01 fixtures cover all three. `itemCollections` returns `undefined` on 404 ("this server can't say"). Open question 3 decides what Fluster does then.
- **D13. The window preference** is a new field, `continueWindow: "7" | "14" | "30" | "all"`, default `"14"`, in `PreferenceValues`. `sanitizePreferences` validates it and falls back to `"14"`. `PREFERENCES_VERSION` stays 1, because a missing field reads as its default. `Preferences` (`src/app/preferences.tsx`) gains a narrow `continueWindow` accessor, `{ get, set, subscribe }`, built like `streamingLimitsOf`. Home reads it with `useSyncExternalStore`, so a change applies on the next render without a refetch. It is not a token, credential, URL, or user id (the rule at the top of `preference-store.ts`). Its place, label, description, option labels, and toast in Settings are open question 2; build exactly the recorded answer.
- **D14. Re-recording fixtures.** Acceptance 9 asks for gateway tests "against the P16-01 fixtures". The new recently-played request has none, so the implementer extends P16-01's recorder (`tests/integration/record-discovery-fixtures.mjs`) with one fixture per version, `discovery-recently-played.json`. It is recorded in a scene with fixed dates: `item-h264` played at `OLD`, `item-ass` played at `RECENT_2`, `item-episode-1` played at `RECENT_3`, `item-multitrack` in progress at `RECENT_1`. The fixture shows the order, `SeriesId`, `LastPlayedDate`, and that the in-progress film is absent. `discovery-fixtures.test.ts` gains sentence-named `it`s for it, and `docs/research/discovery-api.md` gains one table row. The rerun renumbers `id-N` values in the other fixtures. The implementer commits only the new fixture files and the recorder change, and restores the regenerated old ones with `git restore`, as long as the existing fixture tests still pass against them. If Docker or the fixture servers are unavailable, the task is blocked: say so in `evidence` and do not hand-write the fixture.
