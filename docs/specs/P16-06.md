## Goal

A viewer on a film or series page can activate a genre in the facts line and land on that title's library grid filtered to the genre, with the usual sort, chips, count, paging, and Back. Every movie and TV library's toolbar gains a genre `Picker` filled from `GET /Genres` for that library. The genre lives in the URL. Home is unchanged.

## Approach

1. **Gateway.** `libraryGenres(parentId)` sends exactly what P16-01 recorded: `GET /Genres` with `{ userId, parentId }`. No `includeItemTypes`, `fields`, or image params: each would be an unrecorded variation (the fixture shows the server returns only genres of the library's titles). `toGenres` keeps entries with `Id` and `Name` and keeps the server's order (the fixture is alphabetical). `libraryItems` adds `params.genreIds = query.genreId` when set; everything else is unchanged, so the request matches the A10 fixture plus `parentId` and the paging params already sent today.
2. **Route.** `?genre=<encodeURIComponent(id)>` after `sort` and `filters`. The default (no genre) writes nothing. An empty value is no genre. The collection route never carries one. All route strings stay in `routes.ts` (`route-literals.test.ts`).
3. **Which library a facts-line genre opens** (pending Open question 3; this is the recommended default). `genreLibrary(item, views)`, pure:
   - Only `Movie` and `Series` link. The fitting kind is `movies` for a Movie and `tvshows` for a Series.
   - If a view of the fitting kind has `id === item.parentId`, use it (a title stored directly in a library folder has that library as its parent; **unverified** that a library's user-view id equals its folder id on 10.11.7 and 12.4.0; checked on the dogfood server).
   - Otherwise use the first view of the fitting kind in nav order.
   - No fitting view, or views not loaded or failed: the genre stays plain text. It never blocks the page.
   - `genreLinks` takes the first two genres (as today) from `genreItems`; a genre name with no id stays plain text.
4. **Where links appear.** Film and series pages only. Episode facts and the Home hero keep plain text: the hero has its own focus order (§7.3), and §7.7 says episode facts carry no genres. (Pending Open question 4.)
5. **Toolbar.** `BrowseView` asks for genres only for `movies` and `tvshows` libraries, in parallel with the first page. The `Picker` options are `{ value: "all", label: "All genres" }` then one per genre (`value` = id). Picking "All genres" removes the genre from the route. Choosing a genre calls `stopCatchUp()` and `onViewChange`, like Sort. The `Picker` is absent while genres load, when the list is empty, and on error (no error copy: the toolbar is still usable, and Jellyscale answers `/Genres` as a stub today).
6. **A route genre the list lacks.** The grid applies the route's genre immediately, so a link from a facts line shows filtered results without waiting. When the genre list loads successfully and does not contain the route's genre, `replaceRoute` drops it and the grid refetches unfiltered. If the list fails, the genre stays applied without a `Picker`; filtered-empty's "Clear filters" still clears it. Logged as a risk.
7. **Facts row focus.** With links, the facts line is one roving spatial row: Left and Right move between links, Up and Down are spatial. Initial focus is unchanged (`h1` on desktop, primary on TV). Back to the title restores focus to the activated genre link through the existing focus-return stamp (the link carries `data-focus-id` like other restorable targets; if the facts row is not a restorable container today, the implementer adds it the way `SeriesLink` rows are handled, or logs the gap in the plan).
8. **Copy.** "All genres"; trigger accessible name "Genre {value}" by the `Picker`'s existing label-plus-value pattern ("Sort Name A to Z"). Genre names come from the server as is. No new error or empty copy.

## Risks and out of scope

Risks:

- `GET /Genres` with `userId` is assumed to hide genres whose titles the viewer cannot see (parental rating, library access). The fixtures show library scoping only. **Unverified**; check on the dogfood server with a restricted user before ship and log the result in the PR.
- The parent-id library match is **unverified** (Approach 3). If it never matches, the fallback (first library of the kind) still opens a correct, filtered library in single-library households, but can open the wrong one when there are several movie or TV libraries (Open question 3).
- A `/Genres` failure leaves a route genre applied without a visible `Picker` (Approach 6). Low impact; the URL and Clear filters still show and remove it.
- A series library filtered by a genre that only episodes carry would show filtered-empty. Not seen in fixtures.
- Jellyscale answers `/Genres` as a stub (`docs/research/discovery-api.md` §1): the Picker is absent there, by design.
- Visual baselines change on many detail and library scenarios; accept from the CI run as recent tasks did.

Out of scope:

- Genre rows on Home (Q7 A; backlog "Revisit genre rows on Home after the dogfood week").
- Genre links on the Home hero and on episode pages (Open question 4).
- Multi-genre selection, `/Items/Filters2`, studios, tags, people (P16-07).
- A cross-library genre page (only if Open question 3 picks it).
- Remembering the genre between visits.
