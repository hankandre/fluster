## Approach

### 1. `PlayerView` props and composition

Existing props stay. New props:

- `status: ReadyPlayerStatus`, `playMethod?: PlayMethod`, `indicator?: ConversionIndicator` (for `InfoSheet`, the chip, the OSD line, and `PlayerLoading`).
- `playOriginal?: { available: boolean; stillConverting: boolean; onPlay(): void }`. `index.tsx` computes `available = Boolean(plan?.playOriginalAvailable) && !retrying` and `stillConverting = playOriginalRequested && plan?.delivery === "hls" && !retrying`, exactly today's two conditions (`index.tsx:211-214`).
- `backdrop?: { src?: string; blurHash?: string }` for `PlayerLoading`, built in `index.tsx` from `detail.backdrop` with `gateway.imageUrl`.
- `prompt?: ReactNode`: the Up Next card, rendered inside the player section so focus inside it keeps the chrome up.

Markup: `<section className="player-page" aria-label="Player">` (the §11.6 `region`), containing `NativeVideoSurface`, then either `PlayerLoading` or the chrome, then `PlayerStatus`, `Osd`, the warnings and error panel, `SkipSegmentButton`, `prompt`, and the open sheet.

Phases:

- `!session.firstFrameReady && !error`: `PlayerLoading` only. No top bar, scrubber, or controls are rendered. It is opaque (`--void` under the backdrop), so it replaces `.video-loading-cover`. A renegotiation resets the session, so `PlayerLoading` shows again with the new reason.
- First frame ready: the chrome. `PlayerStatus` shows "Buffering…" while `snapshot.buffering`.
- `error`: the existing panel (`player-error.tsx`), content and copy unchanged ("Playback could not start", Retry, "Back to library"). P13-15 restyles and relabels it.

An open sheet stays mounted through a renegotiation; its options are disabled until the new snapshot arrives.

Import rule: chrome files never import from `PlayerView.tsx` or from a deleted module (`pnpm lint:boundaries` has `no-circular` with `tsPreCompilationDeps`, so type imports count). `SeekChapter` and the clock helpers live in `chrome/player-time.ts` and `ConvertedTracks` in `chrome/track-options.ts`; `PlayerView.tsx` re-exports `SeekChapter`.

### 6. `Osd`

`useOsd()` returns `{ message, show(text, kind?) }`. One message at a time; a new one replaces the old and restarts the timer (`OSD_MS`, or `OSD_NOTICE_MS` for `kind: "notice"`). `Osd` is a `role="status"` pill at top centre below the top bar's height, `--surface-1` fill, `--type-label`; notice kind uses `--notice` text with the `RefreshCw` icon. It fades with `--dur-quick` (0 ms under reduced motion through the token). It never takes focus or pointer events. The element stays mounted and empty between messages so the live region works.

Status regions: `Osd` is `role="status"` named "Player message" and `PlayerStatus` is `role="status"` named "Player status", so tests ask for the one they mean. The chip is a button, not a status. Replacements, none weaker: the chip by `getByRole("button", { name: /Converting on server|Repackaging on server/ })` for its text, and the "Player message" region for the OSD line (`player-view.test.tsx` 855, 878, 882, 902, 912); the Up Next countdown scoped to `getByRole("complementary", { name: "Up next" })` (`auto-play-next-view.test.tsx` 153, 284, 291, 299); and for direct play (`player-view.test.tsx:846`) "no chip button, an empty Player message region, and the Info sheet says Original file".

Messages (`osd-copy.ts`), posted by the key handler whether or not the chrome is visible:

| Key | Text |
|---|---|
| Left, `j` / Right, `l` | "−10 s" / "+10 s" |
| Up, Down | "Volume {n}%" (the clamped target) |
| `m` | "Muted", or "Volume {n}%" on unmute |
| `c` | "Subtitles: {title}", "Subtitles: Off", or "No subtitles" when there are none |
| Home / End | "Start" / "End" |
| 0–9 | "{n}0%" ("0%" for 0) |

No OSD for Space, `k`, `f`, `i`, `a`, or Escape: each has its own visible effect.

## Risks and out of scope

Risks:

- **Invariant reading.** The chip is off screen while the chrome is hidden. Approved as Q15 C; the OSD line, loading text, and Info sheet tests are what keep it honest. A regression in the first-frame effect would silently drop the OSD line, so it has both a component test and an e2e assertion.
- **Arrow keys in the track list.** Without the `list` target kind, Up and Down in the panel would change the volume. Covered by keymap and e2e tests.
- **End key.** Seeking to the duration ends the file, which follows the normal end path: the next episode starts (and the finished one is marked played, `index.tsx:139-145`) or the player closes. This is what the acceptance asks for; note it in the PR.
- **First frame never arrives.** The chrome now waits for the first frame. `PlayerLoading` keeps Back and Escape, and an engine error shows the error panel, so the user is never stuck. Audio-only sources are not supported by the catalogue today. Check on the native build (part of the Wayland gate).

- **Test churn.** About 30 unit assertions and 10 e2e selectors move. The reviewer compares each edited test against `origin/main`.
- **`src/styles.css` deletions.** Search for each class literally before deleting; P13-14 and P13-15 still use `.next-episode-*`, `.skip-segment-button`, and `.player-message*`.

## Decisions

1. `PlayerView.tsx` and `player-keymap.ts` stay in `src/components/`; all new code is under `src/features/player/chrome/`. Moving them would collide with the existing `src/features/player/player-view.test.tsx` and widen the diff of the largest P13 task.
2. `a` opens the track panel in this task. DESIGN.md §9 already accepts the key, the panel is built here, and nothing else gives one-key access while the chrome is hidden. It adds a binding and changes none.
3. The top bar's Back button is named "Back".
4. Chip and loading text keep the PRODUCT.md sentences rather than the shorter DESIGN.md example.
5. OSD shows for key actions whether or not the chrome is visible (acceptance 3 is unconditional).
6. The software-decoding and progress-report banners stay as they are (rework-plan Approach 3: behaviour stays put).
7. "Loading…" is the pre-plan status text: "Opening the original file…" would be a claim the client cannot make before the server answers.
8. Sheets are non-modal and not built on `Dialog`.
9. The chrome stays up from the first start until the pointer first moves, as today; it then hides 3 s after the last pointer move, and 3 s after a resume from a pause. A mouse-move at the same position (the browser repeats one when the element under a resting pointer changes) is not input. Keyboard focus on a chrome control holds the chrome up; a control focused by a click does not.
10. Home and `0` are the same action (`seek-to` 0) and both show "Start"; End shows "End"; `1` to `9` show "{n}0%". The action carries no key.
11. Opened with a key, the Info sheet focuses Close, not Play original: Space is the pause key, and it must not start a new session. Only the chip (Q16 A) focuses Play original. The Left and Right keys on the focused scrubber give no OSD line: the preview shows the position.
12. The play method used by `PlayerLoading` is `playMethod !== undefined` (a plan always carries one), so `index.tsx` passes `playMethod` and no separate `planKnown`.
13. An error with no first frame draws the chrome (Back, disabled controls) and the error panel over an opaque cover, so Back and the panel's Back to library both exist.
14. A renegotiation resets the first frame and unmounts the chrome, but not an open sheet; focus returns to the opener on close only while the opener is still on the page.
