## Approach

### 1. `PlaybackNotice` shell

```ts
interface NoticeAction { label: string; onActivate(): void; busy?: boolean }
interface PlaybackNoticeProps {
  title: string;
  context?: string;               // item title line; omitted when unknown
  backdrop?: LoadingBackdrop;     // from chrome/player-loading.tsx
  children?: ReactNode;           // explanation
  whatYouCanDo?: string;          // rendered as <p><strong>What you can do:</strong> {text}</p>
  retry?: NoticeAction;           // primary, first
  back: NoticeAction | { label: string; href: string };  // secondary; primary when there is no retry
  onEscape(): void;
}
```

- The root is `div.playback-notice` with `role="alert"` (as today's refusal and cannot-start text; `player-view.test.tsx:228` and `:665` query it, and visual scenario 58 waits for it). Its styles are `position: absolute; inset: 0; min-block-size: 100vh; background: var(--surface-0); z-index: var(--z-dialog)`. Inside it, in order:
  - `div.playback-notice-art`: absolute, inset 0, `opacity: 0.3`, with the BlurHash data URL as its background via `blurhashToDataUrl`, then `<img alt="">`.
  - `div.playback-notice-scrim`: `background: var(--scrim-floor), var(--scrim-hero)`.
  - `Notice`, in a relative layer above.
  - Override `.playback-notice .ui-notice { min-block-size: 100vh; }`, because the player route has no nav.
- `Notice` gets `headingLevel={1}`, `headingRef`, `context`, the body, `whatYouCanDo`, and `actions`.
  - `actions` is a `div.playback-notice-actions` with `role="group"` and `aria-label="Actions"`. It holds Retry (when present), then Back to details.
  - Both buttons stay normal Tab stops.
  - An `onKeyDown` on the group moves focus to the next or previous button on ArrowRight or ArrowLeft (no wrap) and calls `preventDefault`.
  - Do not use `useRovingFocus` here. A roving row keeps one Tab stop, so Tab would skip Back to details (acceptance 3).
- The heading takes focus on mount (`useEffect(() => headingRef.current?.focus(), [])`), as `RefusalScreen` does. An `onKeyDown` on the root handles ArrowDown and ArrowRight: when the event target is the heading, it focuses the first action and calls `preventDefault`.
- Escape: the three route-level notices use `useEscapeKey(onEscape)`. `PlaybackErrorNotice` inside `PlayerView` passes a no-op `onEscape` and relies on `usePlayerKeys` (Approach 6), so Escape is not handled twice.
- Busy Retry: `disabled` plus `LoaderCircle` (`className="spin"`), as `PlayerErrorPanel` does today.
- `noticeContext(item: LibraryItem)`: `"{seriesName} · {titleLine(item)}"` for an episode with a series name, else `titleLine(item)` (reuse `titleLine` from `chrome/player-top-bar.tsx`).
- `noticeBackdrop(gateway, detail)`: the expression now inline at `index.tsx:162-164`, moved here and reused by `PlaybackScreen`.

### 5. Where Back to details goes (Q1 A, settled)

Today every Back on these screens calls `leavePlayer` (`routes.ts:113-120`), which goes back through history to whatever opened the player. That can be the detail page, Home (hero and Continue Watching use `playActivation`, `card-view.ts:70-76`), or the series page (`series-body.tsx:83`, `series-seasons.tsx:98`).

- New `parseItemRoute(hash: string): string | undefined` in `routes.ts`, mirroring `parsePlayRoute`. It requires the `#/next/item/` prefix, drops any `?query`, rejects an empty id or a literal `/`, and returns `decodeURIComponent(id)` (or `undefined` if decoding throws).
- `openPlayer(route)` reads `window.location.hash` **before** it changes the hash. It computes `openedFromItem = parseItemRoute(previousHash) === route.itemId`, which compares decoded ids so the encoding cannot differ. It then calls `replaceState({ playerFromDetail: route.itemId, playerOpenedFromItem: openedFromItem }, "")`. Keep `playerFromDetail` so `leavePlayer` is unchanged. Store a boolean, not the raw hash.
- New `leaveToDetails(itemId)`: if `history.state.playerFromDetail === itemId && history.state.playerOpenedFromItem === true`, call `history.back()`. Otherwise call `location.replace(itemRoute(itemId))`. When the player was opened from Home, history becomes Home → detail, so Back from the detail page returns Home.
- The route-level notices (cannot start, load failure) call `leaveToDetails` directly. `PlaybackScreen` keeps `leaveTarget = useRef<"opener" | "details">("opener")`. Its `onBackToDetails` sets `"details"`, then calls `playback.back()`. Its `onLeave` calls `leaveToDetails` when the ref says so, and today's logic otherwise. `use-playback-session.ts` is not edited.
- Escape and the player top bar's Back keep `leavePlayer` (§9: Back closes the topmost layer and returns).

## Decisions

1. Notices keep their current titles. Only the labels in Approach 3 and the Q2 A title change. Source: `decisions-P13.md` "Not asked" (copy settled), Q2 A, and AGENTS.md "Never edit acceptance items".
2. Back to details is a button on every notice, never a link that pushes a history entry. A pushed detail entry would make browser Back restart playback.
3. Plain buttons plus an arrow handler, not `useRovingFocus`, so Tab still visits Retry and then Back to details (acceptance 3) and arrows still work (DESIGN.md §9).
4. The playback error notice replaces the whole chrome, but only for `session.error`. The notice is a full-screen state (§7.16) with one `h1` per screen (§11.6). A failed command keeps today's card, so a failed volume change does not hide working playback or lock the keys.
5. A 404 on the play route uses §10 "Item gone" with Go home instead of a pointless Retry.
6. Opacity `0.3` is a literal, matching §7.16's "30%". No new token.
7. `leaveToDetails` compares decoded ids (`parseItemRoute`) and stores a boolean in history state, not the opener hash.
8. Visual: no `58a` duplicate of `58-player-refusal`, and no `noDirectPlay` mock option.
